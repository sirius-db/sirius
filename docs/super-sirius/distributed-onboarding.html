Distributed Sirius

How one SQL query runs across many GPUs, and how to start using it.

Summarized from the documents in docs/super-sirius/ of branch experimental/distributed-sirius, as of commit d9d973a (18 November 2026). Each section names its source document, and the last section lists them. A shorter version is in the slide set.

Sections 01 to 08Understand itWhat it is, the gateway and the ranks, how a query runs across GPUs. Sections 09 to 14Use itBuild, start a cluster, send SQL, run a first benchmark. Sections 15 to 18Look things upLimits, code map, what the branch adds, further reading.

Experimental. Distributed execution is experimental: its settings can change or go away between releases. Through the gateway, CPU fallback is off, so a query Sirius cannot run on the GPU fails instead of running on the CPU.

In one minute

Sirius is a GPU SQL engine that runs inside DuckDB as an extension. Distributed Sirius runs one SQL query across several Sirius processes, one per GPU, on one machine or on several.

One endpointYou connect a DuckDB shell to a gateway and type plain SQL. The gateway sends each statement to every GPU process.
Same SQL everywhereEvery process (a rank) plans and runs the same statement on its own share of each table. Rank 0 returns the result.
Rows move between GPUsWhere a join, a group-by or a sort needs rows from other ranks, the plan has an exchange. It moves batches GPU to GPU, over NVLink where the hardware has it.
  • A machine with several GPUs does not need the gateway for everyday use: pixi run duckdb uses every visible GPU in one process. The gateway is for several machines, and for benchmarks, where every run goes through it so that the numbers compare.
  • Three commands start a cluster: pixi run sirius-gateway, pixi run sirius-node on each GPU machine, pixi run sirius-client. See Getting started.
  • It has been run with 4, 8 and 16 ranks (one, two and four GB200 nodes with 4 GPUs each).

Vocabulary

The documents, the commands and the logs use these words. Nine carry most of the meaning.

WordMeaning
RankOne Sirius process (DuckDB with the Sirius extension) on one GPU. Ranks are numbered from 0. Rank 0 returns the result of every query.
NodeA GPU machine. sirius-node starts one rank per GPU on it.
GatewayA CPU-only DuckDB with the sirius_gateway extension. It is the one SQL endpoint: it puts statements in order, numbers the queries, sends them to every rank, and restarts the ranks when something fails. It needs no GPU.

Architecture

Source: distributed-gateway.md, distributed-sirius.md

PartWhat it doesWhat it does not do
GatewayOrders statements across all clients, gives each query a number, sends it to every rank in parallel, returns rank 0's result, keeps the DDL log, restarts the ranks after a failure.It does not plan or execute queries: the ranks do.
RankPlans the statement with DuckDB and Sirius, rewrites the plan for distribution, scans its share, exchanges rows with the other ranks, runs every operator on its GPU.It does not coordinate the others: every rank works from the same statement and reaches the same plan.
Launch scriptssirius_gateway.sh, sirius_node.sh, sirius_rank_node.sh, sirius_client.sh, sirius_slurm.sbatch: start the processes, register ranks with the gateway, restart a rank that exits.

The one rule everything follows from: every rank must run the same statements, in the same order, with the same query numbers. Exchange streams are numbered by query, so ranks that disagree on the number could not find each other's data. The gateway exists to guarantee this.

Life of a statement

Source: distributed-gateway.md, "How a statement runs" and "Routing"

  1. Route. Quack hands the client's statement to the gateway's router. Most statements are rewritten to run on every rank. A few stay on the gateway, and a few are refused (table below).
  2. Wait for the turn. The gateway runs one statement at a time, in arrival order across all clients, so every rank sees the same order.
  3. Number and send. The gateway takes the next query number K, and sends SET sirius_distributed_query_id = K and then the statement to every rank in parallel. The ranks must run together: they wait on each other inside the exchanges.
  4. Return and record. When every rank is done, the gateway returns rank 0's result. A statement that succeeded on every rank and is not a SELECT, EXPLAIN or transaction statement is added to the DDL log.
StatementWhere it runs
Queries, DDL, INSERT, COPY, ordinary SETEvery rank
sirius_gateway_status(), sirius_gateway_log()The gateway
BEGIN, COMMIT, ROLLBACKThe client's own gateway session. Each statement still commits on the ranks as it runs
SET of a setting the gateway controls (sirius_exchange_*, enable_duckdb_fallback, gpu_execution, the query number)Refused
PREPARE, EXECUTERefused: a prepared plan keeps the query number it was planned with
Other sirius_gateway_*, quack_*, sirius_rank_* callsRefused from clients: gateway console only. The exception is sirius_gateway_add_rank and sirius_gateway_drop_rank when the gateway was started without ranks of its own, so that nodes can register theirs

Things that surprise newcomers, all consequences of the ranks sharing one session each:

  • A client's SET reaches every client's later statements, and is replayed after a restart.
  • CREATE TABLE and INSERT give one copy of the rows per rank. Use views over read_parquet for data that must be split.
  • now() and random() evaluate on each rank. A ROLLBACK does not undo what ran on the ranks.

Life of a distributed query

Source: distributed-sirius.md, "How a query runs" and "The plan rewrite"

Each rank first builds the ordinary single-GPU plan. A rewrite step, distribute_plan(), then walks that plan and inserts an exchange where the single-GPU plan already partitions its data. A distributed plan holds the single-process operators plus the two exchange operators, and nothing else.

The four exchange modes

ModeWhere each row goesUsed for
hashTo the rank chosen by a hash of the key columnsJoins (both sides by join key), grouped aggregation (by group key)
broadcastTo every rankA small join build side; nested-loop joins. The probe side stays where it is
rangeTo the rank that owns the key's rangeA global ORDER BY: every rank derives the same boundaries from a shared sample
gatherTo one rank (rank 0)Ungrouped aggregates, top-N, and the final result
Where the rewrite puts each exchangeseven plan shapes
Plan shapeExchange
Hash joinhash on the join keys, below each side's partition step
Hash join with a small build sidebroadcast of the build side. "Small" is an estimated size of at most 1 GiB and at most the probe side's divided by (ranks − 1), for join types that emit build rows only with a probe match
Nested-loop joinbroadcast of the build side
Grouped aggregation (partial, then merge)hash on the group keys, between the partial and the merge. With COUNT(DISTINCT), below the partial instead
Ungrouped aggregate; top-Ngather to rank 0 between the partial and the merge
Sort (ORDER BY)range between the sample and the partitioned sort
The resultgather to rank 0, in rank order after a distributed sort

Scans, filters, projections and dynamic filters stay on the rank where their input is.

Who reads what

  • Local Parquet files of a table are laid end to end and cut into equal byte spans, one per rank. A rank reads the row groups whose start falls in its span, so every row group is read exactly once and a one-file table still splits. A table of one row group lands on one rank.
  • Remote files (S3) are not split by bytes: each rank takes files rank, rank + ranks, …, so a remote table needs at least as many files as ranks.
  • Every rank binds every file, so DuckDB plans every rank from the same statistics.
  • Only Parquet tables read through read_parquet's file list are split. A DuckDB table is refused.

Two safety checks

  • Plan-shape check. Before running, every rank shares a hash of its plan's shape with every other rank. If any differs, every rank fails the query.
  • Refusal rather than a wrong answer. A plan shape the rewrite does not know is refused with a "not implemented" error, because running such an operator on each rank's share would return a wrong answer. The list is in Limits.

Moving rows between ranks

Source: distributed-sirius.md, "Layers"

The exchange is built in layers. Each is tested without the ones above it.

LayerWhat it doesCode
Wire formatA batch travels as one byte stream cut into frames, in the layout the host memory tier already uses. So the same frames can land on the GPU or in host memory. Columns are fixed-width or strings.src/exchange/wire.*, batch_io.*
TransportSend and receive rings, credits, landing, end of stream, failure. One engine thread owns it.src/exchange/transport.*, messages.*, fabric.hpp
NIXL fabricRegisters the rings with NIXL's UCX backend, fetches every peer's metadata, sends a hello. After that everything is a NIXL write or a notification.src/exchange/nixl_fabric.*
OperatorsEXCHANGE_SINK routes batches by mode; EXCHANGE_SOURCE starts a pipeline with what the senders sent.src/op/sirius_physical_exchange_{sink,source}.*
Collectivesall_gather(): every rank sends one small table to every rank and waits for all. Used for sort samples, the plan-shape check and the Bloom merge, and in the code also for a HAVING optimization (enable_complete_group_having).src/exchange/all_gather.*

Flow control: credits

  • The receive ring is split evenly among the peers at start. A sender writes only into the frames it holds, and gets each one back once the receiver has copied it out.
  • An incoming batch lands on the GPU if memory is free now, otherwise in host memory. With no room in either, its frames stay in the ring and keep their credits. That stops the sender until room appears.
  • The rings are the only memory NIXL registers. By default a rank's rings take 16 MiB × (32 + 16 × peers): 768 MiB with 2 ranks, 2.25 GiB with 8, 4.25 GiB with 16. This memory is outside the GPU memory budget.

Which path the bytes take

Each rank chooses a path to each peer at start, and logs it.

The peer isPathMeasured
On this host, GPUs with peer accessUCX cuda_ipc, zero-copy GPU to GPU
On this host, no peer access between the GPUsHost staging: one copy into a pinned shared-memory mirror of the peer's receive ring (/dev/shm), then host to GPUWithout the mirror UCX stages over TCP at about 1 GB/s
On another node of the same NVLink domain (GB200 NVL)NVLink. The rings are allocated with a fabric handle so that the other node can map themUp to about 780 GB/s each way per GPU pair, against about 98 GB/s over the RDMA rails
On another host, no NVLinkTCP lanes: extra NIXL agents, each with its own connection and thread19.0 GB/s each way with 16 lanes between two ranks on a 200 Gb/s port, against 0.19 without lanes

Check the path in the engine log. On a GB200 NVL system each rank's engine log (where the logs are) should show every peer as
exchange: rank 0 (GPU ...) -> rank 5 (GPU ..., NVLink domain ...): NIXL over the NVLink fabric
For two ranks on different nodes, any other path means that pair uses the network. After connecting, a rank also times one large write to each NVLink peer and warns below 150 GB/s: UCX then did not take cuda_ipc.

Filters across ranks

Source: distributed-sirius.md, "Dynamic filters across ranks"

On one GPU, a join builds a filter from its build side and the other side's scan uses it to skip rows. After a hash exchange a rank's build holds only its share of the keys. A filter made from that share alone would drop rows that another rank's build matches. So in distributed mode every rank:

  1. builds a Bloom filter for each key, sized for its own build rows times the number of ranks;
  2. shares it with every rank (an all-gather);
  3. ORs the others' filters into its own, and only then publishes it to the scan.
  • If any rank's contribution is missing or does not fit (a rank sent none, sizes cannot be folded together, a rank missed the 2-minute wait), that key publishes no filter.
  • A join whose build side was broadcast already holds the whole build and publishes as on one GPU.
  • Filters are optional and the join decides. A missing filter costs speed, never correctness.
  • The other filter kinds of the single-GPU engine (IN-lists, zone maps) are not published in distributed mode.
  • In TPC-H Q12 at SF1000 the merged filter keeps 2.0% of orders before its exchange.

Failures and recovery

Source: distributed-gateway.md, "Failures and cancellation"; distributed-quickstart.md, "Recovery"

The design is fail-stop. A rank's exchange peers are fixed once it connects, so a rank process belongs to one set of ranks only. Anything that may leave the ranks out of step marks the cluster failed, and the next statement restarts every rank and replays the DDL log. The gateway's state is one of stopped, starting, ready, failed.

EventWhat happens
A query fails on one rank (an error)That rank tells its peers and the query is aborted on every rank. The next query runs normally.
A statement fails on every rankThe client gets the error with its root cause. The ranks keep serving.
A rank dies during a statementThe statement fails and the cluster is failed. The next statement restarts every rank and replays the DDL log.
A rank dies between statementsIts node starts it again (after 1 s, doubling up to 30 s), except after exit code 70, which a rank returns when a GDS read never came back. Before each statement the gateway probes every rank's port for 2 s; if a rank is down it restarts every rank, replays the DDL log, then runs the statement. The probe misses a rank that its node has already restarted.
The gateway restartsStart it again. Nodes register their ranks again within 10 s, and the first statement restarts every rank and replays the saved ddl.sql.
A statement runs too longAfter gateway.statement_timeout (3600 s by default) the gateway cancels it on every rank. The ranks keep serving if they stop in time.
A node is addedStart sirius-node on it. Every rank restarts at the next statement.
A node is removedIts ranks stay registered and every restart fails until they are dropped on the gateway's console: CALL sirius_gateway_drop_rank('<host>:<port>').

Statements that carry credentials (CREATE SECRET, a SET of a token or key) are not written to the saved ddl.sql. They are replayed when only the ranks restart, and lost when the gateway itself restarts: run them again then, or put them in sirius_gateway_rank_init.

2. Build

export CHECKOUT=<where the checkout goes> DATA=<the dataset> OUT=<a new run folder>   # absolute paths
git clone --branch experimental/distributed-sirius https://github.com/sirius-db/sirius.git "$CHECKOUT"
cd "$CHECKOUT" && git submodule update --init --depth=1 --jobs 5 \
  duckdb substrait cucascade sirius-duckdb/duckdb sirius-duckdb/extension-ci-tools
pixi run build-distributed            # once: Sirius (which includes NIXL) and the gateway

The build takes 35 to 40 minutes on 144 cores. On a cluster that Slurm schedules, run it as a Slurm job, not on a login node.

3. Start it: pick the case that fits

CaseCommands
One machine, the gateway starts the ranks
pixi run sirius-gateway 4      # 4 ranks, rank i on GPU i; clients on port 9494
pixi run sirius-client         # in another shell
Several machines
pixi run sirius-gateway                       # on one machine; it needs no GPU
pixi run sirius-node --check --data /data/tpch # on each GPU machine: build, GPUs, gateway, data
pixi run sirius-node                           # on each GPU machine: one rank per GPU
pixi run sirius-client                         # on any machine with the build and the shared $HOME
Slurm
sbatch -N2 scripts/sirius_slurm.sbatch         # from the checkout: gateway + 4 ranks per node
SIRIUS_CLUSTER=<job id> pixi run sirius-client
The gateway is named after the job id and serves until the job ends. --ntasks-per-node=2 uses 2 GPUs per node.
No gateway, one host, for development
pixi run scripts/distributed_run_sql.sh 4 /tmp/q12.sql
Runs a SQL file on 4 local GPUs, rank i on GPU i, and prints rank 0's output.

On a node that Slurm schedules, use Slurm for everything. Start processes with sbatch or srun, never over ssh. A stray process can make the next job fail and get the node drained. Run one job per node at a time.

4. Run SQL

CREATE VIEW lineitem AS FROM read_parquet('/data/tpch/lineitem/*.parquet');
SELECT l_shipmode, count(*) FROM lineitem GROUP BY ALL;   -- every rank runs it; rank 0 answers
FROM sirius_gateway_status();                             -- one row per rank, on the gateway
  • The first statement waits until gateway.min_ranks ranks have registered (for at most gateway.join_wait seconds), then starts them. Set min_ranks to the number of ranks you expect: a rank that registers after the first statement restarts every rank.
  • sirius_gateway_status() is the first thing to look at. It has one row per rank with its state, the cluster's state and error, and each rank's last_error. Its columns are rank, name, registered, pid, gpu, host, uri, state, cluster, error, last_error, last_query_id, running_query_id, queued.
  • For SQL with string literals pass a file (pixi run sirius-client < queries.sql) or call pixi run scripts/sirius_client.sh -c "...": a pixi task drops quotes inside its arguments.
  • Stop: Ctrl-D on the gateway's console, Ctrl-C on a node. With Slurm, scancel the job.

Run a benchmark

Source: distributed-experiments.md; without Slurm: distributed-experiments-no-slurm.md; on AWS: distributed-experiments-aws.md

Pick the document for your hardware, then follow it. This is the shape of every run.

There is a skill for this. In Claude Code, working in the checkout, /distributed-sirius-bench walks through these steps: it asks for the branch, dataset, scale factor, nodes and Sirius config, shows the config for approval, runs a smoke test, and then the benchmark. It runs TPC-H by default, or any dataset with a folder of .sql files. It is in .claude/skills/distributed-sirius-bench/, and its script scripts/bench.py also runs by hand.

  1. Check the nodes. Every node sees the build and the data (run the ls even on an idle node: it can have a stale mount). On GB200 NVL, nvidia-smi -q must show the fabric as State: Completed with the same CliqueId and ClusterUUID on every node, otherwise the exchange goes over the network.
  2. Write the config ($OUT/config.yaml). The experiments document gives the SF10000 config and the smaller one used for SF30000 and SF100000.
  3. Write run.sql: .timer on, one view per table over read_parquet, then for each query a marker statement and the query, twice in a row. End with FROM sirius_gateway_status();.
  4. Run it as one job with fresh ranks: start the gateway and ranks, send the SQL with sirius-client -bail, stop everything.
  5. Check the answers against an independent engine on the same data. The build's shell started without Sirius is a plain DuckDB on the CPU. scripts/compare_answers.py compares rows in any order and numbers within a tolerance. It accepts a tie at the LIMIT for Q3 and Q18 when given --ties 3:revenue,o_orderdate --ties 18:o_totalprice,o_orderdate.
  6. Check the engine logs: every peer on the expected path, no error, every rank up,ready in the final status.
  7. Report the commit, config and nodes, the dataset path and its row-group layout, cold and warm seconds per query, how each answer was checked, and what failed or was not run.
export PARTITION=<the GPU partition> NODES=<idle nodes, comma-separated>
export SIRIUS_CONFIG_FILE=$OUT/config.yaml SIRIUS_RANK_LOG_ROOT=$OUT/rank-logs
export SIRIUS_PRIORITY_DOWNSTREAM_FIRST=1            # the reference numbers use it
export SIRIUS_GATEWAY_STATEMENT_TIMEOUT=300
cd "$CHECKOUT" && git log -1 --oneline > "$OUT/env.txt"
job=$(sbatch --parsable -N"$(tr ',' '\n' <<< "$NODES" | wc -l)" -p "$PARTITION" -w "$NODES" \
  --time=40 -o "$OUT/job.out" scripts/sirius_slurm.sbatch)
until [ -s "$HOME/.sirius/gateways/$job/gateway.conf" ]; do
  squeue -j "$job" -h -o %T | grep -q . || { echo "job $job ended: see $OUT/job.out"; exit 1; }
  sleep 5
done
SIRIUS_CLUSTER=$job pixi run sirius-client -bail < "$OUT/run.sql" > "$OUT/client.txt" 2>&1
sleep 5                                              # the ranks flush their logs every 3 s
scancel "$job"

Rules that save a lost day:

  • Start narrow. Run the few queries the question is about, cold and warm. Run all 22 only for a number that will be quoted.
  • Keep the query order when comparing runs. "Cold" is a query's first run in the job and "warm" its second; the first query of a job is slower still.
  • Report the dataset layout. Row-group size changes scan times by 2× and more.
  • Q11's fraction must be 0.0001 / SF, or it returns no or too few rows.
  • Say which query parameters you ran. The query files in the branch (test/tpch_performance/tpch_queries/orig/) carry their own parameter values, for example Q1 with date '1995-08-19', not the TPC-H validation values (date '1998-09-02'). Answers and times are comparable only between runs with the same parameters. (Observed in this review, not stated in the documents.)
  • Ask before holding 4 or more nodes.

Read through GDS

Source: gds-runbook.md

By default each rank reads Parquet with io_uring. With scan_manager.backend: gds it reads through GPUDirect Storage (cuFile), which was about 2 to 2.5 times faster on one, two and four GB200 nodes reading from GPFS over RDMA (table). Its integration is not finished.

sirius:
  executor:
    scan_manager:
      backend: gds
      gds: { num_threads: 8, read_timeout_s: 30 }
export SIRIUS_GDS=1
export SIRIUS_GATEWAY_MIN_RANKS=4                                    # 4 on one node, 8 on two
export SIRIUS_RANK_LOG_ROOT=/path/off/the/data/filesystem/rank-logs  # so the logs survive a storage stall

  • Before the first run on a node: its /etc/cufile.json must list the storage NICs in rdma_dev_addr_list. Build the probe and run it on one exclusive node, and tell the storage admins first: a GDS run can leave a node's storage path degraded for everyone. The script names the partition of the cluster it was written on; pass your own with -p. 
    pixi run cmake --build --preset release --target gds_probe
FILE=/data/lineitem/part.0.parquet CHECKOUT=/path/to/sirius sbatch -w <node> /path/to/sirius/scripts/gds/gds_probe.sbatch
  • Check that reads went through GDS: each rank's engine log has [gds] cuFile ready: ... posix_fallback_allowed=false at start and, per query, [gds] query=N ... held_reads=0 verdict=gds.
  • When a storage NIC stops: the log shows [gds] held: N reads have not returned. Stop the session at the first such line, check the node before using it again, and do not route around the NIC. The runbook places the cause below Sirius, between one client NIC and the storage, so do not report the times of such a session.
  • Fewer read threads make the stall rarer and scans slower: Q9 at SF10000 took 11.3 s with 8 threads, 9.0 s with 16 and 8.2 s with 32.

Limits

Source: distributed-sirius.md, "Limits" and "The plan rewrite"; distributed-gateway.md, "Limits"

Queries that are refused

  • A DuckDB table (only Parquet through read_parquet is split), and a read_parquet of one remote URI.
  • ORDER BY on an expression; COUNT(DISTINCT) with grouping sets; grouped STDDEV_SAMP and ungrouped COUNT(DISTINCT) (their partial results are nested columns, which the wire does not carry).
  • A nested-loop join that emits unmatched build rows (RIGHT, OUTER, RIGHT_SEMI, RIGHT_ANTI); a delim join whose join keys are not its delim columns.
  • filename or file_index of a split table, and any operator the rewrite does not know.
  • PREPARE and EXECUTE through the gateway.

How it runs

  • One statement at a time for the whole gateway, across all clients.
  • One connection per process runs distributed queries.
  • Recovery restarts every rank. A lost peer or a failed transport is not repaired, and nothing reconnects.
  • Some buffers cannot spill: arrivals before their consumer is ready, and an ordered gather's batches. Sends block once a rank's queued sends exceed 1 GiB.
  • Sort samples and Bloom merges block a GPU worker thread until every rank's contribution arrives.
  • Ring memory grows with the number of ranks (18.3 GiB per GPU at 72 ranks with the defaults). More than 16 ranks has not been run: grow in steps and check the path lines at each step.
  • The gateway cannot kill a registered rank. A rank that hangs with its port open is found only by the statement timeout.
  • Nothing builds or tests gateway/ in CI, and the one-rank-per-process tests need several GPUs and run only on developer machines.

Where the documents and the code differ

A code review of the branch found the documents accurate on every port, default, setting name and script. These are the differences a newcomer could trip on:

  • A rank is not restarted after exit code 70 (a GDS read that never returned). The documents say a rank is started again "whenever it exits".
  • The path line does not show what UCX did. A same-host pair on plain NIXL or on shared-memory staging is not on the network, and a missing cuda_ipc shows as a warning about a slow write, not in the path line.
  • A statement timeout restarts the ranks only if a rank ignores the cancel for the grace period, is lost, or the exchange failed. Otherwise the ranks keep serving.
  • Two scripts carry one cluster's names: scripts/gds/gds_probe.sbatch (a partition) and scripts/distributed_test_nixl_pairs.sh (a path). Pass your own.
  • exchange.mnnvl: off gives plain rings, not fabric memory; one table in the gateway document reads otherwise.
