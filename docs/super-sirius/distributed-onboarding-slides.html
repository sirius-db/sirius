One SQL query across many GPUs

Sirius is a GPU SQL engine inside DuckDB. Distributed Sirius runs one query on several Sirius processes, one per GPU.

One endpoint

You connect a DuckDB shell to a gateway and type plain SQL. The gateway sends each statement to every GPU process.

Same SQL everywhere

Every process, called a rank, plans and runs the same statement on its own share of each table. Rank 0 returns the result.

Rows move between GPUs

Where a join, a group-by or a sort needs rows from other ranks, the plan has an exchange: GPU to GPU, over NVLink where the hardware has it.

Experimental. Through the gateway, CPU fallback is off: a query Sirius cannot run on the GPU fails instead of running on the CPU. Run so far with 4, 8 and 16 ranks on one, two and four GB200 nodes.

Eight words you will meet

The documents, the commands and the logs use them.

Rank
One Sirius process on one GPU. Numbered from 0; rank 0 returns every result.

Gateway
A CPU-only DuckDB that is the one SQL endpoint. It orders, numbers and sends statements, and restarts ranks.

Node
A GPU machine. sirius-node starts one rank per GPU on it.

Exchange
The plan operators that move rows between ranks: hash, range, broadcast or gather.

NIXL
The transfer library under the exchange. It writes one rank's GPU memory into another's.

Fail-stop
The failure rule: nothing is repaired in place. Every rank restarts.

DDL log
The statements (views, SET, INSERT …) the gateway keeps and runs again on restarted ranks.

GDS
GPUDirect Storage: an optional way to read Parquet straight into GPU memory.

One gateway, one rank per GPU

SQL and results go through the gateway. Rows go directly between ranks.

Gateway. Orders statements, numbers queries, sends them to every rank, returns rank 0's result. It does not plan or execute: the ranks do.

Rank. Plans the statement, scans its share, exchanges rows, runs every operator on its GPU.

The rule behind it all: every rank runs the same statements, in the same order, with the same query numbers.

Life of a statement

What the gateway does with every statement a client sends.

1

Route

Most statements go to every rank. Status calls stay on the gateway. A few are refused.

2

Wait for the turn

One statement runs at a time, in arrival order across all clients.

3

Number and send

The gateway sets the query number on every rank, then sends the statement to all in parallel.

4

Return and record

Rank 0's result goes back. Statements that change state are added to the DDL log.

  • Refused through the gateway: PREPARE and EXECUTE, and SET of the exchange settings.
  • One copy per rank: CREATE TABLE and INSERT give every rank its own copy of the rows. Use views over read_parquet for data that must be split.
  • Shared sessions: one client's SET reaches every client's later statements.

Distribution is a plan rewrite

Each rank builds the single-GPU plan, then distribute_plan() inserts exchanges where that plan already partitions.

ExchangeWhere each row goesUsed for
hashTo the rank chosen by a hash of the keyJoins, on the join key; grouped aggregation, on the group key
broadcastTo every rankA join input that is small against the other one (at most 1 GiB); nested-loop joins
rangeTo the rank that owns the key's rangeA global ORDER BY, with boundaries from a sample all ranks share
gatherTo rank 0Ungrouped aggregates, top-N, and the final result
  • Scans, filters and projections stay on the rank where their input is.
  • Before running, the ranks compare a hash of their plan's shape. If any differs, the query fails on every rank.
  • A plan shape the rewrite does not know is refused, because running it per rank would return a wrong answer.

Every rank reads its own share

No rank reads a table for the others, and no row group is read twice.

  • Local files are cut by bytes, as in the picture. A table of one row group lands on one rank.
  • Remote files (S3) are dealt out whole, file by file, so a remote table needs at least as many files as ranks.
  • Every rank binds every file, so every rank plans from the same statistics and reaches the same plan.
  • Only Parquet through read_parquet is split. A DuckDB table is refused.
  • Row-group size matters: it changes scan times by 2× and more, so report it with every number.

Moving rows: rings, credits and four paths

A sender can only fill memory the receiver has set aside for it, so a slow receiver slows its senders.

  • Rings. Each rank has a send ring and a receive ring of 16 MiB frames. They are the only memory registered for transfers.
  • Credits. The receive ring is split among the peers. A sender gets a frame back once the receiver has copied it out.
  • Landing. A batch lands on the GPU if there is room, else in host memory, else it waits in the ring and the sender stops.
  • Cost. Ring memory per GPU: 2.25 GiB with 8 ranks, 4.25 GiB with 16.
The peer isPathMeasured
On this hostDirect GPU to GPU (cuda_ipc)
On this host, GPUs without peer accessThrough a shared-memory mirror on the host
On another node of the NVLink domainNVLink between nodesup to 780 GB/s per GPU pair
On another host, no NVLinkTCP lanes19 GB/s on one 200 Gb/s port

Each rank writes its path to every peer in the engine log. On GB200 NVL every line should end in NIXL over the NVLink fabric.

Filters must include every rank

A join builds a filter that lets the other table's scan skip rows. Built from one rank's share alone, it would drop rows another rank needs.

1

Build

Each rank builds a Bloom filter per join key, sized for its own rows times the number of ranks.

2

Share

Every rank sends its filter to every other rank and waits for theirs.

3

Merge, then publish

Each rank ORs the others into its own. Only the merged filter reaches the scan.

  • A missing filter costs speed, never correctness. If any rank's part is missing or does not fit, that key publishes no filter and the join does the work.
  • A broadcast build side already holds every key, so it publishes as on one GPU.
  • In TPC-H Q12 at SF1000 the merged filter keeps 2.0% of orders before its exchange.

When something fails, every rank restarts

A rank's peers are fixed once it connects, so nothing is repaired in place. The gateway restarts the ranks and replays the DDL log.

EventWhat happens
A query fails with an errorIt is aborted on every rank. The ranks keep serving and the next query runs normally.
A rank dies during a statementThe statement fails. The next statement restarts every rank and replays the DDL log.
A rank dies between statementsIts node starts it again. The gateway probes each rank before a statement and restarts all if one is still down.
A statement runs too longThe gateway cancels it on every rank after statement_timeout (3600 s by default).
The gateway restartsNodes register again within 10 s. The first statement restarts the ranks and replays the saved log.

Lost when the gateway itself restarts: statements that carry credentials, such as CREATE SECRET. Run them again then.

Start a cluster in three commands

Build, then start a gateway, a node per GPU machine, and a client.

You need

  • The same checkout and the same data path on every machine.
  • A shared $HOME: nodes and clients find the gateway through a file there.
  • Free ports: 9494 for the gateway; 9500 + i and 27000 + i for the rank on GPU i.
  • Pixi 0.78 or newer, and 35 to 40 minutes for the build on 144 cores.

Under Slurm, use Slurm for everything. Never start a process on a scheduled node over ssh.

Several machines

pixi run build-distributed   # once on a shared checkout
pixi run sirius-gateway      # needs no GPU
pixi run sirius-node --check # on each GPU machine
pixi run sirius-node         # one rank per GPU
pixi run sirius-client       # a DuckDB shell

One machine

pixi run sirius-gateway 4    # starts 4 ranks itself
pixi run sirius-client

Slurm

sbatch -N2 scripts/sirius_slurm.sbatch
SIRIUS_CLUSTER=<job id> pixi run sirius-client

Run SQL and look at the cluster

The client is a DuckDB shell. Tables are views over Parquet files.

CREATE VIEW lineitem AS FROM read_parquet('/data/tpch/lineitem/*.parquet');
SELECT l_shipmode, count(*) FROM lineitem GROUP BY ALL;   -- every rank runs it; rank 0 answers
FROM sirius_gateway_status();                             -- one row per rank, on the gateway
  • The first statement waits until min_ranks ranks have registered, then starts them. Set it to the number of ranks you expect.
  • sirius_gateway_status() shows each rank's state, the cluster's state and the last error. Look here first.
  • Logs: each rank's output is in /tmp/sirius_node_<user>_<cluster>/ on its node. The engine log is in <checkout>/log/, or under $SIRIUS_RANK_LOG_ROOT.
  • Gateway state: ~/.sirius/gateways/<cluster>/ holds its address, token and DDL log.

Configure with one file

sirius.yaml: the distributed section is for the launch scripts, the rest for the engine on each rank. Every key is optional.

sirius:
  distributed:
    cluster: tpch
    gateway:
      min_ranks: 8
      statement_timeout: 3600
    node:
      gpus: all
    exchange:
      mnnvl: auto
  memory:
    host: { capacity_bytes: 200Gi }
KeyWhat
gateway.min_ranksRanks the first statement waits for. Default 1
statement_timeoutSeconds before a statement is cancelled
node.gpusall, a list, or slurm
exchange.mnnvlrequire fails instead of using the network
host.capacity_bytesHost memory per rank. 200Gi works on GB200; 250Gi got ranks killed

Found at $SIRIUS_CONFIG_FILE, then ./sirius.yaml, then ~/.sirius/sirius.yaml. Each distributed key also has an environment variable, which wins.

Your first benchmark

One run is one job with fresh ranks. A number counts only with a checked answer.

1

Check the nodes

Every node sees the build and the data. On GB200 NVL: fabric Completed, same clique and cluster id everywhere.

2

Config and run.sql

Views, then each query twice in a row after a marker (cold, then warm). End with the gateway status.

3

Run

Start gateway and ranks, send the SQL with sirius-client -bail, stop everything.

4

Check the answers

Against plain DuckDB on the same data, with scripts/compare_answers.py.

5

Check the logs

Every peer on the expected path, no error, every rank up,ready.

6

Report

Commit, config, nodes, dataset layout, cold and warm seconds, what failed.

In Claude Code, /distributed-sirius-bench walks through these steps, with a smoke test before the benchmark. Start narrow: a few queries before all 22.

Optional: read through GDS

GPUDirect Storage moves Parquet bytes from storage straight into GPU memory. Its integration is not finished.

Config: two lines

sirius:
  executor:
    scan_manager:
      backend: gds
      gds: { num_threads: 8, read_timeout_s: 30 }

Environment

export SIRIUS_GDS=1
export UCX_MODULES=^ib,rdmacm   # UCX off the storage NICs
export UCX_NET_DEVICES=<iface>  # the ranks' interface

About 2 to 2.5 times faster than io_uring, the default, on one, two and four GB200 nodes.

  • Before the first run on a node: build and run the probe (gds_probe, in the runbook), and tell the storage admins first.
  • Check each query: the engine log says held_reads=0 verdict=gds.
  • If the log says [gds] held: a storage NIC stopped delivering. Stop the session at the first such line and check the node before using it again.
  • Do not report times from a session with held reads. The runbook places the cause below Sirius.

Limits to know

What is refused today, and how the system behaves under load.

Queries that are refused

  • DuckDB tables: only Parquet through read_parquet is split.
  • ORDER BY on an expression.
  • COUNT(DISTINCT) with grouping sets, or without a group-by; grouped STDDEV_SAMP.
  • Nested-loop joins that emit unmatched build rows.
  • PREPARE and EXECUTE through the gateway.

How it runs

  • One statement at a time for the whole gateway.
  • Recovery restarts every rank; nothing reconnects.
  • Some exchange buffers cannot spill to host or disk.
  • Ring memory grows with the number of ranks. More than 16 ranks has not been run.
  • Nothing builds or tests the gateway in CI.
Source: distributed-sirius.md, "Limits" · distributed-gateway.md, "Limits" · distributed-experiments.md, "Past 16 ranks"19 / 22

When it does not work

Look at FROM sirius_gateway_status(); first, then at the rank's rank.log.

SymptomCause and fix
the gateway starts once N ranks are registeredToo few ranks joined in time. A rank that dies at start, usually from the config, shows as rank exited.
rank N failed its session setupThe ranks could not connect to each other. Check the exchange ports and the UCX settings.
Endpoint timeout in a rank's logUCX picked a port the ranks cannot connect through. Keep the default UCX settings.
A peer is not on NIXL over the NVLink fabricNo IMEX channel between the nodes, or different NVLink domains.
Ranks killed in the middle of a queryThe host memory tier is too large. Lower it (200Gi works on GB200).
A job fails in seconds with no output$HOME at its quota, or a stale mount on the node.
