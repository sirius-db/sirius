## Changes in this commit

### Correctness fixes
1. **`src/pipeline/gpu_pipeline_task.cpp`** — Restored `stream.synchronize()` after `op.execute()`.
   Originally removed in `a272bba` for timing-overhead reasons, but the sync is required
   for RMM pool accounting. Without it, memory bookkeeping drifts — invisible on GH200
   (96GB headroom) but causes OOM deadlocks on 24GB GPUs after ~9 queries in a session.

2. **`src/op/scan/direct_block_scan.cpp`** — Rewrote mmap bypass with:
   - `std::call_once` for thread-safe block-layout discovery (was racy globals)
   - Correct block offset computation so bulk H2D stays within block boundaries
   - `MADV_POPULATE_READ` to prefault pages (prevents CUDA staging-thread segfault on PCIe)
   - Runtime validation against DuckDB's `GetDirectBlockPointer` to confirm offsets match

### Performance
3. **`src/op/scan/gpu_native_scan_task.cpp`** — Three changes:
   - **H2D copy merging**: blocks are sorted by `block_id` and consecutive IDs (whose host
     pointers are also contiguous in the mmap) are merged into a single `cudaMemcpyAsync`,
     reducing thousands of 256KB copies to a few dozen multi-MB copies.
   - **RMM-managed staging**: staging buffer now allocated via `rmm::device_buffer(mr)`
     instead of raw `cudaMallocAsync`, so cuCascade tracks it for reservations.
   - **Self-continuation with bounded batches** (`MAX_BATCHES_PER_TASK=4`): each task
     processes up to 4 batches then schedules a replacement, restoring pipeline
     interleaving (the parallel-scan commit `685682c` had each task accumulate ALL
     batches, which caused ClickBench warm OOM).

## Known issue: cold performance
`MADV_POPULATE_READ` prefaults the entire database file on first mmap, adding 16-19s
per cold query (depends on file size). This is necessary on PCIe systems (CUDA's
staging thread segfaults on lazy page faults) but wasteful on GH200 (unified memory
via ATS handles page faults transparently).

**Projected improvement if DuckDB `GetDirectBlockPointer()` is used instead**
(i.e., replace the raw mmap with the DuckDB-managed mmap from the 5 patches):
- DuckDB does not prefault — pages fault in lazily on demand
- Cold query only pays I/O for blocks actually accessed
- TPC-H SF100 cold: ~16s/query → ~4-5s/query (**3-4x faster**)
- ClickBench 100shard cold: ~18s/query → ~1-2s/query (**10-20x faster**)

To enable: change `direct_block_scan.cpp` to call `block_mgr->GetDirectBlockPointer()`
instead of raw mmap. The DuckDB patches (8b2abc7) already provide this API. On PCIe,
add a runtime gate on `cudaDeviceProp::pageableMemoryAccessUsesHostPageTables` so
PCIe systems still get the prefault path.

## Cold-run 3-variant comparison (GH200, per-query avg)

| Variant | Mechanism | Cold TPC-H | Cold CB | Warm TPC-H | Warm CB |
|---------|-----------|-----------:|--------:|-----------:|--------:|
| A | mmap + MADV_POPULATE_READ (PCIe path) | 16.4s | 19.7s | 5.35s | 5.05s |
| B | mmap + lazy faults (GH200 path, **default**) | 2.4s | ~3.3s | 5.41s | 4.99s |
| C | `BufferManager::Pin()` (no mmap) | 1.1s | 1.0s | 6.55s | 5.14s |

- **Variant B vs A**: 6-7x faster cold, no warm change. Ships via `SIRIUS_MMAP_PREFAULT`
  auto-detection (`cudaDeviceProp::pageableMemoryAccessUsesHostPageTables`).
- **Variant C vs A**: 15-20x faster cold, 20% slower warm TPC-H (Pin overhead).
- **Projected Variant D** (`BlockManager::GetDirectBlockPointer()` API, not upstreamed yet):
  best-of-both: Variant C cold speed + Variant B warm speed. Requires upstreaming
  the 5-line `GetDirectBlockPointer` patch to DuckDB.

## Runtime controls added

- `SIRIUS_MMAP_PREFAULT=1` — force prefault (PCIe path)
- `SIRIUS_MMAP_PREFAULT=0` — force lazy faults (GH200 path)
- unset — auto-detect from `cudaDevAttrPageableMemoryAccessUsesHostPageTables`
- `SIRIUS_DISABLE_MMAP=1` — skip mmap entirely, use `BufferManager::Pin()`
