Q10 profile counterexamples follow roadmap D3 and apply equally to empty and nonempty tables. Stored data-evolution or realtime mode cannot become an M1 admission positive merely by overriding the effective option to false. An ORC declaration plus a Parquet override likewise requires independent frozen manifest/data-file and historical-mode evidence before any separately approved profile can qualify. Unknown physical/history facts stay unqualified or explicitly refused; an INSERT-only row-kind observation, empty output or constructor entry does not establish append-only/M1 eligibility. Use benign options with no mode/format conversion, or a separate pure merge test, to verify parameter precedence. A native-entry marker establishes only that execution reached the wrapped static call boundary; it proves neither successful data reading/GPU import nor planning/reading allocation coverage. Record profile qualification, guarded entry and resource refusal as distinct properties; no configuration-only positive closes Q10 or Q01.

Q12 counterexamples implement the existing real-provider/ABI requirement using the coordinator's roadmap D5; they do not introduce a new loader protocol or widen support. On the final immutable P1 tuple, retain a fresh-process record for each supported LOAD order. First establish that a compatible loaded provider succeeds. Then enable `allow_extensions_metadata_mismatch`, LOAD a deliberately incompatible-footer artifact, reset the flag to false, and require refusal before R2 independent C++ initialization or publication of trusted function references. The artifact must be safely loadable enough to reach this validation boundary; an earlier loader crash/error is setup evidence, not proof that the R2 guard rejected it.

Also challenge invalid magic/footer and a loaded-image/current-path disagreement, including replacement/removal of the path after LOAD. Such replacement is a refusal/qualification-boundary probe, not promised hot-replacement support. Capture exact host/provider bytes and ABI/platform, actual mapped module origin, file identity and the path-freeze mechanism. Re-reading a compatible current file or reporting its hash does not qualify a different already-loaded image. If association cannot be demonstrated, decline. Exercise both LOAD orders and provider/plan/module lifetimes; sanitize error evidence. R2 must call `AppearsValid()` before reading `abi_type` and reuse the pinned DuckDB footer compatibility semantics where sufficient; E2E independently checks the final behavior. Implementation/source review alone leaves Q12 NOT RUN, and any reduction of the existing guarantee goes to Aaron.

For the bounded Linux direct-path implementation considered in D5, test the same-open-fd footer check, initializer mapping device/inode association and before/after `fstat` change detection against a frozen genuine positive. These checks do not establish historical same-inode contents or prevent later writes; retain actual artifact hashes and an enforced freeze from before LOAD through use. A null provider, missing `/proc` evidence or an earlier LOAD failure alone cannot close the mismatch/reset or original-path-replacement guards. Preserve evidence that each negative reached its intended guard, with targeted guard-removal controls where needed. A source-only scope audit establishes no runtime, LOAD-order or lifecycle PASS and does not require a general loader attestation framework.


Prerequisites: actual compatible Sirius/provider extensions loaded; owner-supplied experimental opt-in if required; both planning and runtime fallback disabled under the pinned implementation; source profile admitted before native planning. Do not guess new settings. Assert exact types `BIGINT, DECIMAL(12,2)` and multiset `(1,10.00)` twice, `(2,NULL)`, `(3,5.00)`. Preserve existing fixture inventory and snapshot/schema hashes. After the tested statement execute a same-session liveness query.

The same process/query evidence must identify Paimon retained snapshot/schema/source and executed GPU scan/operator. A `gpu_execution=true` result, successful EXPLAIN or unrelated GPU counter is insufficient. Extract from existing registry/profile facilities before proposing new production observability. If those facilities cannot associate execution with the Paimon scan, Q01 stays NOT RUN and the gap goes to adapter owner.

Run a forced-CPU counterpart with `SET gpu_execution=false` and identical expected rows. Its data comparison should succeed while the GPU acceptance checker must reject it with an explicit route-evidence failure. Missing/wrong-query/stale source evidence, wrong rows/types, successful-looking partial logs plus nonzero exit, signal and timeout must also be rejected through the real E2E entrypoint. Checker regression success is distinct from intentional qualification rejection. An isolated reviewer must challenge this checker at its final immutable revision before it can certify GPU PASS.
