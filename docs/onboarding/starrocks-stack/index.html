StarRocks plans the distributed query. Rust translates and coordinates its fragments. DuckDB binds each fragment, and Sirius executes it through GPU pipelines. The exchange staging arena connects the compute nodes.

Two entry paths

Embedded SQL and distributed fragments

In the DuckDB extension, ordinary SQL reaches Sirius through the query interceptor. In the StarRocks path, the FE sends a planned fragment over RPC; the CN translates that plan into Substrait and builds a Fragment. Both meet at the Sirius physical planner and task scheduler.

The distributed translator does not parse SQL, and DuckDB does not replace the FE's distributed planner. These are different planning stages.

A critical distinction

Streaming APIs; a buffered exchange

The C++ primitives expose push, pull, sender-aware EOF and failure propagation. They deliberately have no channel-level backpressure. In this branch, a distributed receiver waits for its expected inputs to finish before running. Most sender output is parked before transport drains it. The existence of streaming primitives does not make this a fully pipelined distributed shuffle.

What is already landed?

The streaming foundation is in dev. The 19 listed PRs are only integrated into this benchmark branch. A local merge commit is not an upstream landing.

02 / Focus area

Staging is a transport window.
The pool holds the backlog.

The arena gives NIXL a stable device address to register. A lease gives one frame temporary ownership of a region. Copying an arrival into pool memory releases that lease, but does not remove the query's accumulated working set.

A separate allocation

exchange_staging_arena allocates one device region using cudaMalloc (or an opt-in fabric allocation). It sits outside the engine's RMM pool. A mutex-protected, coalescing free list supplies aligned leases; normal operation does not resize the registered region.

#1693 adds this allocator. Commit b7452f67 exposes leases and packed batches over FFI. The CN/NIXL commits turn those building blocks into the remote path.

Four budgets, four meanings

  • Arena: temporary packed frames and transport registration.
  • GPU pool: operators, parked output and copied inbound tables.
  • Host: a separately configured cuCascade tier; the raw inbound copy is not automatically a spillable reservation.
  • Disk: a configured downgrade target, reached through full engine YAML. It does not expand the arena.

The life of one remote frame

Step through the ownership handoff. Blocks show where bytes are live.

Ownership rules and required fixes

  1. Keep each source lease alive until NIXL reports transfer completion.
  2. Claim the frame sequence before touching its receiver lease. A retry may refer to a lease already released.
  3. Complete the deep copy before freeing receiver staging bytes.
  4. Retain the ticket until the fragment takes it, or query retirement drops it.
  5. Needs a fix: close ingress and quiesce active copies before destroying the allocator and transport.

Pressure at different layers

batch_stream has no queue-depth credit mechanism. Repository-backed batches rely on normal downgrade machinery. An available arena lease and enough GPU pool memory are separate conditions; a receiver can keep granting fresh arena space after each copy while its raw inbound backlog grows.

The current CN waits for EOS from all expected senders. That barrier lets the whole shuffled input accumulate before downstream work can consume it. Increasing the arena alone cannot fix this working-set limit.

Review gate: receive admission. The arena checks free staging space; InboundStore::stage then allocates through the default GPU resource. This arrival path has no receive-credit budget or cuCascade reservation. The same-box checklist records OOM failures in six SF500 queries. Future receive credits and reservation-bound spilling need their own PRs and correctness tests.

Size the MIG memory envelope

Illustrative arithmetic from the checked-in box notes: 48,512 MiB visible per MIG instance. Remaining bytes must cover CUDA contexts and other allocations; they are not guaranteed usable capacity.

07 / A practical reading path

Start with the boundaries.
Then follow the ownership.

A new teammate should be able to explain who plans, who owns each buffer, who signals completion, and which PR introduces each contract before changing the execution path.

First 30 minutes

  1. Follow the six-boundary architecture diagram.
  2. Compare an embedded DuckDB query with a StarRocks fragment request.
  3. Step through a remote frame from parked output to receiver pool.
  4. Identify the three statuses: landed, existing draft, integration-only.
  5. Open the PR atlas for your component.

The next 90 minutes

  1. Trace one exchange stream ID across translator, FFI and source operator.
  2. Follow a ranged parquet scan through Substrait to row-group ownership.
  3. Trace two-phase AVG: two wire states, final division and descriptor order.
  4. Follow cancellation through rendezvous, tickets and parked output.
  5. Read one review finding and the test needed to establish its fix.

Explain these contracts to a teammate

Translator → DuckDB

A StarRocks slot ID has a type and position. Substrait expresses the relational plan and stream/table reads. DuckDB binds those reads in a transaction, optimizes locally, and Sirius converts the logical plan to GPU operators. Two-phase aggregation must carry the intermediate state type across both fragments.

Teach-back: Why does emitting GROUP BY keys in expression order instead of descriptor order corrupt downstream values?

Scan → cache → pipeline

A byte split owns row groups by their start offset in a half-open range. A ranged scan bypasses whole-file pin-cache serving. File-subset cache hits require per-chunk provenance; matching the table name alone is insufficient.

Teach-back: Why can a pinned table be safe for a file subset yet unsafe for an arbitrary byte range?

Code and reading map

Vocabulary

FE
StarRocks frontend: SQL planning, fragment scheduling, cluster membership and result coordination.
CN
The Rust Sirius compute-node service: receives RPCs, translates plans, manages fragments and exchanges.
Fragment
One executable part of a distributed plan, with declared input streams and one output boundary.
Substrait
The serialized relational-plan boundary between the Rust translator and DuckDB lowering.
Wire order
The column positions and types the sender emits and receiver expects, as defined by descriptors.
Parked output
Completed sender data retained until downstream consumers have received it.
Lease
A temporary aligned allocation inside the stable staging arena, identified by a process-local token.
Inbound ticket
An opaque ID for a deep-copied received batch waiting to be taken by the receiver fragment.
EOS / EOF
End of a sender's stream. A receiver becomes dispatchable only after all required inputs are complete.
RMM / cuCascade
GPU allocation resources and Sirius's reservation/tier machinery. Allocating from the default GPU pool alone does not establish a spillable repository reservation.
NIXL / UCX
The data-transfer layer and transport backend. RPC carries coordination and metadata; the bulk data write is a separate operation.
MIG
Partitioned GPU instances selected by CUDA visibility. This benchmark assigns a CN to each instance and budgets pool plus arena per instance.
