The Big Picture

You load one extension. Your SQL doesn't change. Supported queries silently run on the GPU. Where exactly does the swap happen?

A simultaneous interpreter in the booth

DuckDB is the speaker at the podium; Sirius sits in the interpreter's booth, translating the talk into GPU execution live, mid-sentence. When it hits an idiom it can't translate, it hands the mic back — and the audience never notices the switch.

🗣️
DuckDB speaks

Parses, binds, optimizes — business as usual. It has no idea it's being interpreted.

🎧
Sirius translates live

In the booth, it converts DuckDB's optimized plan into its own GPU operators, mid-sentence.

🎤
The mic hands back silently

Untranslatable idiom? The CPU takes over — correct results, and nobody hears the switch.

Concretely: Sirius is a GPU-native SQL engine shipped as a DuckDB extension. Compute runs on cuDF and RMM, with memory and data-movement primitives from NVIDIA cuCascade.

🧠
The whole engine in one sentence

Sirius intercepts a SQL query, converts DuckDB's plan into its own physical operators, groups them into pipelines, and a task creator turns 'operator + available input' into GPU tasks that a scheduler runs. Data flows between operators through repositories (not function returns), and ports tell each operator where its input lives.

The swap happens in exactly one place

Sirius hooks DuckDB through an optimizer extension. The hook itself decides nothing about GPU support — it just captures the plan for a later verdict.

1
The hook copies the optimized logical plan

DuckDB's optimizer finishes; Sirius copies the plan and stashes it in its per-connection state. No GPU judgment yet.

2
OnFinalizePrepare runs create_plan()

sirius_physical_plan_generator::create_plan() walks the copy, building Sirius physical operators — or throwing at the first unsupported one.

3
Success wraps the plan; a throw falls back

Success: the plan is wrapped in PhysicalSiriusExecution and swapped in. Throw: DuckDB's own CPU plan runs, silently.

src/transparent/sirius_optimizer_extension.cpp 

  // Copy the optimized plan. OnFinalizePrepare will attempt create_plan() on this
  // copy — that's the single source of truth for GPU support. If the plan contains
  // unsupported operators, create_plan() throws and we fall back to CPU.
  try {
    auto plan_copy = plan->Copy(context);
    ctx->set_captured_logical_plan(std::move(plan_copy));
  } catch (duckdb::NotImplementedException&) {
    // Plan not serializable — skip GPU.
  } catch (std::exception& e) {
    spdlog::debug("Transparent execution: failed to copy logical plan: {}", e.what());
  }
Plain English

The comment states the contract: create_plan() on this copy is the single source of truth for GPU support — no other code path gets a vote.

And the failure mode is spelled out up front: an unsupported operator means a throw, and the throw is the fallback signal.

Copy the plan so Sirius owns its own version — DuckDB keeps the original, untouched, ready for CPU execution.

Stash the copy in Sirius's per-connection state; OnFinalizePrepare will pick it up once preparation finalizes.

Some plans can't even be copied (not serializable). No drama: quietly skip GPU — the user's query still runs on CPU.

Anything else unexpected gets logged at debug level. The user never sees an error, just a CPU-executed query.

Either way the query proceeds. GPU is an optimization, never a requirement.

💡
Key insight: GPU support is a plan-level decision, made once

create_plan() either succeeds (plan wrapped and swapped) or throws (silent CPU fallback). So when a query unexpectedly runs on CPU — or you wonder "will my new operator ever be used?" — there is exactly one gate to check.

Life of a Query

One query traced end to end with the real functions — from SQL string to fulfilled future.

One query, two pipelines

Let’s trace one query, end to end, with the real functions — every name below is grep-able in the tree:

the query 
SELECT count(*) FROM orders WHERE amount > 100;

DuckDB parses it; Sirius converts the plan and cuts it at the COUNT, because an aggregate is a pipeline breaker — it must see all input before emitting anything. The result is two pipelines:

the split plan 
Pipeline A (streaming): SCAN(orders) → FILTER(amount>100) → [sink: partial COUNT state]
Pipeline B (terminal): COUNT finalize → RESULT_COLLECTOR

Mental model: a kanban factory line. Stations never push work downstream — a station pulls when its input bin has parts, and the andon board only updates when a worker turns in a job card. Hold on to that second rule; it becomes a bug story in Module 7.

Not all bins are equal. Each input port carries a barrier type that decides when the consumer may start:

PIPELINE A’s internal hops: SCAN → FILTER → sink stream batch by batch.
FULL B’s input port: COUNT finalize is blocked until Pipeline A completely finishes.
PARTIAL Not used in this query — the in-between type for hand-offs like concat.

Kickoff: one line of code starts everything

DuckDB’s execution thread calls exactly one Sirius entry point, then goes to sleep. Everything else in this module happens on Sirius worker threads while that thread blocks on the returned future.

The heart: get_next_task_hint()

The task creator never guesses what to run next. Before building any task it asks the operator for a hint — and there are exactly three possible answers.

⚡

READY{this}

“Build me a task.” Every input port has data, or I am a source with splits left. The creator wraps the pipeline in a gpu_pipeline_task.

🔁

WAITING_FOR_INPUT_DATA{producer}

“Go ask upstream.” A FULL-barrier port has an unfinished producer, and the hint carries a pointer to it. The creator recurses — the hint chain.

🏁

std::nullopt

“I’m done forever.” No task will ever be needed here again — a scan answers this once its last split is gone. The creator stops asking.

src/include/op/sirius_physical_operator.hpp:49 
enum class TaskCreationHint { WAITING_FOR_INPUT_DATA, READY };

enum class MemoryBarrierType { PIPELINE, PARTIAL, FULL };

struct task_creation_hint {
  TaskCreationHint hint{TaskCreationHint::WAITING_FOR_INPUT_DATA};
  sirius_physical_operator* producer{nullptr};
};

The base implementation walks the input ports looking for a FULL barrier whose producer pipeline hasn’t finished. Found one? Answer WAITING, pointing at that pipeline’s source. Every port satisfied? The function falls through to READY.

src/op/sirius_physical_operator.cpp:275 
std::optional<task_creation_hint> sirius_physical_operator::get_next_task_hint()
{
  if (ports.empty()) { return std::nullopt; }

  // look at the input ports and see if there are any unfinished hard barriers
  auto unfinished_barrier = std::find_if(_ports_list.begin(), _ports_list.end(), [](const auto& p) {
    return p->type == MemoryBarrierType::FULL && p->src_pipeline &&
           !p->src_pipeline->is_pipeline_finished();
  });

  if (unfinished_barrier != _ports_list.end()) {
    auto* producer = &((*unfinished_barrier)->src_pipeline->get_operators()[0].get());
    return task_creation_hint{TaskCreationHint::WAITING_FOR_INPUT_DATA, producer};
  }

A task runs the line

A READY hint becomes a gpu_pipeline_task: one split pushed through every station of one pipeline. Four moves, always in this order:

1
Reserve GPU memory

Admission control: the memory this batch needs is reserved before anything executes. Module 5 lives entirely inside this step.

2
prepare_for_processing()

Lock the input batches and colocate them into one memory space, so the kernels see resident, same-device inputs.

3
execute() each operator

The batch is pulled through the station chain on the GPU: scan output through FILTER, results into the partial-COUNT sink.

4
publish_output() → terminal sink()

Surviving rows are pushed into the repository of the next port — as handles, never copies.

🔗
Data moves by handle, not copy

publish_output() deposits references to GPU-resident batches; nothing is serialized and nothing returns up the call stack. What a batch actually is — that’s Module 4.

The Data Plane

In Sirius, no operator ever returns data to its caller. Ever. Here's why that one decision buys spilling, backpressure, and multi-GPU almost for free.

A named dock, not a return value

Think freight docks: a producer pipeline drops pallets — batches — at a named dock, and the dock's rules say when the consumer may start unloading. In Sirius the dock is a port — and it never holds goods itself, it points at the repository where they live.

Here is the entire replacement for "function returns data" — the base-class sink(), about seven lines. When our running count(*) query's filter finishes a batch of partial counts, this is how they leave: each handle is filed at every downstream dock, and the caller never sees a thing.

Three unloading rules

The barrier type is pipeline semantics compressed into one enum. Same repository machinery underneath — only the release rule changes.

🚚

PIPELINE — roll-through dock

Pallets release one at a time, the moment they land. This is how a filter chain streams: each batch flows straight to the next operator in the same pipeline.

🌊

PARTIAL — wave release

Goods release in waves while the shipment is still arriving. CONCAT-after-PARTITION consumes partitions incrementally, across a pipeline boundary.

🏛️

FULL — bonded warehouse

Sealed until the entire shipment clears customs. A hash-join's build side stays invisible until its producing pipeline completely finishes.

Pallets have manifests: the batch lifecycle

A data_batch is the manifest, not the pallet — and you never touch its buffers directly, only through RAII locks: many read_only readers XOR one mutable holder. idle means nobody holds it.

N

read_only
Any number of concurrent readers. Converters queue behind all of them.

⇄
0

idle
Nobody holds it. The only state that can be locked either way — and the only state that can be spilled.

⇄
1

mutable_locked
Exactly one exclusive holder. Required to mutate — or convert to another memory space.

💡
Spillable = idle + in a registered repository

The downgrade executor never asks operators for memory back — it walks repositories and takes idle batches. Both conditions are load-bearing: a batch it can't find or can't lock might as well not exist. That is why repositories being first-class, inspectable objects is the whole game — it's what makes spilling possible at all.

⚠️
How you cause an OOM

Park batches in a private queue, or sit on locks "for later" — either way they're invisible to the downgrade executor and the query dies under pressure instead of spilling. Module 7's streaming design exists to dodge exactly this: ownership stays in repositories, and only {batch_id, size} handles travel through channels.

History: this tri-class lock design replaced a 4-state FSM (cuCascade #117, adopted in Sirius #689) — lock-discipline races stopped being runtime bugs and became compile errors.

Memory & Multi-GPU

GPU memory is the scarcest thing in this engine. Sirius’s answer: nothing runs without a reservation, and pressure triggers relocation — not a crash.

Book before you travel

Think of a hotel with an annex and a storage depot: you don’t get a room by walking in, you book before travel. In Sirius, every memory allocation lives on a three-rung tier ladder, and no task touches tier 0 without a booking.

0

GPU device memory
the main building — fast, tiny, contested

→
1

→
2

All three tiers are managed by sirius_memory_reservation_manager (cuCascade). Before the GPU executor’s manager thread dispatches a task, it makes a reservation sized from the pipeline’s memory history.

1
Reserve

The manager thread books a budget on a specific memory space, sized from what this pipeline actually used before.

2
Run inside the budget

The task dispatches; its operators allocate within the reservation — never around it.

3
Release at task end

Check-out is automatic. The freed budget is what lets the next blocked task dispatch.

no reservation → the task won’t run. There is no walk-in path to GPU memory.

What if a task allocates beyond its reservation anyway? It throws oom_reschedule_exception — the moment a task gives up gracefully, packaging its partial state and the operator index to resume from.

The graceful surrender: not a crash, but a thrown value that is the reschedule plan.

Read the comment out loud: at SF100, 10 retries × 5 ms — 50 ms of patience — was far too short.

Now it’s 100 retries × 50 ms (~5 s): enough for probe tasks to outlast a contention window, while still bailing on truly wedged queries.

The budget itself: a hard cap of 100 retries.

Only past that cap does OOM stop being control flow…

…and become a loud, logged query termination.

The log carries the task id and the original task id — each retry is a fresh task.

Plus the exact operator index where the reservation ran out: your first stop when debugging.

🔁
The closed loop

Reserve → run → spill-under-pressure → retry-on-OOM is one circle, not four features. The memory history records each failure’s peak, so the retry books a bigger room — the system converges instead of thrashing.

Multi-GPU: your room number comes from your booking

Since #732, tasks are dispatched by data locality — round-robin only when nothing has a preference. Which device your code runs on is decided by one thing: the device contract (SCHED-RR).

1
The reservation names the device

gpu_pipeline_task::execute takes its memory space from its reservation — the booking is the sole authority.

2
prepare_for_processing colocates everything

Every input batch is moved onto that memory space — before any operator runs.

3
Only then do operators run

An operator never asks a batch where it lives. Batches are guests; the booking decided the room.

⚠️
War story: push, pile-up, pin

#732’s greedy push scheduling piled tasks into per-GPU queues — beyond the downgrade executor’s reach, so their batches could never be spilled. #827 restored pull-signal backpressure: workers ask for work, queues stay shallow, victims stay reachable. And after cross-device SIGABRTs, #996 turned “prefer this device” into “pin this device” for cuco-backed operators.

Which brings us to the two ways new code dies in production here:

🔒

Hoarding out of reach

Holding memory the downgrade executor can’t see — a private stash outside repositories and the inspectable queue turns pressure into a dead query.

🧭

Guessing the device

Inferring your GPU from anything but the task’s reservation — a #996-class crash waiting for an 8-GPU box.

Debug it before it ships

A new operator picks its CUDA device with batches[0]->get_memory_space() before prepare_for_processing has run. Single-GPU tests pass. What happens on an 8-GPU box?

✗

RESULT_COLLECTOR clone

A pure terminal: its sink() runs inside the compute pipeline’s task. It creates no tasks of its own — so a full channel could only ever stall a worker thread mid-task.

✓

CONCAT-shape boundary

A boundary operator: is_source() && is_sink(), heading its own pipeline. Backpressure becomes a task-creation condition: full channel → no sink tasks → upstream port repos fill with idle, spillable batches → the engine throttles itself. No worker ever blocks.

The channel contract

Both operators stand on one primitive. Its contract fits on a card — read it as the spec your unit tests will assert:

Planned API — from the design notes, not yet in tree

exchange_channel — bounded, close-then-drain

{batch_id, size_bytes} What travels: a handle, never a batch. The batch is registered in a repository FIRST, then the handle is pushed.
try_push(h) False when full or closed; never blocks. The engine side only ever uses the try_ pair.
try_pop() Nullopt when empty; never blocks. Blocking push/pop exist only for the wrapper/test side.
close() Idempotent. Forbids new pushes — but queued items stay poppable: close-then-drain, not abort.
drained() closed() && empty() — the one true EOS predicate, same shape as split_connector::is_closed().

Why handles? Module 4’s law: a batch idle in a repository is a spill candidate. Trace one batch across the boundary:

1
Producer registers the batch in a repository

Ownership lands where the downgrade executor can see it — idle, unlocked, spillable.

2
Then it pushes {batch_id, size_bytes}

Two POD fields cross the channel. The channel holds metadata, never memory.

3
Your source resolves the id at task-creation time

pop_data_batch_by_id(h.batch_id) claims the batch from the repo only when a task is actually being built.

⚖️
The channel must never own memory

A shared_ptr<data_batch> in the queue would make the channel a hidden owner of GPU memory — invisible to the downgrade executor, Module 5’s cardinal sin. Handles keep every queued batch idle-in-repo until the moment a task claims it.

Your source’s hint table

Module 3’s three answers, re-derived for a channel instead of a split_connector — this is the table your operator’s get_next_task_hint() implements (per the design notes):

⚡

channel non-empty

READY{this} — one task per available batch, open or closed. Multi-shot; READY must carry this (a null producer throws).

⏸

open but empty

WAITING_FOR_INPUT_DATA{nullptr} — “not now.” The producer is a remote machine; there is no upstream operator for the hint chain to recurse into.

🏁

closed AND drained

std::nullopt — exhausted forever, terminal. The streaming twin of a scan running out of splits.

all_ports_empty() Overridden to channel->drained(). A zero-port source inherits a base that returns true unconditionally — forget this override and your operator’s body silently never runs.
⚠️
The hint is not admission control

Module 3’s task creator evaluates the hint once, then loops building tasks — it does not re-poll the hint per pull. Per-pull gating belongs in get_next_task_input_data(): try_pop(), and return nullptr when nothing is there.

Install your own switch

A scan gets its completion evaluation for free — there’s always a task in flight to trip the sensor. A stream must install its own switch: every zero-task EOS path has to trigger the status evaluation itself. Any operator whose input isn’t the scan manager will face this exact gap.
