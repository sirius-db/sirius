The Big Picture

You load one extension. Your SQL doesn't change. Supported queries silently run on the GPU. Where exactly does the swap happen?

A simultaneous interpreter in the booth

DuckDB is the speaker at the podium; Sirius sits in the interpreter's booth, translating the talk into GPU execution live, mid-sentence. When it hits an idiom it can't translate, it hands the mic back — and the audience never notices the switch.

🗣️
DuckDB speaks

Parses, binds, optimizes — business as usual. It has no idea it's being interpreted.

🎧
Sirius translates live

In the booth, it converts DuckDB's optimized plan into its own GPU operators, mid-sentence.

🎤
The mic hands back silently

Untranslatable idiom? The CPU takes over — correct results, and nobody hears the switch.

Concretely: Sirius is a GPU-native SQL engine shipped as a DuckDB extension. Compute runs on cuDF and RMM, with memory and data-movement primitives from NVIDIA cuCascade.

🧠
The whole engine in one sentence

Sirius intercepts a SQL query, converts DuckDB's plan into its own physical operators, groups them into pipelines, and a task creator turns 'operator + available input' into GPU tasks that a scheduler runs. Data flows between operators through repositories (not function returns), and ports tell each operator where its input lives.

The swap happens in exactly one place

Sirius hooks DuckDB through an optimizer extension. The hook itself decides nothing about GPU support — it just captures the plan for a later verdict.

1
The hook copies the optimized logical plan

DuckDB's optimizer finishes; Sirius copies the plan and stashes it in its per-connection state. No GPU judgment yet.

2
OnFinalizePrepare runs create_plan()

sirius_physical_plan_generator::create_plan() walks the copy, building Sirius physical operators — or throwing at the first unsupported one.

3
Success wraps the plan; a throw falls back

Success: the plan is wrapped in PhysicalSiriusExecution and swapped in. Throw: DuckDB's own CPU plan runs, silently.

src/transparent/sirius_optimizer_extension.cpp ↗ reader mode

Plain English

The comment states the contract: create_plan() on this copy is the single source of truth for GPU support — no other code path gets a vote.

And the failure mode is spelled out up front: an unsupported operator means a throw, and the throw is the fallback signal.

Copy the plan so Sirius owns its own version — DuckDB keeps the original, untouched, ready for CPU execution.

Stash the copy in Sirius's per-connection state; OnFinalizePrepare will pick it up once preparation finalizes.

Some plans can't even be copied (not serializable). No drama: quietly skip GPU — the user's query still runs on CPU.

Anything else unexpected gets logged at debug level. The user never sees an error, just a CPU-executed query.

Either way the query proceeds. GPU is an optimization, never a requirement.

💡
Key insight: GPU support is a plan-level decision, made once

create_plan() either succeeds (plan wrapped and swapped) or throws (silent CPU fallback). So when a query unexpectedly runs on CPU — or you wonder "will my new operator ever be used?" — there is exactly one gate to check.

Meet the Actors

Every Sirius bug report eventually reduces to: which of seven objects misbehaved? Learn their names and their threads and you can triage anything.

One room, seven consoles

Think mission control: the Flight Director owns the go/no-go, the trajectory team plans the next burn, each spacecraft has its own ops crew, and life support quietly keeps everyone breathing. Nothing talks directly — it all goes through the loop. In Sirius the room itself is SiriusContext, registered as a DuckDB ClientContextState — and its member list is the component map.

Plain English

The flight recorder — every console below reports its timings here.

The shared telemetry log: all data that moves between operators lives here, never handed console-to-console.

The Flight Director — one management loop that bridges task requests to the per-GPU crews.

Life support — note the vector: one downgrade executor per memory space, not per query.

The trajectory team — decides what runs next. Deciding, not running.

Ground stations — owns splitting base tables and feeding the data uplink.

💡
Roles are strictly separated

Deciding what runs next (task_creator) is a different object — and different threads — from running it (the executors) and from surviving memory pressure (the downgrade executors). "Where do I put this logic?" and "whose thread am I on?" are the two questions that prevent broken PRs.

The seven consoles

Each console has exactly one job. Memorize the mapping — every stack trace you'll ever read lands in one of these.

📋

sirius_engine + plan generator

Mission planning. At query start it translates DuckDB's plan into GPU pipelines (src/planner/sirius_physical_plan_generator.cpp) — once, on the DuckDB query thread.

🧭

task_creator

The trajectory team — decides the next burn. Walks each pipeline's hint chain and turns READY hints into tasks. 2 threads by default.

🎙️

task_scheduler

The Flight Director — owns the go/no-go. A management event loop bridging task requests to executors. Renamed from pipeline_executor in #687.

🚀

gpu_pipeline_executor

One ops crew per spacecraft — one executor per GPU. 1 manager thread + 4 workers, each worker pinned with its own CUDA stream.

📡

scan_manager + scan executor

Ground stations. Splits base tables into scan splits and runs the ingest that feeds every pipeline's first operator.

🛟

downgrade_executor

Life support — consumables management. Monitor + processing threads per memory space; spills batches downhill before anyone hits OOM.

🗄️

shared_data_repository_manager

The shared telemetry log. Every batch an operator produces is published here for the next one to pull — no direct hand-offs, ever.

Mental model: a kanban factory line. Stations never push work downstream — a station pulls when its input bin has parts, and the andon board only updates when a worker turns in a job card. Hold on to that second rule; it becomes a bug story in Module 8.

Not all bins are equal. Each input port carries a barrier type that decides when the consumer may start:

The heart: get_next_task_hint()

The task creator never guesses what to run next. Before building any task it asks the operator for a hint — and there are exactly three possible answers.

⚡

READY{this}

“Build me a task.” Every input port has data, or I am a source with splits left. The creator wraps the pipeline in a gpu_pipeline_task.

🔁

WAITING_FOR_INPUT_DATA{producer}

“Go ask upstream.” A FULL-barrier port has an unfinished producer, and the hint carries a pointer to it. The creator recurses — the hint chain.

🏁

std::nullopt

“I’m done forever.” No task will ever be needed here again — a scan answers this once its last split is gone. The creator stops asking.

src/include/op/sirius_physical_operator.hpp:49 ↗
enum class TaskCreationHint { WAITING_FOR_INPUT_DATA, READY };

enum class MemoryBarrierType { PIPELINE, PARTIAL, FULL };

struct task_creation_hint {
  TaskCreationHint hint{TaskCreationHint::WAITING_FOR_INPUT_DATA};
  sirius_physical_operator* producer{nullptr};
};

The base implementation walks the input ports looking for a FULL barrier whose producer pipeline hasn’t finished. Found one? Answer WAITING, pointing at that pipeline’s source. Every port satisfied? The function falls through to READY.

src/op/sirius_physical_operator.cpp:275 ↗ reader mode
std::optional<task_creation_hint> sirius_physical_operator::get_next_task_hint()
{
  if (ports.empty()) { return std::nullopt; }

look at the input ports and see if there are any unfinished hard barriers
  auto unfinished_barrier = std::find_if(_ports_list.begin(), _ports_list.end(), [](const auto& p) {
    return p->type == MemoryBarrierType::FULL && p->src_pipeline &&
           !p->src_pipeline->is_pipeline_finished();
  });

  if (unfinished_barrier != _ports_list.end()) {
    auto* producer = &((*unfinished_barrier)->src_pipeline->get_operators()[0].get());
    return task_creation_hint{TaskCreationHint::WAITING_FOR_INPUT_DATA, producer};
  }

A task runs the line

A READY hint becomes a gpu_pipeline_task: one split pushed through every station of one pipeline. Four moves, always in this order:

1
Reserve GPU memory

Admission control: the memory this batch needs is reserved before anything executes. Module 6 lives entirely inside this step.

2
prepare_for_processing()

Lock the input batches and colocate them into one memory space, so the kernels see resident, same-device inputs.

3
execute() each operator

The batch is pulled through the station chain on the GPU: scan output through FILTER, results into the partial-COUNT sink.

4
publish_output() → terminal sink()

Surviving rows are pushed into the repository of the next port — as handles, never copies.

Where exactly does the CPU stop and the GPU begin? The four moves above straddle a boundary. Hover the nodes — each one answers an ownership question: who controls execution, who owns the memory, where kernels launch, where the sync points are.

The producer’s last word. close() is idempotent and wakes every blocked consumer — the close half of close-then-drain.

Errors ride the connector itself: the first non-null exception wins, and later close() calls cannot overwrite it.

And it is rethrown only after the queue drains — consumers still receive every split that made it in before the failure.

The consumer’s entire API: block until a split arrives or the stream is over.

nullopt ≠ error. It is the clean end-of-stream; failure arrives as a throw, on this same call, post-drain.

is_closed = closed AND drained. A closed connector with splits still queued has work left to hand out.

In Sirius, no operator ever returns data to its caller. Ever. Here's why that one decision buys spilling, backpressure, and multi-GPU almost for free.

Pallets have manifests: the batch lifecycle

A data_batch is the manifest, not the pallet — and you never touch its buffers directly, only through RAII locks: many read_only readers XOR one mutable holder. idle means nobody holds it.

N

💡
Spillable = idle + in a registered repository

The downgrade executor never asks operators for memory back — it walks repositories and takes idle batches. Both conditions are load-bearing: a batch it can't find or can't lock might as well not exist. That is why repositories being first-class, inspectable objects is the whole game — it's what makes spilling possible at all.

⚠️
How you cause an OOM

Park batches in a private queue, or sit on locks "for later" — either way they're invisible to the downgrade executor and the query dies under pressure instead of spilling. Module 8's streaming design exists to dodge exactly this: ownership stays in repositories, and only {batch_id, size} handles travel through channels.

History: this tri-class lock design replaced a 4-state FSM (cuCascade #117, adopted in Sirius #689) — lock-discipline races stopped being runtime bugs and became compile errors.

The closed loop

Reserve → run → spill-under-pressure → retry-on-OOM is one circle, not four features. The memory history records each failure’s peak, so the retry books a bigger room — the system converges instead of thrashing.

Multi-GPU: your room number comes from your booking

Since #732, tasks are dispatched by data locality — round-robin only when nothing has a preference. Which device your code runs on is decided by one thing: the device contract (SCHED-RR).

2

3

An operator never asks a batch where it lives. Batches are guests; the booking decided the room.

⚠️
War story: push, pile-up, pin

#732’s greedy push scheduling piled tasks into per-GPU queues — beyond the downgrade executor’s reach, so their batches could never be spilled. #827 restored pull-signal backpressure: workers ask for work, queues stay shallow, victims stay reachable. Hoarding out of reach

Guessing the device

Inferring your GPU from anything but the task’s reservation — a #996-class crash waiting for an 8-GPU box.

The channel must never own memory

A shared_ptr<data_batch> in the queue would make the channel a hidden owner of GPU memory — invisible to the downgrade executor, Module 6’s cardinal sin. Handles keep every queued batch idle-in-repo until the moment a task claims it.

Your source’s hint table

Module 3’s three answers, re-derived for a channel instead of a split_connector — this is the table your operator’s get_next_task_hint() implements (per the design notes):

⚡

channel non-empty

READY{this} — one task per available batch, open or closed. Multi-shot; READY must carry this (a null producer throws).

⏸

open but empty

⚠️
The hint is not admission control

Module 3’s task creator evaluates the hint once, then loops building tasks — it does not re-poll the hint per pull. Per-pull gating belongs in get_next_task_input_data(): try_pop(), and return nullptr when nothing is there.

Install your own switch

A scan gets its completion evaluation for free — there’s always a task in flight to trip the sensor. A stream must install its own switch: every zero-task EOS path has to trigger the status evaluation itself. Any operator whose input isn’t the scan manager will face this exact gap.
