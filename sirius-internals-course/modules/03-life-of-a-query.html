Life of a Query

One query traced end to end with the real functions — from SQL string to fulfilled future.

One query, two pipelines

Let’s trace one query, end to end, with the real functions — every name below is grep-able in the tree:

the query 
SELECT count(*) FROM orders WHERE amount > 100;

DuckDB parses it; Sirius converts the plan and cuts it at the COUNT, because an aggregate is a pipeline breaker — it must see all input before emitting anything. The result is two pipelines:

the split plan 
Pipeline A (streaming): SCAN(orders) → FILTER(amount>100) → [sink: partial COUNT state]
Pipeline B (terminal): COUNT finalize → RESULT_COLLECTOR

Mental model: a kanban factory line. Stations never push work downstream — a station pulls when its input bin has parts, and the andon board only updates when a worker turns in a job card. Hold on to that second rule; it becomes a bug story in Module 7.

Not all bins are equal. Each input port carries a barrier type that decides when the consumer may start:

PIPELINE A’s internal hops: SCAN → FILTER → sink stream batch by batch.
FULL B’s input port: COUNT finalize is blocked until Pipeline A completely finishes.
PARTIAL Not used in this query — the in-between type for hand-offs like concat.

Kickoff: one line of code starts everything

DuckDB’s execution thread calls exactly one Sirius entry point, then goes to sleep. Everything else in this module happens on Sirius worker threads while that thread blocks on the returned future.

The heart: get_next_task_hint()

The task creator never guesses what to run next. Before building any task it asks the operator for a hint — and there are exactly three possible answers.

⚡

READY{this}

“Build me a task.” Every input port has data, or I am a source with splits left. The creator wraps the pipeline in a gpu_pipeline_task.

🔁

WAITING_FOR_INPUT_DATA{producer}

“Go ask upstream.” A FULL-barrier port has an unfinished producer, and the hint carries a pointer to it. The creator recurses — the hint chain.

🏁

std::nullopt

“I’m done forever.” No task will ever be needed here again — a scan answers this once its last split is gone. The creator stops asking.

src/include/op/sirius_physical_operator.hpp:49 
enum class TaskCreationHint { WAITING_FOR_INPUT_DATA, READY };

enum class MemoryBarrierType { PIPELINE, PARTIAL, FULL };

struct task_creation_hint {
  TaskCreationHint hint{TaskCreationHint::WAITING_FOR_INPUT_DATA};
  sirius_physical_operator* producer{nullptr};
};

The base implementation walks the input ports looking for a FULL barrier whose producer pipeline hasn’t finished. Found one? Answer WAITING, pointing at that pipeline’s source. Every port satisfied? The function falls through to READY.

src/op/sirius_physical_operator.cpp:275 
std::optional<task_creation_hint> sirius_physical_operator::get_next_task_hint()
{
  if (ports.empty()) { return std::nullopt; }

  // look at the input ports and see if there are any unfinished hard barriers
  auto unfinished_barrier = std::find_if(_ports_list.begin(), _ports_list.end(), [](const auto& p) {
    return p->type == MemoryBarrierType::FULL && p->src_pipeline &&
           !p->src_pipeline->is_pipeline_finished();
  });

  if (unfinished_barrier != _ports_list.end()) {
    auto* producer = &((*unfinished_barrier)->src_pipeline->get_operators()[0].get());
    return task_creation_hint{TaskCreationHint::WAITING_FOR_INPUT_DATA, producer};
  }

A task runs the line

A READY hint becomes a gpu_pipeline_task: one split pushed through every station of one pipeline. Four moves, always in this order:

1
Reserve GPU memory

Admission control: the memory this batch needs is reserved before anything executes. Module 5 lives entirely inside this step.

2
prepare_for_processing()

Lock the input batches and colocate them into one memory space, so the kernels see resident, same-device inputs.

3
execute() each operator

The batch is pulled through the station chain on the GPU: scan output through FILTER, results into the partial-COUNT sink.

4
publish_output() → terminal sink()

Surviving rows are pushed into the repository of the next port — as handles, never copies.

🔗
Data moves by handle, not copy

publish_output() deposits references to GPU-resident batches; nothing is serialized and nothing returns up the call stack. What a batch actually is — that’s Module 4.

Completion drives everything

Nothing polls this factory. The only moment the engine re-evaluates a pipeline is the tail of mark_task_completed() — a worker turning in a job card:

Escape hatch: a LIMIT downstream already has every row it needs — stop early.

Otherwise, two conditions: the source has handed out its last split, AND every input port has been drained.

In-flight accounting: every job card issued has been turned back in. No task is still running against these operators.

Only now is the pipeline declared finished.

Each operator gets its one finalize call — the partial COUNT seals its state here.

Close the profiling range, and flag that downstream pipelines waiting on our FULL barrier must be notified — this is what wakes Pipeline B.

Completion is edge-triggered: if no task completes, update_pipeline_status() never runs and nobody ever re-checks anything. The andon board only updates on a turned-in job card — and that exact property becomes a hang story in Module 7.
