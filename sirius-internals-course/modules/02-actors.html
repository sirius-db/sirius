Meet the Actors

Every Sirius bug report eventually reduces to: which of seven objects misbehaved? Learn their names and their threads and you can triage anything.

One room, seven consoles

Think mission control: the Flight Director owns the go/no-go, the trajectory team plans the next burn, each spacecraft has its own ops crew, and life support quietly keeps everyone breathing. Nothing talks directly — it all goes through the loop. In Sirius the room itself is SiriusContext, registered as a DuckDB ClientContextState — and its member list is the component map.

Plain English

The flight recorder — every console below reports its timings here.

The shared telemetry log: all data that moves between operators lives here, never handed console-to-console.

The Flight Director — one management loop that bridges task requests to the per-GPU crews.

Life support — note the vector: one downgrade executor per memory space, not per query.

The trajectory team — decides what runs next. Deciding, not running.

Ground stations — owns splitting base tables and feeding the data uplink.

💡
Roles are strictly separated

Deciding what runs next (task_creator) is a different object — and different threads — from running it (the executors) and from surviving memory pressure (the downgrade executors). "Where do I put this logic?" and "whose thread am I on?" are the two questions that prevent broken PRs.

The seven consoles

Each console has exactly one job. Memorize the mapping — every stack trace you'll ever read lands in one of these.

📋

sirius_engine + plan generator

Mission planning. At query start it translates DuckDB's plan into GPU pipelines (src/planner/sirius_physical_plan_generator.cpp) — once, on the DuckDB query thread.

🧭

task_creator

The trajectory team — decides the next burn. Walks each pipeline's hint chain and turns READY hints into tasks. 2 threads by default.

🎙️

task_scheduler

The Flight Director — owns the go/no-go. A management event loop bridging task requests to executors. Renamed from pipeline_executor in #687.

🚀

gpu_pipeline_executor

One ops crew per spacecraft — one executor per GPU. 1 manager thread + 4 workers, each worker pinned with its own CUDA stream.

📡

scan_manager + scan executor

Ground stations. Splits base tables into scan splits and runs the ingest that feeds every pipeline's first operator.

🛟

downgrade_executor

Life support — consumables management. Monitor + processing threads per memory space; spills batches downhill before anyone hits OOM.

🗄️

shared_data_repository_manager

The shared telemetry log. Every batch an operator produces is published here for the next one to pull — no direct hand-offs, ever.

the defaults, straight from sirius_config.hpp

  exec::thread_pool_config _task_creator_config{.num_threads        = 2,
  exec::thread_pool_config _gpu_pipeline_executor_config{.num_threads        = 4,

Who owns which directory

The consoles map one-to-one onto the source tree. Click a directory to expand or collapse it, hover an owner chip to recall its job — every row links to the real code.

The room, live

Here's the radio traffic for one query: SELECT count(*) FROM orders WHERE amount > 100;. Note who talks to whom — and who never talks to anyone directly.

D
DuckDB → all

Prepared statement ready. Sirius, you're up — plan swapped in.

S
Scheduler → TaskCreator

start_query(). Please make a task for the SCAN.

TC
TaskCreator → GPU-0

Scan says READY. Here's a gpu_pipeline_task for Pipeline A.

G0
GPU-0 → all

Reserved 512 MB, ran scan→filter→partial count. Batch published to the repo.

DG
Downgrade → all

GPU 0 at 92% — spilling two idle batches to host. Carry on.

TC
TaskCreator → GPU-0

Scan drained, last task done → Pipeline A finished. Pipeline B is READY.

G0
GPU-0 → DuckDB

COUNT finalized into RESULT_COLLECTOR. Future fulfilled — your rows, sir.
