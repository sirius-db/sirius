The Big Picture

You load one extension. Your SQL doesn't change. Supported queries silently run on the GPU. Where exactly does the swap happen?

A simultaneous interpreter in the booth

DuckDB is the speaker at the podium; Sirius sits in the interpreter's booth, translating the talk into GPU execution live, mid-sentence. When it hits an idiom it can't translate, it hands the mic back — and the audience never notices the switch.

🗣️
DuckDB speaks

Parses, binds, optimizes — business as usual. It has no idea it's being interpreted.

🎧
Sirius translates live

In the booth, it converts DuckDB's optimized plan into its own GPU operators, mid-sentence.

🎤
The mic hands back silently

Untranslatable idiom? The CPU takes over — correct results, and nobody hears the switch.

Concretely: Sirius is a GPU-native SQL engine shipped as a DuckDB extension. Compute runs on cuDF and RMM, with memory and data-movement primitives from NVIDIA cuCascade.

🧠
The whole engine in one sentence

Sirius intercepts a SQL query, converts DuckDB's plan into its own physical operators, groups them into pipelines, and a task creator turns 'operator + available input' into GPU tasks that a scheduler runs. Data flows between operators through repositories (not function returns), and ports tell each operator where its input lives.

The swap happens in exactly one place

Sirius hooks DuckDB through an optimizer extension. The hook itself decides nothing about GPU support — it just captures the plan for a later verdict.

1
The hook copies the optimized logical plan

DuckDB's optimizer finishes; Sirius copies the plan and stashes it in its per-connection state. No GPU judgment yet.

2
OnFinalizePrepare runs create_plan()

sirius_physical_plan_generator::create_plan() walks the copy, building Sirius physical operators — or throwing at the first unsupported one.

3
Success wraps the plan; a throw falls back

Success: the plan is wrapped in PhysicalSiriusExecution and swapped in. Throw: DuckDB's own CPU plan runs, silently.

Plain English

The comment states the contract: create_plan() on this copy is the single source of truth for GPU support — no other code path gets a vote.

And the failure mode is spelled out up front: an unsupported operator means a throw, and the throw is the fallback signal.

Copy the plan so Sirius owns its own version — DuckDB keeps the original, untouched, ready for CPU execution.

Stash the copy in Sirius's per-connection state; OnFinalizePrepare will pick it up once preparation finalizes.

Some plans can't even be copied (not serializable). No drama: quietly skip GPU — the user's query still runs on CPU.

Anything else unexpected gets logged at debug level. The user never sees an error, just a CPU-executed query.

Either way the query proceeds. GPU is an optimization, never a requirement.

💡
Key insight: GPU support is a plan-level decision, made once

create_plan() either succeeds (plan wrapped and swapped) or throws (silent CPU fallback). So when a query unexpectedly runs on CPU — or you wonder "will my new operator ever be used?" — there is exactly one gate to check.

Four eras to get here

The codebase you're joining is the third engine to wear the name. Knowing the strata explains why src/legacy/ exists and why everything new lives in namespace sirius.

⛏️

2024 · Hand-written CUDA

The gpu_processing era: a bespoke kernel per operator. Heroic, unmaintainable, ultimately a dead end.

🔄

Apr 2025 · The cuDF pivot

#6 rebased compute onto cuDF: stop writing kernels, start composing libcudf. The engine got a library.

🏗️

Dec 2025–Feb 2026 · Super Sirius

Ground-up rewrite on cuCascade: #96 → #134 → #198, first end-to-end query in #206. #267 wired TPC-H into the integration tests — ever since, that's how the project knows a change is correct.

🎭

Apr 2026 · Transparent interception

#518: load the extension and plain SQL just runs on GPU. No special syntax — the interpreter enters the booth. The old engine was walled off in the same push: gated behind an ENABLE_LEGACY_SIRIUS build flag (#509, Mar 2026), then relocated under src/legacy/ (#692, Apr 2026).

src/legacy/ The dead gpu_processing path, quarantined. Read it for archaeology — never modify it. All new work targets Super Sirius.
