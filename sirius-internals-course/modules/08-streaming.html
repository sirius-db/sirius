Your streaming source

Pops handles from an exchange_channel a remote producer pushes into. Same hint machinery — but a stream can legally produce zero tasks. Hold that thought.

Your sink (#837) mirrors it at the top of the fragment — and its shape is the first real design decision on your PR:

✗

RESULT_COLLECTOR clone

A pure terminal: its sink() runs inside the compute pipeline’s task. It creates no tasks of its own — so a full channel could only ever stall a worker thread mid-task.

✓

CONCAT-shape boundary

A boundary operator: is_source() && is_sink(), heading its own pipeline. Backpressure becomes a task-creation condition: full channel → no sink tasks → upstream port repos fill with idle, spillable batches → the engine throttles itself. No worker ever blocks.

The channel contract

Both operators stand on one primitive. Its contract fits on a card — read it as the spec your unit tests will assert:

Planned API — from the design notes, not yet in tree

exchange_channel — bounded, close-then-drain

{batch_id, size_bytes} What travels: a handle, never a batch. The batch is registered in a repository FIRST, then the handle is pushed.
try_push(h) False when full or closed; never blocks. The engine side only ever uses the try_ pair.
try_pop() Nullopt when empty; never blocks. Blocking push/pop exist only for the wrapper/test side.
close() Idempotent. Forbids new pushes — but queued items stay poppable: close-then-drain, not abort.
drained() closed() && empty() — the one true EOS predicate, same shape as split_connector::is_closed().

Why handles? Module 5’s law: a batch idle in a repository is a spill candidate. Trace one batch across the boundary:

1
Producer registers the batch in a repository

Ownership lands where the downgrade executor can see it — idle, unlocked, spillable.

2
Then it pushes {batch_id, size_bytes}

Two POD fields cross the channel. The channel holds metadata, never memory.

3
Your source resolves the id at task-creation time

pop_data_batch_by_id(h.batch_id) claims the batch from the repo only when a task is actually being built.

⚖️
The channel must never own memory

A shared_ptr<data_batch> in the queue would make the channel a hidden owner of GPU memory — invisible to the downgrade executor, Module 6’s cardinal sin. Handles keep every queued batch idle-in-repo until the moment a task claims it.

Your source’s hint table

Module 3’s three answers, re-derived for a channel instead of a split_connector — this is the table your operator’s get_next_task_hint() implements (per the design notes):

⚡

channel non-empty

READY{this} — one task per available batch, open or closed. Multi-shot; READY must carry this (a null producer throws).

⏸

open but empty

WAITING_FOR_INPUT_DATA{nullptr} — “not now.” The producer is a remote machine; there is no upstream operator for the hint chain to recurse into.

🏁

closed AND drained

std::nullopt — exhausted forever, terminal. The streaming twin of a scan running out of splits.

all_ports_empty() Overridden to channel->drained(). A zero-port source inherits a base that returns true unconditionally — forget this override and your operator’s body silently never runs.
⚠️
The hint is not admission control

Module 3’s task creator evaluates the hint once, then loops building tasks — it does not re-poll the hint per pull. Per-pull gating belongs in get_next_task_input_data(): try_pop(), and return nullptr when nothing is there.

For your source, both clauses delegate to the channel: finished and all_ports_empty() are both drained(). An empty, closed stream passes instantly.

Zero created equals zero completed — trivially true. Every condition holds.

The condition is perfect. The streaming question is different: who calls this when a stream closes and no task is in flight? Pre-fix: nobody.

💡
Install your own switch

A scan gets its completion evaluation for free — there’s always a task in flight to trip the sensor. A stream must install its own switch: every zero-task EOS path has to trigger the status evaluation itself. Any operator whose input isn’t the scan manager will face this exact gap.

The ship checklist

Six invariants, one from each stop of this course. Pin this next to your two PRs:

✓
The channel carries handles; the repository owns batches M4

Queued data stays idle-in-repo — spillable — and the channel never pins GPU memory.

✓
Barrier types on the wired ports are streaming-compatible M4

A FULL barrier waits for a producer pipeline to finish — check what that means when the producer is a stream.

✓
Admission lives in get_next_task_input_data(), not just the hint M3

The creator’s loop doesn’t re-poll hints — gate every pull, return nullptr when the channel is dry.

✓
Zero-task EOS paths trigger status evaluation themselves M7

No completion edge means no free re-check. The empty stream and the late close both need your switch.

✓
External consumers must not outlive drain_after_error’s drain order M2/M3

The error path tears down in a fixed order; a remote reader holding handles past it is a use-after-free.

✓
The device comes from the reservation when #838 partitioning arrives M5

Never infer a GPU from a batch — the task’s reservation is the sole authority, streaming or not.
