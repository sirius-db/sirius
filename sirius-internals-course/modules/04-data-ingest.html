Where Data Comes From

Module 3 hand-waved a whole subsystem: “the scan executor produces batches.” Produced from what? Here’s the machinery between a file path and a GPU-resident batch.

The quarry that feeds the crusher

Think of a quarry: surveyors mark the seams (metadata walk → splits), a blasting schedule decides load sizes (split providers), and a conveyor with a buffer bin (the IO framework) keeps the crusher — GPU decode — fed. The design goal of everything below: the crusher never waits on the quarry.

The connector’s contract: close, then drain

A split is one schedulable unit of scan work — a batch of parquet row groups, or byte ranges of a .duckdb file. The connector between providers and the operator is small enough to memorize, and its three semantics are exactly the ones people get wrong:

Plain English

The producer’s last word. close() is idempotent and wakes every blocked consumer — the close half of close-then-drain.

Errors ride the connector itself: the first non-null exception wins, and later close() calls cannot overwrite it.

And it is rethrown only after the queue drains — consumers still receive every split that made it in before the failure.

The consumer’s entire API: block until a split arrives or the stream is over.

nullopt ≠ error. It is the clean end-of-stream; failure arrives as a throw, on this same call, post-drain.

is_closed = closed AND drained. A closed connector with splits still queued has work left to hand out.

Four sources, one scan machinery

The parquet and DuckDB-native paths sit behind gpu_ingestible since the unification (#871): one scan operator, pluggable decoders (src/op/scan/gpu_ingestible.cpp ↗). The other two compose with that machinery instead of reimplementing it: S3 is a datasource feeding the parquet decoder from below, and Iceberg landed as its own ICEBERG_SCAN operator layered on the parquet machinery — though that path is currently non-functional (see the card below). “Add a storage format” stays a bounded problem — a decoder + split provider for a new file format; just a datasource for a new place bytes live.

🧊 Iceberg — landed in #521, currently non-functional ▸ details

What landed (#521): V1/V2 table scans where the metadata reader walked manifests into splits and positional/equality deletes ran as GPU filter kernels rather than CPU-side row rewrites.

Current status — the GPU Iceberg path is non-functional in this tree. It went stale during the IO-framework transition (#997): iceberg_metadata_reader.cpp and iceberg_scan_task.cpp are excluded from the build, neither the scan manager nor the task creator has any ICEBERG_SCAN handling, and delete-data reading is stubbed out with a runtime warning (prefetch_iceberg_delete_data, src/sirius_engine.cpp ↗). The plan generator still accepts iceberg_scan, but nothing downstream can execute it — don’t rely on GPU Iceberg scans today.

The conveyor and the buffer bin

Why a whole framework? Scan throughput was gated on synchronous file I/O — the framework overlaps I/O with decode, and gave S3 a place to plug in as just another datasource.
