The Data Plane

In Sirius, no operator ever returns data to its caller. Ever. Here's why that one decision buys spilling, backpressure, and multi-GPU almost for free.

A named dock, not a return value

Think freight docks: a producer pipeline drops pallets — batches — at a named dock, and the dock's rules say when the consumer may start unloading. In Sirius the dock is a port — and it never holds goods itself, it points at the repository where they live.

repo == NULL is a feature, not a bug

When the scan pipeline was split out (#620), some pipelines still had to run in order without exchanging a single batch. The answer is a dependency-only port: a scheduling edge with no warehouse — same struct, treated as "empty, not data-gating".

Output is a push, never a return

Here is the entire replacement for "function returns data" — the base-class sink(), about seven lines. When our running count(*) query's filter finishes a batch of partial counts, this is how they leave: each handle is filed at every downstream dock, and the caller never sees a thing.

src/op/sirius_physical_operator.cpp · L238-246 ↗

void sirius_physical_operator::sink(const operator_data& output_data, rmm::cuda_stream_view stream)
{
  auto& pipelineable_output = dynamic_cast<const pipelineable_operator_data&>(output_data);
  for (auto& batch : pipelineable_output.get_data_batches()) {
    for (auto& next_port_info : next_port_after_sink) {
      next_port_info.next_operator->push_data_batch(next_port_info.next_operator_port_name, batch);
    }
  }
}

Three unloading rules

The barrier type is pipeline semantics compressed into one enum. Same repository machinery underneath — only the release rule changes.

🚚

PIPELINE — roll-through dock

Pallets release one at a time, the moment they land. This is how a filter chain streams: each batch flows straight to the next operator in the same pipeline.

🌊

PARTIAL — wave release

Goods release in waves while the shipment is still arriving. CONCAT-after-PARTITION consumes partitions incrementally, across a pipeline boundary.

🏛️

FULL — bonded warehouse

Sealed until the entire shipment clears customs. A hash-join's build side stays invisible until its producing pipeline completely finishes.

Pallets have manifests: the batch lifecycle

A data_batch is the manifest, not the pallet — and you never touch its buffers directly, only through RAII locks: many read_only readers XOR one mutable holder. idle means nobody holds it.

N

read_only
Any number of concurrent readers. Converters queue behind all of them.

⇄
0

idle
Nobody holds it. The only state that can be locked either way — and the only state that can be spilled.

⇄
1

mutable_locked
Exactly one exclusive holder. Required to mutate — or convert to another memory space.

💡
Spillable = idle + in a registered repository

The downgrade executor never asks operators for memory back — it walks repositories and takes idle batches. Both conditions are load-bearing: a batch it can't find or can't lock might as well not exist. That is why repositories being first-class, inspectable objects is the whole game — it's what makes spilling possible at all.

⚠️
How you cause an OOM

Park batches in a private queue, or sit on locks "for later" — either way they're invisible to the downgrade executor and the query dies under pressure instead of spilling. Module 8's streaming design exists to dodge exactly this: ownership stays in repositories, and only {batch_id, size} handles travel through channels.

History: this tri-class lock design replaced a 4-state FSM (cuCascade #117, adopted in Sirius #689) — lock-discipline races stopped being runtime bugs and became compile errors.
