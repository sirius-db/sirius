# S3 integration test scaffolding (PR15)

Local MinIO + fixture tooling for the `[s3][integration]` Catch2 tests and the
`test/sql/datasource/s3_read.test` SQLLogicTest.

## What this gives you

- A pinned MinIO container exposing S3 at `http://127.0.0.1:9000`.
- A fixture generator (`generate_fixtures.py`) that writes a 16-byte text blob,
  a small parquet (~256 rows), and a medium parquet (~200k rows) under
  `test/integration/s3/fixtures/local/`.
- A `fixtures.sh` script that uploads the same files to MinIO via the `mc`
  container image so tests can bit-compare S3 reads against the local copy.
- `env.sh` that exports the `SIRIUS_TEST_S3_*` variables consumed by
  `test/cpp/io/s3/test_s3_ioctx.cpp` and `test_s3_integration.cpp`.

## Requirements

- Docker (engine + compose plugin).
- Python 3 with the `duckdb` module (`pip install duckdb` inside the pixi
  shell, or use the `duckdb-python` pixi env which already has it).
- `curl` (used by `fixtures.sh` for readiness probing).

## Typical flow

```bash
# Bring MinIO up and populate fixtures.
make s3-up

# Run the S3 integration Catch2 tag. env.sh points it at the local MinIO.
make s3-test

# Or run a specific test:
source test/integration/s3/env.sh
build/release/extension/sirius/test/cpp/sirius_unittest "[s3][integration]"

# Run the SQLLogicTest end-to-end (manual — not wired to `make test`
# because SQLLogicTests run the legacy gpu_processing path by default).
source test/integration/s3/env.sh
build/release/test/unittest --test-dir . test/sql/datasource/s3_read.test

# Tear down (the `-v` in `down -v` also removes the named volume).
make s3-down
```

## Pinned image versions

The compose file pins both images to exact release tags rather than `:latest`
so the same sirius commit produces reproducible test behavior over time:

| image | tag |
|---|---|
| `minio/minio` | `RELEASE.2025-04-22T22-12-26Z` |
| `minio/mc`    | `RELEASE.2025-04-16T18-13-26Z` |

To bump: replace both tags, run `make s3-up` locally, and confirm
`make s3-test` still passes. Keep the two tags close in age — `mc` command
surface changes occasionally and mixing a very new `mc` with an older server
can break the `mc mb --ignore-existing` flag the script relies on.

## Fixtures

Regenerated by `generate_fixtures.py` on every `make s3-up`. Output is
deterministic (seeded by `range()` + static string templates) so a second run
produces identical files and the sha256 manifest stays stable:

| file | size | purpose |
|---|---|---|
| `hello.txt`      | 16 B   | HEAD + tiny-range read |
| `small.parquet`  | ~20 KB | bit-equal parquet scan via `datasource_factory` |
| `medium.parquet` | ~8 MB  | multi-range reads across row groups |

A sha256 manifest is written to `fixtures/local/MANIFEST.sha256`.

## Caveats

- MinIO signs with `us-east-1` by default; if you set `MINIO_REGION` to
  something else in the compose file, also bump `SIRIUS_TEST_S3_REGION`.
- `fixtures.sh` uses `--network=host` on Linux and `host.docker.internal` on
  macOS/Windows to let `mc` reach MinIO on the host network. If you run MinIO
  inside a non-host-network compose stack, override `SIRIUS_TEST_S3_ENDPOINT`
  to the compose-internal name and drop `--network=host`.
- When `SIRIUS_TEST_S3_*` is not set the integration tests `SUCCEED` with a
  skip message rather than failing — this is intentional so the default
  `sirius_unittest` run stays green on CI runners without docker.
