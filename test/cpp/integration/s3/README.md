# S3 integration test scaffolding

Local MinIO + fixture tooling for the Catch2 `[s3]` tests. The suite covers
the S3 backend from the lower-level `s3_ioctx` and retry/cache paths through
`scan_manager`, parquet split-provider routing, `describe_parquet`, and the
SQL-over-S3 surface.

## What this gives you

- Pinned MinIO containers exposing S3 at `http://127.0.0.1:9000` and
  `https://127.0.0.1:9443`.
- A generated self-signed TLS certificate under `certs/` for the HTTPS MinIO
  service. The certificate is regenerated by `make s3-up` when missing and is
  not checked in.
- A fixture generator (`generate_fixtures.py`) that writes a 16-byte text blob,
  a 20 KiB deterministic binary blob, and an 8 MiB deterministic binary blob
  under `test/cpp/integration/s3/fixtures/local/`, then copies the standard
  Parquet fixtures from `test/cpp/integration/data/parquet/` into
  `fixtures/local/parquet/`.
- A `fixtures.sh` script that uploads everything to MinIO via the `mc`
  container image so tests can bit-compare (and parse) S3 reads against the
  local copy.
- An opt-in `fixtures.sh --perf` / `make s3-test-large` path that also
  generates and uploads the SF10 `tpch/lineitem_sf10.parquet` fixture for
  large SQL correctness coverage.
- `env.sh` that exports the `SIRIUS_TEST_S3_*` variables consumed by
  the S3 Catch2 tests, including `SIRIUS_TEST_S3_HTTPS_ENDPOINT` and
  `SIRIUS_TEST_S3_CA_BUNDLE` for TLS coverage.
- A strict-mode toggle (`SIRIUS_TEST_S3_STRICT`) that keeps ad-hoc local runs
  best-effort while making `make s3-test` fail hard if live S3 access breaks
  after the environment is present.

## Requirements

- Docker (engine + compose plugin).
- Python 3.9+ (stdlib only).
- `curl` (used by `fixtures.sh` for readiness probing).

## Typical flow

```bash
# Build and run the default Catch2 suite. This does not start MinIO.
make test

# Run the full S3 correctness gate. This starts MinIO, populates fixtures,
# sources env.sh, enables strict mode, runs every non-large, non-aws
# [s3][integration] Catch2 test (including the SQL-over-S3 subset), and tears
# MinIO down even if the tests fail.
make s3-test

# Run the opt-in large-SF10 SQL-over-S3 correctness suite. This generates
# test/cpp/integration/s3/fixtures/generated/lineitem_sf10.parquet with the
# in-tree build/release/duckdb, uploads it to s3://sirius-test/tpch/, and runs
# the [s3][sql][large] tests. Expect this to take much longer than s3-test.
make s3-test-large

# Or run manually:
make s3-up
source test/cpp/integration/s3/env.sh
export SIRIUS_TEST_S3_STRICT=1
build/release/extension/sirius/test/cpp/sirius_unittest "[s3]~[large]"

# SQL-over-S3 subset only:
build/release/extension/sirius/test/cpp/sirius_unittest "[s3][sql]~[large]"

# Large SQL-over-S3 subset only, after `make s3-up-large`:
build/release/extension/sirius/test/cpp/sirius_unittest "[s3][sql][large]"

# Tear down (the `-v` in `down -v` also removes the named volume).
make s3-down
```

## Pinned image versions

The compose file pins both images to exact release tags rather than `:latest`
so the same sirius commit produces reproducible test behavior over time:

| image | tag |
|---|---|
| `minio/minio` | `RELEASE.2025-04-22T22-12-26Z` |
| `minio/mc`    | `RELEASE.2025-04-16T18-13-26Z` |

To bump: replace both tags, run `make s3-up` locally, and confirm
`make s3-test` still passes. Keep the two tags close in age - `mc` command
surface changes occasionally and mixing a very new `mc` with an older server
can break the `mc mb --ignore-existing` flag the script relies on.

## Fixtures

Regenerated by `generate_fixtures.py` on every `make s3-up`. Binary output is
deterministic (seeded PRNG), and Parquet fixtures are copied from the standard
C++ integration dataset, so a second run produces identical files and the
sha256 manifest stays stable:

| file | size | purpose |
|---|---|---|
| `hello.txt` | 16 B | HEAD + tiny-range read |
| `small.bin` | 20 KiB | bit-equal full-object read via `datasource_factory` |
| `medium.bin` | 8 MiB | multi-range reads at odd offsets |
| `parquet/*.parquet` | varies | standard TPCH Parquet fixtures reused by S3 datasource, scan-manager, split-provider, and SQL-over-S3 tests. |
| `tpch/lineitem_sf10.parquet` | ~1.5 GiB | opt-in large SQL correctness fixture generated only by `fixtures.sh --perf` / `make s3-test-large`. |

`small.bin` / `medium.bin` are opaque deterministic byte blobs, not real
parquet - the byte-equality tests in `test_s3_integration.cpp` do not invoke
a parquet reader.

The same standard fixtures are uploaded to both the HTTP and HTTPS MinIO
containers. The HTTPS path uses the generated CA bundle so `s3_ioctx` exercises
TLS verification instead of disabling certificate checks.

The S3 Parquet tests currently use `parquet/nation.parquet`, whose TPCH
contents are fixed and small enough for direct row-level assertions:
25 nations, keys 0-24, and five nations per region.

A sha256 manifest is written to `fixtures/local/MANIFEST.sha256`.

## Caveats

- MinIO signs with `us-east-1` by default; if you set `MINIO_REGION` to
  something else in the compose file, also bump `SIRIUS_TEST_S3_REGION`.
- `fixtures.sh` uses `--network=host` on Linux and `host.docker.internal` on
  macOS/Windows to let `mc` reach MinIO on the host network. If you run MinIO
  inside a non-host-network compose stack, override `SIRIUS_TEST_S3_ENDPOINT`
  to the compose-internal name and drop `--network=host`.
- When `SIRIUS_TEST_S3_*` is not set the integration tests `SUCCEED` with a
  skip message rather than failing - this is intentional so the default
  `sirius_unittest` run stays green on CI runners without docker.
- When `SIRIUS_TEST_S3_STRICT=1`, once the env/fixture preconditions are met,
  live failures such as `HEAD` or `datasource_factory::create` errors fail the
  test instead of downgrading to a skip. `make s3-test` enables this mode.
- Some parquet-backed S3 tests additionally skip when
  `parquet/nation.parquet` is missing locally. In normal repo checkouts this
  means `make s3-up` did not populate fixtures successfully.
- SQL-over-S3 tests cover `sirius_read_parquet('s3://...')` directly and the
  `gpu_execution('... read_parquet("s3://...") ...')` rewrite path.
- Large SQL-over-S3 tests are tagged `[s3][sql][large]` and hidden from the
  default Catch2 run. `make s3-test` explicitly excludes `[large]`; use
  `make s3-test-large` when you want the SF10 coverage.
- `env.sh` also exports `SIRIUS_CONFIG_FILE` pointing at `sirius.yaml` in this
  directory. It caps Super Sirius's startup GPU/host reservation at 256/128
  MiB so `require sirius` in SQL tests in this area won't OOM on GPUs that
  don't have ~90% free. The parquet-integration test spins up a bare
  `duckdb::DuckDB` and does not touch the reservation manager. If you've
  already set `SIRIUS_CONFIG_FILE` the `env.sh` assignment is a no-op.
