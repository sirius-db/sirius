How Sirius runs SQL on the GPU

Super Sirius, end to end. One idea governs everything on this page: DuckDB owns SQL and remains the executor of last resort; Sirius quietly copies the optimized logical plan, and create_plan() is the single gate — if every operator translates, the physical plan is swapped for a GPU pipeline program; if anything throws, the CPU plan runs untouched and the user never notices.

One base class, sirius_physical_operator. Blocking operators are the sink of one pipeline and the source of the next.
src/planner
15 plan builders
One generator class, 15 create_plan() overloads. Anything else throws — which is the CPU-fallback mechanism.
cuCascade
3 memory tiers
GPU, pinned host (per NUMA node), disk. Every byte lives in exactly one memory_space = (tier, device).
runtime
6 thread families
Query thread, management loop, per-GPU executors, task creator, scan manager + I/O reactors, downgrade executors.

Step 0

Why three optimizers get disabledThe pre-optimizer hook (sirius_pre_optimizer_hook) snapshots the connection's disabled-optimizer set and turns off IN_CLAUSE, COMPRESSED_MATERIALIZATION, and STATISTICS_PROPAGATION — they produce DuckDB-internal plan shapes the transparent rebind path can't execute yet. The post-hook restores the snapshot, so the connection is never permanently altered.

Registration happens once at LOAD: LoadInternal (src/sirius_extension.cpp:1877) attaches a SiriusContext to every connection (key "sirius_state"), initializes the converter registry and GPU settings, and registers the hooks:

OptimizerExtension opt_ext;
opt_ext.pre_optimize_function = sirius::transparent::sirius_pre_optimizer_hook;
opt_ext.optimize_function     = sirius::transparent::sirius_optimizer_hook;   // stores LogicalOperator::Copy()
OptimizerExtension::Register(config, std::move(opt_ext));

The gpu_execution setting is checked in exactly one helper — gpu_execution_enabled (src/transparent/sirius_optimizer_extension.cpp:34, mirrored at src/sirius_context.cpp:774) — a literal TryGetCurrentSetting("gpu_execution", …). SET gpu_execution = false and the hooks stand down.

The decisions that shape the plan

  • Hash vs. nested-loop join — at least one equality condition → HASH_JOIN (checked by are_conditions_supported() for mixed equality+inequality on disjoint columns, created with a max_build_hash_table_bytes cap); pure-inequality joins take NESTED_LOOP_JOIN when PhysicalNestedLoopJoin::IsSupported(). Convention: left = probe (streamed), right = build (materialized).
  • cuDF gaps rewritten at plan time — AVG decomposes into SUM + COUNT_VALID (finalized on-device with cudf::binary_operation); COUNT(DISTINCT) goes through COLLECT_SET; HUGEINT downcasts to BIGINT (no int128 in cuDF).
  • Filter pushdown — with FILTER_PUSHDOWN support, filters move into sirius_physical_table_scan, filter columns join projection_ids, and a residual sirius_physical_filter covers what the table function can't evaluate.
  • Projection folding — passthrough projections are elided; a final fold_adjacent_projections() + push_projection() pass composes stacked PROJECTION → PROJECTION pairs into one select list, so each batch pays one expression_evaluator stage. Folding refuses when a select-list slot is null or a non-trivial inner expression would be duplicated across outer references — and only immediate parent/child pairs fold.
  • Dynamic-filter channels — get_or_create_dynamic_filter_channel() keys a sirius_dynamic_filter_set by the DynamicTableFilterSet* pointer DuckDB plants on both the join (producer) and the scan (consumer); the channel is how a BUILD_PROBE join's build side later feeds membership filters into parquet scans.
Per-operation fallbacks are plan-time tooSome individually supported shapes still route to CPU on purpose: BIGINT SUM / ADD / SUB / MUL fall back because there's no INT128 accumulator on the GPU path — falling back prevents silent overflow, not a crash. DECIMAL SUM instead widens (32→64→128). And the reverse exists: read_parquet('s3://…') is rewritten to sirius_read_parquet (sirius_sql_rewrite.hpp), a GPU-only path with no CPU fallback at all.
04 · Pipelines

From operator tree to pipeline graph

Two passes build the executable form. First sirius_meta_pipeline::build() walks the plan — streaming operators (FILTER, PROJECTION, LIMIT) append to the current pipeline; blocking operators (HASH_JOIN, ORDER_BY, aggregates) become sinks and spawn child meta-pipelines (build side before probe side). Then sirius_pipeline_converter rewrites the graph into its final GPU form.

Sirius ≠ DuckDB hereIn DuckDB, source and sink live outside the operators list. In Sirius, finalize_pipeline_structure() pushes the sink into operators and sets source = &operators[0] — afterwards operators contains every operator, and a task's compute_task() simply calls execute() on each one, source→sink, then publish_output() calls the last one's sink(). Blocking operators are therefore the sink of one pipeline and the source of the next.

The converter (src/pipeline/sirius_pipeline_converter.cpp) runs seven phases — schedule_and_copy_pipelines → split_pipelines → wire_data_repositories → setup_pipeline_parents → finalize_pipeline_structure → link_join_partition_siblings → log_pipeline_debug_info — leaving sirius_engine::initialize_internal() a ~35-line orchestrator. The interesting work is in the rewrites:

rewrite 1TABLE_SCAN → GPU_SCAN, in place

No separate scan pipeline. The scan is rewritten to a unified sirius_gpu_scan_operator at operators[0]; insert_parquet_scan_operator() / insert_duckdb_native_scan_operator() capture the DuckDB bind data into parquet_ingestible_table_info / duckdb_native_ingestible_table_info and build the per-format gpu_ingestible via make_ingestible(). The scan is a normal pipeline source running on GPU-executor workers — scans are not a separate executor.

rewrite 2HASH_JOIN → breaker + PARTITION → CONCAT on both sides
  • A PARTITION/CONCAT pipeline pair is inserted before the join on both probe and build inputs; a pipeline breaker precedes PARTITION so the total input size is known when picking the partition count (determine_num_partitions() from hash_partition_bytes).
  • Barriers: PARTITION → CONCAT is PARTIAL (incremental); CONCAT → join is FULL, with the build side landing in the join's "build" port.
  • Probe and build PARTITIONs are sibling-linked (link_join_partition_siblings()) so both sides agree on the partition count.
rewrite 3Aggregates and TOP_N get merge stages

HASH_GROUP_BY → PARTITION → MERGE_GROUP_BY (all FULL barriers): each partition is aggregated independently, then merged. UNGROUPED_AGGREGATE → MERGE_AGGREGATE with no PARTITION (there's only one group). TOP_N → MERGE_TOP_N. The merge operators drain one whole partition per task.

rewrite 4ORDER_BY → a three-pipeline sample sort

[scan … ORDER] —PIPELINE→ [SORT_SAMPLE, SORT_PARTITION] —FULL→ [MERGE_SORT]. Each batch is locally ordered (cudf::order_by), SORT_SAMPLE overrides get_next_task_hint() to wait until it has seen enough byte-based samples to compute range boundaries, SORT_PARTITION reads them via _sample_op and range-partitions, MERGE_SORT k-way merges one partition per task (gpu_merge_impl::merge_order_by()).

Doc trivia: execution-flow.md calls this the "4-phase sort" (counting operators), physical-plan-generation.md the "3-Phase Sort" (counting pipelines — SORT_SAMPLE and SORT_PARTITION share one task). Same machinery.

rewrite 5DELIM_JOIN — correlated subqueries
  • The delim join wraps an internal join plus an embedded sirius_physical_grouped_aggregate (the distinct), both fed simultaneously by sink() pushes.
  • RIGHT variant: RHS replaced with dummy_scan; build via partition_join → CONCAT into the "build" port (breaker only if intermediates exist).
  • LEFT variant: LHS replaced with column_data_scan (never a breaker); build via a standard child meta-pipeline.

Ports and barriers — how pipelines connect

Pipelines never share operators; they share repositories. insert_repository() (src/sirius_engine.cpp) creates a cucascade::shared_data_repository keyed by (operator_id, port_id) for every sink→source edge — repositories are never placed mid-pipeline. The consuming operator sees it as a port (named "default", or "build" for a hash join's build input) with a barrier type the base get_next_task_hint() enforces:

BarrierSemanticsCanonical user
FULLDownstream waits until the entire upstream pipeline has finishedHash-join build port, merge stages
PARTIALDownstream may consume incrementally, with coordinationCONCAT after PARTITION (inner joins)
PIPELINEPure streaming — consume as producedORDER → SORT_SAMPLE edge, streaming chains

Pipeline completion (update_pipeline_status()): the source reports is_source_pipeline_finished(), all_ports_empty() holds, and tasks_created == tasks_completed — or an operator exhausts a LIMIT early.

05 · Tasks & scheduling

Data-driven task creation, reservation-gated dispatch

Nothing polls operators on a timer. Work exists only when data does: after every task, downstream consumers are offered to the task_creator, which walks the hint chain to find something actually ready to run.

task_creator — the hint chain

  • schedule(op) enqueues; manager_loop() pops and asks get_operator_for_next_task().
  • Each operator's get_next_task_hint() answers READY{producer} or WAITING_FOR_INPUT_DATA{producer} — on WAITING the creator recurses into the producer, so data flows from the deepest ready producer first.
  • The base hint checks ports in order: a FULL-barrier port requires its source pipeline finished; every port needs data. Base get_next_task_input_data() pops one batch per port.
  • pipeline.mark_task_created() is called before popping input — otherwise a pipeline can look finished mid-pop (a real race, now an invariant).
  • Scan policy: at most 2 scans scheduled at startup; continuous rescheduling on exhaustion only when the plan has a single scan.

task_scheduler + gpu_pipeline_executor

  • management_eventloop() matches two signals — executors publish device_ready, schedule() publishes task_available — and per ready device picks: (a) a dynamic-filter build-subtree task, (b) an exact preferred-device match, (c) anything else.
  • Preference-less tasks round-robin across GPUs (_no_pref_rr_counter, reset per query — the cache=table_gpu warm path depends on that reset).
  • Per-GPU executor manager loop: reserve a worker slot → send task_request → pop task → clamp the memory ask to get_max_memory() → make_reservation() → attach → acquire an exclusive CUDA stream → dispatch.
  • Worker: lock_or_prepare_batch() colocates inputs, compute_task() runs execute() on every operator, publish_output() calls the sink's sink().
  • Completion is checked before downstream scheduling — never mint tasks against destroyed operators. Errors: report_error() then drain_after_error() (stop creator → drain queues → drain executors → restart creator).
The SCHED-RR contract — multi-GPU correctness"Every operator's input batches MUST arrive on the task's reservation device." The only thing that makes batches[0]->get_memory_space() a safe alias for the target space is that prepare_for_processing() → lock_or_prepare_batch() colocated every batch — all or nothing (std::nullopt → reschedule). History: preference-less tasks used to be accidentally pinned to one GPU by unordered_map iteration order; real round-robin destroyed that accidental safety, and 11 read sites had to be audited. New operators that read get_memory_space() on a batch they didn't construct must carry an INVARIANT (SCHED-RR contract) comment (pattern: src/op/sirius_physical_concat.cpp:193), and test/cpp/operator/test_mgpu_stress.cpp guards it with 500 runs.

06 · Operators

One base class, thirty shapes

Every operator derives from sirius::op::sirius_physical_operator (src/include/op/sirius_physical_operator.hpp). The surface splits into four roles — execute, source, sink, and pipeline-build — and most operators implement only the slice they need.

…in English

  • execute — pure batch-in → batch-out on a given CUDA stream. Called on every operator of the pipeline, per task.
  • memory estimate — feeds the reservation system; defaults to 2× input bytes until pipeline_memory_history has real samples.
  • source — decides when a new task can exist (get_next_task_hint) and assembles its input (get_next_task_input_data). This is where barriers, channels, and split connectors surface.
  • sink — receives the pipeline's final batch: push into a repository port, accumulate build state, or collect results.
  • build_pipelines — the plan-time walk that decides append-vs-break (streaming vs blocking).
  • Input arrives as operator_data → pipelineable_operator_data (locked data_batches) → partitioned_operator_data (adds partition_idx).

07 · Expressions

One AST, three ways to run it

Scalar expressions have a single currency across planner, operators, and evaluator: sirius::ast::node (src/include/expression/ast/node.hpp) — a std::variant translated from DuckDB expressions once, at plan time via sirius::ast::from_duckdb(). Operators never see a DuckDB expression again.

using node = std::variant<
  reference, constant,            // leaves
  comparison, conjunction,        // predicates
  between, in_list, case_expr,    // control shapes
  cast, unary_op, coalesce,
  function_call, aggregate>;      // calls
// alternative order is ABI — append-only.
// every alternative implements cudf_ast_op_count()

expression_evaluator (src/expression_evaluator/) exposes exactly two verbs — evaluate(input) for PROJECTION and select(input) for FILTER — and dispatches per-alternative through one specialization file each (specializations/{comparison,case,cast,…}.cpp). The strategy is a session setting:

StrategyHow it runsTrade-off
MATERIALIZEOne cuDF kernel per node (unary_operation/binary_operation), intermediates materializedMost compatible, most memory traffic
AST_INTERPRET (default)Build a cudf::ast::tree, run one monolithic cudf::compute_columnOne kernel for the whole tree
AST_JITcudf::compute_column_jitJIT compile cost, best steady-state
AST breakers — the tree of treesNodes with no cuDF-AST equivalent — CASE, LIKE, SUBSTRING, non-fixed-width CAST — are materialized into columns and re-referenced from the enclosing AST subtree, producing a "tree of AST trees": maximal AST islands stitched together by materialized columns. Tiny islands aren't worth it: min_ast_size (default 2, measured via cudf_ast_op_count()) demotes them back to MATERIALIZE. String concat/|| is materialize-only (cudf::strings::concatenate with a null narep for SQL null propagation), and coalesce is iterative cudf::replace_nulls.

A separate translator, gpu_expression_translator, converts Sirius AST → standalone cuDF AST for two consumers that bypass the evaluator: MIXED_JOIN conditions and parquet reader pushdown (emitting column_name_reference nodes). It refuses — returns nullopt — on case_expr, coalesce, and VARCHAR casts.

08 · Memory & spilling

Reserve first, spill under pressure, reschedule as a last resort

cuCascade gives Sirius three tiers — GPU, pinned host (per NUMA node), disk — and every byte lives in exactly one memory_space. sirius_memory_reservation_manager installs each GPU's cuda_async_memory_resource as cuDF's device resource, so every cuDF allocation is visible to the budget. Tasks don't allocate hopefully; they reserve first.

How much to reserve? Ask history.

  • pipeline_memory_history: a 64-entry ring of {estimated, peak, output} per pipeline; estimate_peak_memory() is a log-ratio-weighted average of past peak/estimate ratios.
  • No history yet? no_history_peak_memory_estimate() — default 2× input bytes.
  • Add bytes_to_materialize_input (inputs that must be upgraded back to GPU), then clamp to get_max_memory() — the clamp kills a real livelock where an over-capacity estimate gets a partial grant while spilling demands the full size, forever.
  • OOM'd records ratchet the estimate upward (record_on_failure) so the same task asks for more next time.

Enforcement

  • A reservation_aware_resource_adaptor wraps the RMM resource: allocations beyond the grant fail gracefully instead of taking down the pool.
  • First response is not spilling but defragmentation: defragmenter_oom_policy detects pool fragmentation (reserved > used + 10× requested via cudaMemPoolGetAttribute), trims with cudaMemPoolTrimTo, retries.
  • Hard OOM raises oom_reschedule_exception carrying the intermediates and a resume operator index — up to MAX_OOM_RETRIES = 10 with 5 ms backoff, then the query dies.
  • Pinned host side: small_pinned_host_memory_resource — 64 MB blocks, 1024 per pool, NUMA-affine.

Step 0

"Downgrade" ≠ CPU fallback — don't conflate themIn Super Sirius, downgrade means data-tier demotion: the downgrade_executor (one per memory space, src/downgrade/downgrade_executor.cpp) moves data GPU→host→disk. It never routes execution to the CPU. CPU fallback is a plan-time decision (section 03: create_plan() throws, or per-op cases like BIGINT SUM). Even the top-level CLAUDE.md blurs this — the docs (memory-management.md) are the authority.

Anatomy of the downgrade executor

  • Three thread roles — a processing thread dequeues downgrade_requests sequentially; an optional monitor fires on should_downgrade_memory() and a stateless viability gate has_viable_downgrade_target() (disk always viable; GPU→host viability probed with a chunk-sized make_reservation_or_null, released immediately; otherwise back off and warn once); a bounded worker pool does the byte movement.
  • Requests are predicates, not sizes — request_downgrade(predicate) returns a future<size_t>; on a reservation shortfall the predicate is "does make_reservation_or_null(bytes_needed) succeed now?" — so spilling stops the moment the reservation fits. No over-freeing, and the monitor is never on the correctness path.
  • Candidates, lazily, in tiers — (1) idle GPU-resident batches from data repositories (convertible_data_batch_provider, partitions back-to-front), then (2) whole queued tasks pulled from the pipeline task queue (convertible_gpu_pipeline_task_provider, mutable_pop_if with RAII return). Each converts via convertible_data::convert() — atomic lock + reservation + tier conversion + rollback on failure — through the sirius_converter_registry.
  • The return trip is lazy — nothing eagerly promotes spilled data; the next task that needs it upgrades it in prepare_for_processing() → lock_or_prepare_batch(), which also enforces the SCHED-RR colocation contract.

The unit being spilled is the same unit everything else uses: cucascade::data_batch, with its three-state lock idle ↔ read_only ↔ mutable_locked. An idle shared_ptr<data_batch> grants no data access — data is reachable only through RAII lock accessors, which is exactly what makes "idle = spillable" safe. Batches can be owned (a real cudf::table) or view-backed (owning_table_view: a table_view plus a type-erased owner) — the basis of zero-copy projection passthrough.

09 · Scan & I/O

From files to GPU-resident tables

sirius_scan_manager::prepare_for_query() either matches a pinned-table cache entry or builds a split_provider per scan. A single per-query sequencer — the load_balancing_scan_batch_coalescer — then drives metadata tasks, coalesces splits up to scan_task_batch_size (512 MB default), stamps each with a preferred_device_id (round-robin), fires prefetch hints, and pushes onto each scan's split_connector.

Two ingestibles

  • Parquet — cudf::io::read_parquet over coalesced row-group slices; footer caching in metadata_store; stats-based row-group pruning (filter_row_groups_with_stats()); reader-side predicate pushdown via set_filter, decided per split.
  • DuckDB-native — custom CUDA kernels decode .duckdb segments on the GPU: gpu_decode_table() for fixed-width (UNCOMPRESSED / CONSTANT / RLE / BITPACKING / ALP), gpu_decode_strings_column() for strings (DICTIONARY / FSST / DICT_FSST) — src/cuda/scan/*.cu.
  • A non-viable native scan (unsupported codec/type, or all row groups pruned) throws before any per-segment I/O — triggering clean CPU fallback.

The I/O stack (src/io/)

  • sirius_datasource implements cudf::io::datasource; per-GPU sirius_ioctx picks a reactor by URI scheme: io_uring for local files, REST/libcurl + SigV4 for s3://, kvikio fallback.
  • In front: the pinned-memory prefetching_cache — packed atomic chunk state machine, partial-read + populate-on-read, tiered-LRU eviction, admission_control budget of 2048 in-flight chunks.
  • Multi-GPU mode is deliberately kvikio-free (enforce_sirius_datasource_for_multi_gpu()) — kvikio binds file handles to one CUDA context.

Pinned tables — the warm path

CALL pin_table('lineitem', tier => 'gpu') drives the ingestible to completion and keeps the table resident: GPU tier round-robins chunks across GPU memory spaces; host tier converts each batch to a NUMA-local host_data_representation and frees the GPU copy (peak GPU residency ≈ one batch). Cache serving is layout-identical to a fresh read — can_serve_with_columns() matches format + identity + column superset, and columns come back in materialized_column_order(). Re-pinning merges when row counts and per-chunk placement match, otherwise replaces.

Dynamic filters ride the scanA BUILD_PROBE hash join's build side publishes runtime predicates through the plan-time channel (section 03) into parquet scans: zone-map filters lowered into the reader's set_filter (off by default) and membership filters — cuco::static_set in-list or cuco::bloom_filter, chosen by L2-cache fit — applied post-decode behind an adaptive selectivity gate (on by default, enable_dynamic_filter_pushdown). Filters are always redundant with the authoritative join, so they can never change results — measured 1.65× on SF300 with 2 GPUs.
10 · Exchange & streaming

The exchange channel: bytes-bounded, handle-based, close-then-drain

The streaming layer (this branch) lets an external producer feed batches into a running pipeline — the foundation for distributed exchange. Two pieces: exec::exchange_channel (src/include/exec/exchange_channel.hpp), a bounded MPMC handoff, and the port-less STREAMING_SOURCE operator that drains it.

// can_push_unlocked — the byte bound
if (_queue.size() >= _cfg.capacity_items)
    return false;
if (_cfg.capacity_bytes == 0)
    return true;                  // unbounded bytes
if (_queue.empty())
    return true;                  // oversized-batch rule
if (_total_bytes >= _cfg.capacity_bytes)
    return false;
return h.size_bytes
    <= _cfg.capacity_bytes - _total_bytes;
// subtraction, not addition — no overflow

…in English

  • Two independent caps: items and bytes (config{capacity_items, capacity_bytes}).
  • A push is rejected if it would cross the byte bound — not merely when the queue is already over it (commit 6cb48fae).
  • Except into an empty channel: a single batch larger than the whole byte budget must still be admittable, or the stream wedges forever.
  • Comparing via subtraction avoids integer overflow on huge size_bytes.
  • API — blocking push() / non-blocking try_push() for producers; pop() / try_pop() for consumers; close(); observers closed(), empty(), size_bytes(); end-of-stream is drained() = closed() && empty() — close-then-drain, never close-and-discard.
  • Callbacks — set_on_push / set_on_pop / set_on_close. The on-close callback is what lets an empty or late-closed pipeline finish: without it, a source that went WAITING on an empty-but-open channel would never be re-scheduled after close() (commit fa01e9d4).
  • Engine-side discipline — GPU workers only ever try_pop(). A full or empty channel parks task creation (the hint goes WAITING), never a GPU worker thread.
  • Lifetime — the channel may outlive the operator, so ~sirius_physical_streaming_source clears the on-close callback it registered.
Why the channel carries handles, not ownersThe item type is exchange_batch_handle — a repository reference, not an owning shared_ptr<data_batch>. The producer must add_data_batch() into the shared_data_repository before pushing the handle. Consequence: batches queued in the channel remain accounted and idle — which means the downgrade executor can spill them under memory pressure exactly like any other repository batch. An owning channel would make queued data invisible to the memory system.

Inside the operator: get_next_task_hint() maps channel state to the task machine — non-empty → READY, open-but-empty → WAITING_FOR_INPUT_DATA, drained() → nullopt (EOS). get_next_task_input_data() resolves the popped handle through the repository into a pipelineable_operator_data; execute() is a pure pass-through; the peak-memory estimate is plain input bytes rather than the default 2×.
