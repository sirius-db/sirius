On hot host-pinned SF1000 runs, slow queries (q21, q18, q13, q1) alternate between compute-only phases (100% SM, zero H2D) and copy-only phases (~350 GB/s H2D, ~20% SM). Root cause chain: `task_scheduler::start_query` schedules only `scans.front()`; all other scans are pulled lazily by the task-creator hint chain, and the H2D for a pinned-host chunk happens inside `lock_or_prepare_batch` (HOST→GPU `convert_to`) only when the scan's `gpu_pipeline_task` executes. Cached splits sit ready in each scan's `split_connector` from query start (per-query wrapper `data_batch` over a host **slice** of the pinned chunk — safe to convert in place without touching the pin).

**Tail-first drain handling (2026-07-31, commit f1de4ed9 local on feat/scan-prefetcher):** the skip-if-draining guard was leaving the active scan's own batches to task-time upload (visible in quent as HOST-origin Preparing). Aggressiveness knobs isolated (2026-07-31): threads-only (8) and quiet/poll-only (25ms/1ms) are exact noise — prefetch threads are STARVED (2 threads keep up with all eligible work; 4x threads staged +1.4%). The 8-thread+floor-0.2 combo regressed q9 +12%, mechanism CONFIRMED at debug level = downgrade bounce: floor 0.2 lets prefetch cross the 0.8 downgrade trigger → 4 monitor evictions × ~50GB including repo intermediates → re-upload churn (retroactively explains July's "floor 0.25 slightly worse / 0.2 loses"). Task-events telemetry (quent Reserving.bytes_to_materialize) shows q9 still uploads ~138GB at task time post-tail-first. Deep-dive via data_batch InTransit events: all scan inputs exist at t=1ms (eligible from start); the big probe scan's conversions start at ~200ms (workers convoy through connectors in scan order) and cover only 50/150 batches. BUT fixing the ordering (staggered worker start offsets, +80GB staged from t≈0) was NEUTRAL (q9 1.892 vs 1.880) — third confirmation that staged-GB doesn't map to runtime. Root insight: **the scan's own 4-thread task pipeline already overlaps prepare-time uploads with compute; task-time HOST-origin uploads are mostly NOT stalls.** Tail-first's -3.1% was the schedulable remainder. Recovering more needs FEWER/FASTER bytes (pin compression, GPU-tier pinning, convert_to throughput), not more prefetching. Stagger experiment reverted (not committed).

**Converter-path findings (2026-07-31 late, via quent InTransit + code read):** (1) REAL BUG: prefetcher's batch pre-check used blocking to_read_only() → workers convoy batch-by-batch on the batch being converted (measured concurrency 1.0 with 2 workers, lock-skip counter = 0); fix = try_to_read_only. Focused q21 -3.6%, but at suite level mixed: parallel prefetch shifts contention into short scan-bound queries (q6/q12/q14/q15 flip ±5% between runs — noise band). noblock + one-worker-per-draining-connector claim left UNCOMMITTED in scan-prefetcher-perf worktree pending the converter fix. (2) Hot path convert_host_fast_to_gpu ALREADY uses cudaMemcpyBatchAsync (one call per conversion; the 1MB-loop is only in the packed converter). Its costs: pre-sync of caller stream (MEASURED NEUTRAL — prototype reverted), final sync (guards eager host-block free; needs event-deferred free to remove), and acquire_stream() from the SHARED round-robin pool inside the converter — defeats the prefetcher's dedicated streams, top suspect for the 41ms/5GB (120GB/s) per-conversion rate and thread-scaling harm. Hand to convert-audit (task chip started as separate session). Lesson (1) below refines to: never prefetch NEAR THE POP POINT of a draining connector.

Three iteration lessons that were essential: (1) NEVER prefetch an actively-draining connector — the scan's 4 task threads convert concurrently; fewer prefetch threads holding exclusive locks serialize them (q13 +5.5% until fixed). (2) A pop-count delta between 2ms sweeps misses drains with 10-40ms inter-pop gaps — need 100ms quiet-period hysteresis after the last pop (q1 +12% until fixed). (3) Use a dedicated `exclusive_stream_pool`, not `memory_space::acquire_stream()` (shared round-robin pool interleaves 5GB prefetch copies with task kernels on the same stream). Alternative (rejected as first step): eagerly scheduling scan pipelines — runs decode/filter early, fills downstream repos, and risks downgrade bounce ([[downgrade-bounce-fix]]).

**Why:** copies are glued to task execution and tasks to topology order, so copy engines idle during compute and vice versa; q21 could hide ~0.4–0.7 s of its 2.66 s hot time.

**How to apply:** evidence lives in per-iteration traces (`benchmark_results/tpch_*periter_a1/sirius/q21/nsys.2.sqlite`, 100 ms binning shows the 900–1600 ms zero-H2D window and Pipeline 38 GPU_SCAN burst at 1600–2000 ms). Key files: `src/pipeline/task_scheduler.cpp` (start_query), `src/creator/task_creator.cpp` (hint chain), `src/include/pipeline/batch_lock_utils.hpp` (H2D site), `src/scan_manager/sirius_scan_manager.cpp:96` (cached_databatch_provider slice), `src/scan_manager/split_connector.{hpp,cpp}`.

**Three-agent follow-up campaign (2026-07-17) — net conclusion: the base prefetcher captured ~all available overlap on GB300; remaining q21 time is memory-capacity- and sizing-bound, not scheduling-bound.** (a) Priority-aware prefetch (branch approach3-priority-prefetch, SIRIUS_SCAN_PREFETCH_PRIORITY=1): ±0.15% = noise, because the 0.4 floor rarely binds on this HBM; strict lookahead=0 has a reproducible q12 +7% idle-worker trap — never ship without lookahead≥1; revisit on smaller-HBM GPUs. (b) Downgrade-eligible prefetched batches (branch approach2-downgrade-eligible, commit ea8dc891): candidate-provider hook walked as tier-0 before repos, tail-first eviction + per-query blacklist against bounce; works and is FREE at floor 0.4, but lower floors LOSE (0.2 → +1.9%): the 0.8/0.6 downgrade hysteresis evicts ~55GB per episode, cancelling the extra staging. **Worth merging as robustness (protects hot state under pressure), keep floor 0.4.** (c) Incremental scan→PARTITION preset — tested 2026-07-17, NO WIN (branch approach1-partition-incremental, commit a22cef54).** Hypothesis "preset the adaptive partition count from the pinned entry's known size, relax scan→PARTITION FULL→PARTIAL" was implemented (env `SIRIUS_PARTITION_INCREMENTAL=1`) and is correct (results byte-identical, presets fire) but perf is noise: SF1000 hot subset q1/9/13/18/21 = prefetch 8.155s vs prefetch+incr 8.200s; no-prefetch 8.899s vs incr-only 8.879s. Two reasons: (1) **q21's big lineitem scans (l2=op 116, l3=op 127) feed PARTIAL probe partitions whose sizing driver is the build side fed by the RIGHT_DELIM_JOIN distinct chain (MERGE_GROUP_BY)** — the count is genuinely runtime-dependent, presetting from scan size is not legal there; q21's only scan-fed FULL build partitions are nation (n_name filter) and orders (o_orderstatus filter) — filtered ⇒ size not exact ⇒ ineligible. (2) Where it does fire (q9 orders 18.4GB build scan, q18 customer 4.5GB), the prefetcher already hides the H2D window. Follow-ups if revisited: upper-bound sizing for filtered scans (count from unfiltered bytes — valid, just more partitions), or decoupling probe-partition start from sibling sizing (deep change to PARTITION pair negotiation in src/op/sirius_physical_partition.cpp).
