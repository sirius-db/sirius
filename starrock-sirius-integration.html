04 · Your operators

Streaming source #836 & streaming sink #837

Fragment boundaries become a streaming source at the bottom and a streaming sink at the top. Both are ordinary sirius_physical_operator subclasses — not a separate subsystem.

Streaming source — #836 (build first)

  • Used only for exchange — when a fragment's input comes from another compute node.
  • A leaf fragment reading parquet uses the normal existing source (DUCKDB_SCAN / GPU_PARQUET_SCAN) — it may still have a streaming sink. A trivial single-node SELECT * has neither.
  • Multi-shot: publishes a task each time a batch arrives on its input channel, until close_input — unlike today's one-shot scan.

Streaming sink — #837 (build second)

  • Final operator of its pipeline; runs inside a normal gpu_pipeline_task on the existing gpu_pipeline_executor — like RESULT_COLLECTOR or MERGE_GROUP_BY today. No dedicated thread pool; nixl's own threads live in the wrapper.
  • Incremental: pushes each output batch per sink() call instead of materializing a ColumnDataCollection (as sirius_physical_materialized_collector does today).
  • Sink output stays on the GPU (cuCascade data repository), so Nixl can pick the fast path when moving GPU-resident data between nodes.
  • Partitioned variant: per-destination output channels (one slow receiver cannot head-of-line-block the rest) + bounded coalescing of small slices up to a size/time threshold — otherwise you ship a flood of tiny RDMA transfers. Coalescing state is bounded, accounted, repository-visible.

The data unit and why channels don't own it

shared_ptr<cucascade::data_batch> wrapping a cudf::table, guarded by a 3-state lock (idle / read_only / mutable_locked). Channels carry handles (repository batch-ids), not owning shared_ptrs — the channel is deliberately not an owner, so queued batches stay accounted/spillable via the shared_data_repository and use_count() reflects only real owners. That is what makes the sink's zero-copy steal possible.

Partition-hash parity — correctness-critical

The sink must reproduce StarRocks' hash bit-exactly, per partition type (be/src/exec/pipeline/exchange/exchange_sink_operator.cpp). Getting this wrong silently corrupts shuffle joins and aggregations. Validate against test/sql/test_exchange_hash_function.

Partition typeHashNotes
HASH_PARTITIONEDfnv_hash (v0, default) or xxh3_hash (v1)Dispatched on exchange_hash_function_version. Only regime where deviating is ever safe — and only with all-Sirius CNs and no native hash-bucketed tables.

Distributed GROUP BY shape

  • HASH_GROUP_BY (partial) → partitioned streaming sink — the shuffle is the partition, no separate local PARTITION → nixl → streaming source → MERGE_AGGREGATE (final).
  • No StarRocks-specific merge operator: both ends are Sirius, so shipped partial-aggregate state is Sirius's own format; nixl routes opaque bytes.
  • Sirius does not choose the phasing — the FE plans the partial/final fragment structure.

Ordering caveat

  • Order is not preserved — incremental emission + coalescing reorder rows.
  • v1 targets order-insensitive exchanges only.
  • A merging exchange (ORDER BY / top-N) is future work (open Q14).

Edge-triggered re-arming — know the raceTask creation is triggered by schedule(op), so when the wrapper pull()s a batch it must re-schedule the sink. A narrow race remains; the fallback is that a sink finding the channel full keeps its result idle in the repository (still spillable) and yields its worker rather than blocking it.

Two existing throttles compose with this: GPU memory reservations block when the budget is exhausted, and the GPU executor dispatches through a bounded worker pool. For the root fragment, the output channels are the query result — drained and returned to the FE via fetch_data. Routing everywhere is by stream id.

06 · Transport

Nixl — how bytes actually move

A high-level, agent-based, point-to-point GPU data-transfer API from the Dynamo project. You hand it data; it picks the fastest path: cudaMemcpy intra-GPU, NVLink-class intra-box, UCX (among others) remote. The appeal: plan fragments already encode partition routing, so the CN just tells Nixl where partitions go — no custom transport logic.

Transfer protocol (this is a sequence)

  1. Startup: each CN creates one agent and computes local metadata (get_local_md).
  2. First contact: first transfer to a new peer exchanges agent metadata over the side-channel, cached per peer (invalidated on restart).
  3. Per transfer: buffer metadata via NixlMetadataService::exchange_metadata.
  4. Receiver leases a pre-registered staging buffer (bump-allocated, RAII lease).
  5. Sender issues create_xfer_req + post_xfer_req, polls get_xfer_status.
  6. transfer_complete handshake.
  7. Receiver wraps the bytes as a repository-registered data_batch and enqueues a handle on the input channel.

Path preference

  • GPUDirect RDMA GPU staging is preferred.
  • Host staging is a deployment/tier choice — not a failure path.
  • bRPC/CPU is the true last-resort fallback.
  • Same-CN exchange skips the network entirely — in-process channel hand-off, no serialization (StarRocks' local-exchange equivalent).

Why Nixl, not UCXX directly (sync decision)

  • Good abstraction for plan-fragment-encoded routing/partitioning.
  • Built-in side channel for backpressure/metadata; out-of-the-box spilling to host memory or disk.
  • Nixl wraps UCXX internally — swapping to UCXX later fits the same architecture.
  • Heavy internal investment via Dynamo; NV Research wants a Dynamo-powered distributed query engine with Sirius underneath.
  • Direct UCXX would take multiple weeks — Rod and William cited a long history of painful UCX integrations at BlazingDB.
07 · Resource management #840

One GPU, two tenants, one budget

The wrapper (nixl staging/receive buffers) and Sirius (compute + spill) share one physical GPU. Three budget models were considered; the recommendation is option A — a shared cuCascade memory_reservation_manager, owned by the wrapper, borrowed by Sirius.

Why option A winsIt is the only option where in/out exchange batches can be spill candidates alongside compute via the existing downgrade_executor — whose sweep walks registered shared_data_repository batches and filters on idle state, not origin.

Two required changes

  • sirius_context borrows the wrapper's manager instead of constructing its own (sirius_context::sirius_context in src/sirius_context.cpp).
  • Exchange memory made visible: queued batches held as repository-registered data_batches, and the nixl staging arena reserved once against the budget at startup. Per-transfer leases are sub-allocations — no further reservation; only the cuMemAlloc-and-register fallback needs fresh reservations.

Four constraints for all-to-all exchange

  • Lease-aware spill — copying a staging-backed batch out returns the lease.
  • Reserved receive-staging floor.
  • Reserved copy-out credit.
  • Reserved send-copy credit — the last two prevent "must free memory to send, but the send needs memory" deadlocks.
The sync already settled the v1 directionAgreed simplest first version: keep the queue inside Sirius so the existing downgrade executor handles memory pressure, accepting some leaking of dependency types initially. Option A is that agreement, formalized. William's pluggable-downgrade proposal (register external data repositories with a priority) is the future direction, not v1. Also deferred: exposing resource info on the streaming session so the receiving side can make backpressure and host-memory/disk placement decisions — fold this into your #839/#840 config scoping.

09 · Hands-on

From clone to end-to-end verification

Eight steps. Run all Pixi tasks from experimental/starrocks/ — it has its own Pixi workspace, separate from the main repo's manifest, and running elsewhere picks up the wrong one.

Step 0Orient yourself in the layout

Four Pixi environments: fe (JDK 17 + Maven), cn (Rust), client (mysql CLI), engine (CUDA/cudf/rmm/duckdb). The build chain:

  1. Build DuckDB, then Sirius on top → a DuckDB CLI with Sirius preloaded and sirius.duckdb_extension (an .so). A distributable CPack extension exists but isn't needed locally.
  2. sirius_ffi.hpp / sirius_ffi.cpp add symbols to that .so so external code can call into Sirius (today: just the unique_ptr wrapper around the DuckDB Sirius context).
  3. Rust crates: sirius-sys (low-level cxx bindings) → sirius (safe API: SiriusContext::new() / from_config_file(), RAII teardown). A telemetry crate exists — ignore it.
  4. StarRocks CN = plain cargo project; FE = plain Maven/Java project. sccache speeds up rebuilds after the first.

Long-term direction: DuckDB is still tightly integrated into Sirius, but decoupling from DuckDB-internal APIs has begun — the goal is for the DuckDB extension to become a thin shim around the Sirius library, mirroring how StarRocks embeds Sirius. The embedded telemetry/profiling component (single-node, Sirius-only, no StarRocks integration yet) is out of scope for now.

10 · Why this matters

Goals, timeline, staffing

North star

  • Get Alibaba to buy in — they told the team to do StarRocks instead of making Doris faster. Work happens on dev, so every Sirius improvement lands in the StarRocks path too.
  • Other interested customers: Trend Micro and RM Labs (blockchain analysis). Both already use StarRocks — currently the fastest distributed open-source database; performance-focused users are the natural target (analogous to DuckDB adoption).

First internal goal

  • Execute all of TPC-H across multiple compute nodes — possibly single-node multi-GPU first; real target: multi-node on an NVL72 — with StarRocks as the driver, correctly.
  • Only then measure speedup and go back to Alibaba. No benchmark baseline yet; implied baseline is standalone CPU StarRocks.
  • Sync-era ETA (under Rod's "healthy pressure"): ~1–2 weeks to first queries — since achieved: the #1024 stack runs a single fragment end to end. ~1 more week to a working exchange — still outstanding; this is the clock your #836/#837 work sits on. Then iterate on operators and performance.
  • Deployment config (sync-era): single-node multi-GPU, configurable as one compute node per GPU or per node — tuned experimentally.
  • Staffing / bus factor: Matthijs was the sole engineer; you were added as the second full-time engineer specifically to reduce that risk (plus time-zone alignment). The team is deliberately not swarming more people — TPC-H benchmark deadlines and benchmark politics take priority until one "home run" lands. Akhil is absorbing Sirius work from William.
  • Sequencing philosophy: "Make it work first, then make it fast." Don’t optimize early — conceptually nothing should make this much slower than direct Sirius execution except the exchange, and Nixl handles path selection there. Always keep it demoable — if Alibaba wants to try it early, it should just work.
