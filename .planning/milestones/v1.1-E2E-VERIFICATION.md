# Milestone v1.1 End-to-End Multi-GPU Verification

## Verdict

**GAP CONFIRMED.** A minimal SQL query (`SELECT count(*) FROM nation`) distributes successfully across both GPUs at v1.1 HEAD — scan batches route to GPU 0 and pipeline tasks dispatch to GPU 1. However, the moment SQL has non-trivial shape (filter + sort, aggregation, join — i.e. every real TPC-H query exercised here), execution fails with `cuda_memcpy.cu:42 cudaErrorInvalidValue` during `pipelineable_operator_data::prepare_for_processing`. This reproduces in both the duckdb CLI driver and the Catch2 integration test binary — provided `num_gpus: 2` is actually applied.

The previously claimed **979/979 unit-tests pass on N=2** in `07-04-VALIDATION.md` was **not a full 2-GPU exercise**: `test/cpp/integration/test_gpu_execution_tpch.cpp:56` and `test/cpp/integration/test_gpu_execution_multi_format.cpp:60` both `setenv("SIRIUS_CONFIG_FILE", integration.yaml, 1)` in their fixture, and `integration.yaml` carries `num_gpus: 1`. So all parquet/join/groupby integration tests ran effectively single-GPU. Only tests that build their own 2-GPU `sirius_config` in-memory (MGPU-04 registration, MGPU-07 downgrade distribution) actually exercised two GPUs — and those exercise converters / distribution logic in isolation, not the scan→compute pipeline.

This is a **real v1.2 fix**, not a v1.1 amendment. The code on HEAD shipped as `v1.1` (tag `076b587`) with this gap. The gap is documented here for transparency; the milestone status should remain "v1.1 shipped, v1.2 needs cross-device SQL fix".

## 7. Root-cause signal (for v1.2 planners)

The failure path:

```
SiriusExecuteQuery
  → gpu_pipeline_executor::run_task
    → gpu_pipeline_task::prepare_for_processing         [src/pipeline/gpu_pipeline_task.cpp:339]
      → pipelineable_operator_data::prepare_for_processing  [src/op/sirius_physical_operator.cpp:59]
        → pipeline::lock_or_prepare_batch                    (cucascade entry)
          → ... → cudf::cuda_memcpy.cu:42  cudaErrorInvalidValue
```

Observations:
- Error is thrown from cucascade/cudf's host↔device or device↔device copy utility, not from the Sirius P2P converter override
- The P2P override (at `src/data/sirius_p2p_converter.cpp`) runs successfully at `initialize()` and is registered; but real SQL pipelines don't reach it — the failure happens earlier, inside `lock_or_prepare_batch` when data scanned on one device has to be prepared for a pipeline task on another device
- This is the same error signature Phase 4 RESEARCH documented as "Phase-4-deferred failure mode" (`reduce_by_key cudaErrorIllegalAddress / cudaErrorInvalidValue` in cudf's cuda_memcpy utility) — Phase 7 claimed to have resolved it via the override, but the resolution only covers the **converter-level** round-trip (GPU0 → GPU1 → GPU0 explicit conversions), not the **pipelineable_operator_data::prepare** path that real SQL takes

This is the precise v1.2 work: make `lock_or_prepare_batch` stream-correct across devices, OR force the scheduler to keep scan and pipeline tasks on the same device, OR add a same-device-preference constraint on `preferred_device_id` when the source data is already on a different device.

The instrumentation added in `fd24174` makes this debuggable in production — SREs can grep for `[mgpu-audit]` in any sirius log and see the routing decision before the failure.

## 8. Why the milestone audit missed this

`v1.1-MILESTONE-AUDIT.md` claimed:
> **Full unit-test suite:** 979/979 pass (78,789,847+ assertions) as of Plan 07-04 close.

And `07-04-VALIDATION.md` claimed:
> `Exit code: 0 | Duration: 220.4s` for `mcp__project-commands__run_command unit-tests` — `979/979 PASS`.

Both statements are technically true, but the audit chain did not catch that:

1. `mcp__project-commands__run_command unit-tests` uses whatever `sirius.yaml` the default search resolves to, which (since neither `$HOME/.sirius/sirius.yaml` nor project-root `sirius.yaml` existed on HEAD) runs against no user config. Most tests provide their own configs (many yaml files under `test/cpp/scan/`, `test/cpp/integration/`, etc.).
2. The TPC-H / parquet / join integration tests (`test_gpu_execution_tpch.cpp`, `test_gpu_execution_multi_format.cpp`) override SIRIUS_CONFIG_FILE inside their fixtures to point at `test/cpp/integration/integration.yaml`, which carries `num_gpus: 1` on HEAD.
3. Only tests that build their own in-memory 2-GPU `sirius_config` (MGPU-04 registration gate, MGPU-06 hidden round-trip, MGPU-07 asymmetric-memory downgrade test, `test_gpu_execution_locality.cpp` adaptive-scan test) actually ran against 2 GPUs.
4. None of those tests exercise the `pipelineable_operator_data::prepare_for_processing` → `lock_or_prepare_batch` → cudf cross-device copy path with a real SQL shape that crosses device boundaries.

So the test suite effectively validates:
- Topology + P2P + io_backend init at 2-GPU (MGPU-01..03, MGPU-06 infra) — ✅
- Converter registration + in-isolation round-trip (MGPU-04) — ✅
- Scan-executor's memory-proportional GPU selection in isolation (MGPU-07) — ✅
- Real TPC-H SQL end-to-end on 2 GPUs — **never covered**

This is the gap this verification pass identified.

## 9. What TO carry forward

### Into v1.2 planning
- **REQ-CANDIDATE:** "Real TPC-H SF1 SQL runs end-to-end on `num_gpus: 2` config with correct results"
  - Acceptance: at least Q1 + Q3 + Q6 + Q12 + Q14 all pass via `call gpu_execution(...)` on 2-GPU config
  - Acceptance: `[mgpu-audit] pipeline_task` + `[mgpu-audit] scan_batch` counts both > 0 across the run
  - Acceptance: result correctness byte-match against `num_gpus: 1` run
- **TECH-DEBT:** `lock_or_prepare_batch` / `pipelineable_operator_data::prepare_for_processing` cross-device failure mode — investigate whether the pack/copy is issuing on a device other than the owning device; match the pattern the Sirius-side P2P converter override already uses (pack on source stream under source-device RAII, copy on target stream)
- **TEST HARNESS:** make `test_gpu_execution_tpch.cpp` able to parameterize `num_gpus: {1, 2}` — e.g. extend the `sirius_config_env_guard` fixture to look for a `SIRIUS_TEST_NUM_GPUS` env var (or equivalent) and swap the integration.yaml copy it loads accordingly. Then extend the MCP `unit-tests` command to run the suite twice, once per `num_gpus` value. This is the minimal harness change that would have caught this gap in Phase 7.

### Into v1.1 tech-debt record
The v1.1 milestone audit's `tech_debt` list should be extended with the cross-device SQL execution item. The milestone still shipped (tag `076b587` stands), but the shipped artifact has a known limitation: `num_gpus: 2` config works for converter infrastructure but **does not work for real SQL queries** beyond trivial `COUNT(*)`.
