    1. **Heading**: `## Per-task-device contract under SCHED-RR`

    2. **Why it exists** (~3 paragraphs):
       - Pre-Phase-14 history: `_gpu_executors` was a `std::unordered_map`, `begin()->first` was hash-bucket-ordered, every preference-less source-pipeline task piled onto the same GPU. "Default GPU is begin()" was the implicit contract.
       - Phase 14 SCHED-RR change: `std::map` for deterministic ordering + `_no_pref_rr_counter` for atomic round-robin distribution. Source-pipeline tasks now genuinely land on multiple GPUs.
       - The hazard this exposes: operators that read `valid_batches[0]->get_memory_space()` as the authoritative target memory space were accidentally safe pre-Phase-14 (only one GPU was in play). Under SCHED-RR they could silently get wrong results if the contract isn't enforced upstream.

    3. **The contract** (formal statement, blockquote):
       > Every operator's input batches MUST arrive on the task's reservation device. Operators MUST NOT use `batches[0]->get_memory_space()` as the authoritative target memory space; that read is acceptable only as an alias for `target_space` after `prepare_for_processing` has run.

    4. **How the contract is enforced** (~4 paragraphs with code quotes):
       - `gpu_pipeline_task::execute_pipeline_task_round` at `src/pipeline/gpu_pipeline_task.cpp:310-349` reads `target_space` from the task's reservation.
       - It calls `local_state._input_data->prepare_for_processing(target_space, stream)` (line 332).
       - `pipelineable_operator_data::prepare_for_processing` (`src/op/sirius_physical_operator.cpp:37-84`) iterates each batch and calls `pipeline::lock_or_prepare_batch(batch, target_space, stream)`.
       - `lock_or_prepare_batch` (`src/include/pipeline/batch_lock_utils.hpp:48-126`) locks the batch on `target_space` if already there, or calls `batch->convert_to<gpu_table_representation>(registry, target_space, stream)` if not.
       - **Postcondition:** after prepare_for_processing returns, every batch in `_input_data->_data_batches` is on `target_space`. Therefore `batches[0]->get_memory_space() == target_space`.

       Quote each of the four files at the relevant lines (not the whole function — just the 3-5 critical lines with `file:line` anchors).

    5. **The SCHED-RR distribution policy** (~3 paragraphs with code quotes):
       - `_gpu_executors` is `std::map<int, std::unique_ptr<gpu_pipeline_executor>>` — deterministic ascending-by-device-id iteration. Quote `src/include/pipeline/task_scheduler.hpp:204-208`.
       - `_no_pref_rr_counter` is `std::atomic<size_t>{0}`. Reset in `prepare_for_query` (line 160). Fetch-add in `management_eventloop` (line 260) gated on `!have_pref && _gpu_executors.size() > 1` so 1-GPU configs and preference-bearing tasks (SCHED-01/02/04 locality) are untouched. Quote both lines.
       - Per-query reset rationale: required for `cache=table_gpu` warm-path correctness — without it, iteration N+1 of the same query would dispatch preference-less source tasks to a different GPU than iteration N, causing cache miss. Reference Phase 13 follow-up #17 scale-up test as the regression gate.

    6. **Migration note** (~1 paragraph, BOLD callout):
       > **Migration note (Phase 14):** the pre-Phase-14 "default GPU is `_gpu_executors.begin()->first`" behavior is gone. Any operator that hardcodes single-GPU assumptions, defaults to GPU 0, or uses `batches[0]->get_memory_space()` without going through the lock protocol upstream is now WRONG under SCHED-RR distribution. Phase 15 (cross-GPU operator-colocation audit) verifies all 11 known sites; new operators MUST follow the same pattern.

    7. **Empirical evidence** (~1 paragraph):
       - Phase 14 ship-validation: `[mgpu]` 12/13 PASS, `[TPC-H][parquet]` 22/22 PASS, `[integration][TPC-H]` 48/48 PASS — corroborates that the contract holds for all currently-shipping operators.
       - Phase 15 audit: see `.planning/phases/15-mgpu-operator-colocation-audit/15-AUDIT-LOG.md` for per-site classification of the 11 sites verified during Wave 1.
       - Phase 15 stress test: `test/cpp/operator/test_mgpu_stress.cpp` exercises the contract under arbitrary `_no_pref_rr_counter` starting offsets (catches hash-bucket-order-dependent bugs that a counter-always-starts-at-0 test would mask).

    8. **For new operator authors** (~1 paragraph):
       - When writing a new sirius_physical_operator subclass that reads memory_space from any batch, add an INVARIANT comment matching the format in `src/op/sirius_physical_concat.cpp:193`:
         ```cpp
         // INVARIANT (SCHED-RR contract): all input batches arrive on target_space
         // via gpu_pipeline_task::execute_pipeline_task_round ->
         // pipelineable_operator_data::prepare_for_processing -> lock_or_prepare_batch.
         ```
       - This makes the upstream-protection assumption explicit and reviewable. The comment is mandatory for any code touching `get_memory_space()` on a batch the operator did not itself construct.
