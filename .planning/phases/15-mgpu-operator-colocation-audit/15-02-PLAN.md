<objective>
Add a test-only setter on `task_scheduler` for injecting initial values into `_no_pref_rr_counter`, then build a stress test that varies the counter's starting offset across 100 iterations and runs 5 pre-bound representative [mgpu] tests at each offset, asserting CPU baseline match. Catches hash-bucket-order-dependent bugs and any latent off-by-one in the SCHED-RR distribution path that could be masked when the counter always starts at 0. Capture the verbatim MCP run output to a log file so the verify gate is BEHAVIORAL (the test was actually executed and passed), not just structural (the test file exists).

Purpose: 15-CONTEXT.md acceptance criterion 2 — "New `mgpu_stress_test` runs 100 iterations × all [mgpu] tests without correctness divergence vs CPU baseline."

**Spec deviation (documented):** the verbatim "100 iterations × all 13 [mgpu] tests" is ~1300 runs at ~5s/run = ~108 minutes — over the project's 60-min MCP budget. Planner picks **100 iterations × 5 representative tests = 500 runs at ~5s/run = ~42 min** which fits inside a 60-min budget. Rationale: the audit sites in Plan 15-01 cluster on a small set of operator types (concat, top_n, ungrouped_aggregate, order/sort, hash_join). Coverage of those 5 across 100 distinct counter offsets gives strictly more offset-rotation per audit site than '100 iterations × 13 tests' would, since most of the 13 tests don't exercise audit sites. The 5 tests are pre-bound by exact Catch2 case name in the kQueries array below — the executor does not "discover" them at runtime.

**Why warm-up is infeasible (planner-decided, no decision branch in plan):** `prepare_for_query` resets `_no_pref_rr_counter` to 0 at the start of EVERY query (verified in 14-01 SUMMARY line 138: "Per-query reset in prepare_for_query: Required for cache=table_gpu correctness ... iteration N+1 must dispatch the same preference-less task to the same GPU as iteration N"). This means any warm-up via no-op queries cannot persist counter state across query iterations — the next real query's `prepare_for_query` clobbers the counter. Therefore the SETTER is the only viable approach. The setter must be invoked AFTER `prepare_for_query` runs but BEFORE the first task dispatch hits `management_eventloop`'s round-robin block.
