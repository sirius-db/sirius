From `src/pipeline/gpu_pipeline_task.cpp` (lines 310-349) — the contract enforcement point:
```cpp
auto reservation         = local_state.release_reservation();
const auto* requested_memory_space =
  reservation != nullptr ? &reservation->get_memory_space() : nullptr;
// ...
handles_opt =
  local_state._input_data.get()->prepare_for_processing(requested_memory_space, stream);
// ...
// AFTER THIS POINT: every batch in local_state._input_data->_data_batches
// is on requested_memory_space, the task's reservation device.
```

**Implication of these three quotes for the audit:**

If an operator's `execute()` is called from `gpu_pipeline_task::execute_pipeline_task_round` AFTER line 332 above, and its input is the `_input_data` that was just `prepare_for_processing`-ed, then `batches[0]->get_memory_space()` is a SAFE alias for `target_space`. The audit task is to trace each of the 11 sites' input data construction back to a `pipelineable_operator_data` instance that goes through this path. If yes -> SAFE. If no (e.g., the site reads batches off a port directly, or a data-repository pull bypasses the lock) -> NEEDS-PATCH; surface upward.

From `src/include/pipeline/task_scheduler.hpp` (lines 204-208) — Phase 14 SCHED-RR:
```cpp
/// device_id -> GPU executor. std::map (not unordered_map) so iteration
/// order is deterministic (ascending by device_id) — keeps preference-less
/// task dispatch reproducible across runs.
std::map<int, std::unique_ptr<gpu_pipeline_executor>> _gpu_executors;
std::atomic<size_t> _no_pref_rr_counter{0};
```

This is the reason Phase 15 is needed: with `_no_pref_rr_counter`, source-pipeline tasks now genuinely land on multiple GPUs. Without it, the `valid_batches[0]->get_memory_space()` pattern was accidentally safe because every preference-less task piled onto `begin()->first`.
