<objective>
Add data-locality-aware GPU selection to the task creation and dispatch flow.

Purpose: Today management_eventloop dispatches tasks to whichever GPU sends a task_request (pull model). This plan changes it so tasks are routed to the GPU where their input data resides, using the reservation attempt as the routing mechanism. This is the core scheduling change that makes multi-GPU execution performant.

Output: task_creator computes preferred_device_id per task, management_eventloop routes to preferred GPU executor, tasks execute where data lives.
</objective>

     ```cpp
     // Compute preferred GPU based on data locality
     std::optional<int> preferred_device_id;
     if (input_data && !input_data->get_data_batches().empty()) {
       std::unordered_map<int, size_t> gpu_bytes;
       std::unordered_map<int, size_t> host_bytes;
       for (const auto& batch : input_data->get_data_batches()) {
         auto* space = batch->get_memory_space();
         if (!space || !batch->get_data()) continue;
         auto size = batch->get_data()->get_size_in_bytes();
         if (space->get_tier() == cucascade::memory::Tier::GPU) {
           gpu_bytes[space->get_device_id()] += size;
         } else if (space->get_tier() == cucascade::memory::Tier::HOST) {
           host_bytes[space->get_device_id()] += size;
         }
       }
       if (!gpu_bytes.empty()) {
         // SCHED-01: Route to GPU with most data by bytes
         preferred_device_id = std::max_element(
           gpu_bytes.begin(), gpu_bytes.end(),
           [](const auto& a, const auto& b) { return a.second < b.second; }
         )->first;
       } else if (!host_bytes.empty() && !_numa_to_gpu.empty()) {
         // SCHED-02: No GPU data, route to GPU on same NUMA as host data
         auto top_host = std::max_element(
           host_bytes.begin(), host_bytes.end(),
           [](const auto& a, const auto& b) { return a.second < b.second; }
         )->first;
         auto it = _numa_to_gpu.find(top_host);
         if (it != _numa_to_gpu.end()) {
           preferred_device_id = it->second;
         }
       }
     }
     if (preferred_device_id.has_value()) {
       local_state->set_preferred_device_id(preferred_device_id.value());
     }
     ```

1. Modify `pipeline_executor::management_eventloop()` in pipeline_executor.cpp.

   **Current flow (lines 207-224):**
   - Wait for task_request (GPU says "I'm ready")
   - Pop task from queue
   - Dispatch to the GPU that requested

   **New flow (reservation-as-routing per user decision "single shared queue, reservation attempt IS the routing"):**
   - Pop task from _task_queue (task-first, not request-first)
   - Read task's preferred_device_id
   - Dispatch to _gpu_executors.at(preferred_device_id)
   - Fallback: if preferred not set or not found, use first available GPU executor

   ```cpp
   void pipeline_executor::management_eventloop()
   {
     while (_running.load()) {
       // Task-first: pop the next task to dispatch
       auto task = _task_queue.pop();
       if (task == nullptr) {
         SIRIUS_LOG_INFO("Task queue closed, exiting management event loop.");
         break;
       }

       // Determine target GPU from task's data locality preference
       int target_device_id = _gpu_executors.begin()->first;  // default: first GPU
       if (auto* gpu_task = dynamic_cast<pipeline::gpu_pipeline_task*>(task.get())) {
         auto pref = gpu_task->get_preferred_device_id();
         if (pref.has_value() && _gpu_executors.count(pref.value())) {
           target_device_id = pref.value();
         }
       }

       SIRIUS_LOG_DEBUG("management_eventloop: routing task to GPU {}", target_device_id);
       _gpu_executors.at(target_device_id)->schedule(std::move(task));
     }
   }
   ```

   **Critical change:** The management_eventloop no longer waits on _task_request_channel. This is the shift from pull model to push model. The capacity control now happens in gpu_pipeline_executor::manager_loop() via bounded_pool->reserve().

2. Modify `gpu_pipeline_executor::manager_loop()` in gpu_pipeline_executor.cpp to remove the task_request sending.

   - Make reservation on own _memory_space
   - Dispatch

   **New flow:**
   - Reserve slot in bounded_pool (keep -- this is capacity control)
   - Remove the _task_request_publisher.send() call entirely (no more pull signal)
   - Pop task from own _task_queue (blocks until management_eventloop pushes)
   - Make reservation on own _memory_space (keep -- this is reservation-as-routing)
   - Dispatch (keep)

   Note: The _task_request_publisher member can remain for now (scan executor still uses it). Only the GPU pipeline executor stops sending task_requests.

3. Handle the scan task path. In the current management_eventloop, scan tasks are handled via `if (!request->is_scan)` check. With the new flow, scan tasks go through a different path. The scan executor (`duckdb_scan_executor`) has its own queue and manager_loop -- scan tasks are scheduled directly to it. Verify that `pipeline_executor::schedule()` already routes scan tasks separately:

   Check `pipeline_executor::schedule()` method. If it pushes ALL tasks (including scans) to `_task_queue`, then the management_eventloop change needs to also handle scan routing. If scans go to a separate path, no change needed.

So management_eventloop should NOT see scan tasks. The `!request->is_scan` check was about task_requests, not tasks. With the new push model, all tasks in _task_queue are GPU pipeline tasks.

The publisher side in gpu_pipeline_executor::manager_loop() should also be removed (step 2 above). The scan executor still uses its own task_request_publisher to signal scan readiness -- this is a different mechanism and should be kept.

5. **SCHED-03 compliance:** With the new flow, when all GPUs are at capacity (bounded_pool full), tasks queue up in the gpu_pipeline_executor's internal _task_queue. Since management_eventloop routes to the preferred GPU, the task naturally waits on its preferred GPU. When the preferred GPU's bounded_pool has no slots, `_task_queue.pop()` in manager_loop blocks in the NEXT iteration after the slot is reserved. Actually, the gpu_pipeline_executor::schedule() pushes to its _task_queue, and manager_loop does `_bounded_pool->reserve()` THEN `_task_queue.pop()`. So if bounded_pool is full, manager_loop blocks on reserve(). Tasks accumulate in _task_queue. This satisfies "wait on preferred GPU if no GPU can reserve" because the task was already routed to the preferred GPU by management_eventloop.

   The "try other GPUs" fallback from SCHED-03 is NOT implemented in this plan -- the task goes to the preferred GPU and waits there. This is acceptable for the initial implementation: the research notes that `any_memory_space_in_tier_with_preference` handles fallback at the reservation level, but the current architecture doesn't easily support re-routing a task after it's been pushed to a gpu_executor's queue. The "try preferred, wait if all fail" semantic is satisfied because the preferred GPU eventually frees memory (via downgrade_executor).
