<objective>
Fix Bug 1 from 08-08-DIAGNOSIS.md (hypothesis E): record batch→GPU affinity at the same instant `select_target_gpu()` emits its `[mgpu-audit]` log, and keep the map query-bounded. This gives the codebase an authoritative, atomic batch→GPU record that future lookups (and the AUDIT disjointedness REQUIRE in Plan 09-03) can rely on.

Per RESEARCH.md Q5: batches assigned lazily during `compute_task` cannot be pre-mapped at dispatch time, so the minimum-viable fix is to (a) CO-LOCATE affinity recording with the `_scan_round_robin` counter increment inside `select_target_gpu()` (same point that produces the `batch_id=K` in the audit log), and (b) keep the map bounded by resetting it alongside `_scan_round_robin` when the scan executor's per-query cache is rebuilt.

This plan does NOT introduce a cross-GPU yield/requeue primitive (scan executor has no such mechanism per RESEARCH.md Q5; that would be a Phase 10+ redesign). It produces a data structure that Plan 09-03's test can assert against, and lays the foundation so that Bug 1's "same batch on two GPUs" symptom is impossible in the log record (even if runtime races in lock_or_prepare_batch remain — those are handled by the existing OOM retry budget in gpu_pipeline_executor bumped in commit 6d73680).

A secondary, defensive pass on `pipelineable_operator_data::prepare_for_processing` confirms that the existing `return std::nullopt` path cleanly propagates to callers without downstream deref.

Output: header + executor source updated; affinity map atomic with audit log; optional defensive log in prepare_for_processing; build exits 0.
