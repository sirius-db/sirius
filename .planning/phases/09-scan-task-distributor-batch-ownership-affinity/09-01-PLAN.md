<objective>
Fix Bug 2 from 08-08-DIAGNOSIS.md (hypothesis E): `parquet_scan_task::compute_task` entry observes `preferred_device_id=-1` because nothing writes `target_gpu_id` back to the scan task's state before dispatch. Consequence: `_datasource` is constructed on `backends.begin()` (GPU 0's io_backend) even when the task is running on GPU 1's dispatch thread — a cross-device I/O mismatch.

Fix: add `std::optional<int> _preferred_device_id` to `parquet_scan_task_local_state` (NOT the shared global state — see Pitfall 1 in RESEARCH.md), plumb `target_gpu_id` into it from `duckdb_scan_executor::manager_loop` BEFORE `_bounded_pool->dispatch`, and in `parquet_scan_task::compute_task` read it via a two-tier lookup that mirrors `gpu_pipeline_task::get_preferred_device_id()` at `src/include/pipeline/gpu_pipeline_task.hpp:188-194` (local wins over global).

Purpose: The scan-task dispatcher chooses the target GPU correctly (`select_target_gpu()` is right), but its choice is invisible to `compute_task`. Without this plumbing, the `_datasource` io_backend is device-mismatched against the stream and RAII guard the dispatch lambda installed. This is the first of two fixes needed for v1.2 ship.

Output: Header + two source files updated; build exit 0; a grep on the build log after a 2-GPU unit-test run should show `preferred_device_id=N` (N in {0, 1}) on at least one `[mgpu-probe] parquet_scan_task::compute_task entry` line.
</objective>
