# Plan 08-09 — HALTED

**Halt decision:** 2026-04-22, after Plan 08-08 diagnosis returned hypothesis **E (unexpected)**.

The pre-authored `08-09-PLAN.md` assumed hypotheses A/B/C/D from `08-VERIFICATION.md`. The 08-08 probe run rejected all four. The real bug is NOT in the `host_parquet` converter that Plans 08-01..07 patched — it's in the **scan-task distributor + pipeline task queue** allowing the same `batch_id` (already resident on one GPU) to be dispatched to a task on a different GPU.

## Evidence

From `.planning/phases/08-multi-gpu-sql-pipeline-fix/08-08-PROBE-LOG.log` (hive partition test, num_gpus=2):

```
batch_id=3 ... current_device=0 batch_device_id=0 target_device_id=0 lock_status=0 success=true
batch_id=3 ... current_device=1 batch_device_id=0 target_device_id=1 lock_status=3 success=false
```

Same `batch_id=3` (owned by GPU 0) dispatched twice: once to a GPU-0 task (success), once to a GPU-1 task (memspace-match failure → SIGSEGV downstream).

Also observed: `parquet_scan_task::compute_task entry preferred_device_id=-1, memspace_device_id=-1` — GPU preference plumbing is broken at scan-task dispatch time.

## Failure mode shift

- **v1.1 E2E verification + Plan 08-06 baseline:** `cudaErrorInvalidValue @ cuda_memcpy.cu:42`
- **Plan 08-08 observation:** SIGSEGV in scan-task distributor

Either the 08-07 breadcrumbs altered timing, or commits `1f80c2a` / `6d73680` from earlier in Phase 8 introduced a masking regression. This is worth noting for Phase 9 scoping but does not change the fix direction.
