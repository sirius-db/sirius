**B — apply_partition_inject_fn scalar leak**
Predicted: `host_parquet_to_gpu entry current_device=0 memspace_device_id=1` AND `exit current_device=1` AND the failing test is a HIVE-partition test (`gpu_execution hive partition - filter on data column` at test_gpu_execution_multi_format.cpp:815). Entry mismatch indicates caller-side hazard; the fact that the failing test exercises apply_partition_inject_fn (which calls value_to_cudf_scalar with default RMM) points at B. Matching fix: inline apply_partition_inject_fn scalar construction under explicit target-device RAII and explicit mr_ref.

**C — cucascade-internal stream mismatch**
Predicted: `host_parquet_to_gpu entry current_device=1 target_device_id=1` (entry is clean) AND failure STILL occurs — hazard is inside cudf::read_parquet's cucascade-backed datasource path on the target_stream which is correctly bound. Low likelihood per verifier note. This hypothesis would require a Sirius-side wrapper around the cucascade re-entry. Matching fix: wrap cucascade::io_backend::async_read_into_host_allocation call inside prefetched_data_source with a target-device RAII guard.

**D — mr_ref captured before RAII**
Predicted: `host_parquet_to_gpu entry current_device=0 memspace_device_id=1` AND the failing test is non-hive (TPC-H Q1 parquet). Even though `get_default_allocator()` should be device-specific, if mr_ref is bound before the RAII guard on line 98, it may pick up the caller's default resource rather than the target's per-device resource. Matching fix: reorder — declare target_device_raii FIRST, then mr_ref = target_memory_space->get_default_allocator().
