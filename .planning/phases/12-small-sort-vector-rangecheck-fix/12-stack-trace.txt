## Confirmation that the throw is libstdc++'s `_M_range_check`, NOT cucascade's `partition_idx out of range`
The local variable `__s` at frame #1 (above) literally holds:

    "vector::_M_range_check: __n (which is 2) >= this->size() (which is 2)"

This is the libstdc++ default `vector::at()` message format. cucascade's `pop_data_batch` throws with the custom message `"partition_idx out of range"`, which does NOT appear anywhere in this stack. Frame #2 is `cudf::table_view::select` (a libcudf function whose implementation calls `vector::at()` internally on the `_columns` vector); frame #3 is the FIRST Sirius frame. Therefore the fix-site is in Sirius, not cucascade.

## Note on test runner setup
The MCP test wrapper command for reproduction is:

    mcp__project-commands__run_command name=unit-tests filter="physical_order - small sort stays single-GPU"

The MCP `run_debug` mode=gdb wrapper sets `--abort` and replays this filter under gdb. The raw 1628-line GDB output (caching at `~/.claude/projects/.../tool-results/mcp-project-commands-run_debug-1777489710616.txt` in the agent's session memory at capture time) was filtered to the salient frames embedded above. To re-reproduce this artifact from scratch, run:

```bash
mcp__project-commands__run_debug command_name=unit-tests mode=gdb \
    command_args.filter="physical_order - small sort stays single-GPU" \
    flags="--batch -ex 'set pagination off' -ex 'catch throw' -ex 'commands' -ex 'silent' -ex 'python\\ntinfo=str(gdb.selected_frame().read_var(\"tinfo\"))\\nif \"out_of_range\" in tinfo:\\n  gdb.execute(\"bt 30\"); gdb.execute(\"quit 0\")\\nelse:\\n  gdb.execute(\"continue\")\\nend' -ex 'end' -ex run"
```

The Python guard skips past unrelated `std::runtime_error` throws and stops at the first `std::out_of_range` (the libstdc++ `vector::_M_range_check` we want).
