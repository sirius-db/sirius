Per D-05: These tests exercise lifecycle methods from SiriusContext's perspective. Per D-06: drain() is sufficient because pool->wait_all() ensures all dispatch lambdas have returned, releasing shared_ptr<data_batch> captures.

**Test 1: "start_stop_cycle" [downgrade_lifecycle]** (LIFE-01)
- Construct executor with nullptr memory_space (no monitor loop)
- Call start(), verify _running is true (submit a request that succeeds)
- Call stop()
- Call start() again, submit another request, verify it completes
- Call stop() again
- Verifies: start/stop can be called multiple times safely

**Test 2: "drain_clears_pending_requests" [downgrade_lifecycle]** (LIFE-01, LIFE-02)
- Construct executor, start()
- Submit 3 requests via request_free_memory (async, 0 repos so they complete quickly with 0 bytes)
- Wait for all futures to resolve
- Call drain()
- Submit a new request after drain, verify it completes
- Verifies: drain() allows the executor to continue processing new requests

**Test 3: "drain_releases_batch_references" [downgrade_lifecycle]** (LIFE-02)
- Construct executor with real memory manager (GPU space)
- start() the executor
- Create a data_repository, add a data_batch with GPU data
- Submit request_free_memory for those bytes, wait for it
- Verify the batch was downgraded (data moved to HOST)
- Call drain()
- After drain, verify no shared_ptr<data_batch> references are held by the executor
  - The test itself holds the only shared_ptrs; use_count() == 1 after drain
- Verifies: drain guarantees no dangling batch refs

**Test 4: "monitor_loop_triggers_downgrade" [downgrade_lifecycle]** (LIFE-03)
- Construct executor with real memory_space (monitor enabled)
- Create a data_repository with GPU data that exceeds the downgrade threshold
- start() the executor
- Wait up to 500ms for the monitor to detect pressure and trigger downgrade
- Verify that some data was moved from GPU to HOST tier
- stop() the executor
- Verifies: monitor loop detects should_downgrade_memory() and acts

**Test 5: "concurrent_api_safety" [downgrade_lifecycle]** (LIFE-04)
- Construct executor, start()
- Launch 4 threads, each calling request_free_memory(1024) concurrently
- All 4 futures must resolve without crash, deadlock, or exception
- Call drain() from a 5th thread while requests are in-flight
- Verify no crash and executor is still operational (submit + complete another request)
- Verifies: thread safety of public API

**Test 6: "cuda_stream_lifecycle" [downgrade_lifecycle]** (LIFE-05)
- Construct executor with real memory_space
- Before start(): _stream is nullptr (not directly accessible, but verified indirectly)
- Call start()
- Submit a request that requires GPU->HOST copy (uses the stream internally)
- Wait for completion — success means stream was created and usable
- Call stop()
- Call start() again
- Submit another request, wait for completion
- Verifies: stream created on start, destroyed on stop, re-created on next start
