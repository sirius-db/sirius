### Bug isolation (verified in this session, 2026-05-08)
- **D-01:** Q11 returns 0 rows at SF10+ regardless of num_gpus. Verified empirically:

  | Config | Q11 result | column-count warnings (id=17) | pipeline_task dispatches |

### Architectural hypothesis (UNTESTED at scaffold time — verify in plan-phase research)
- **D-03:** `src/planner/sirius_plan_cte.cpp:48-53` constructs `sirius_physical_cte` with `_types = right->types`:
  ```cpp
  cte = duckdb::make_uniq<sirius::op::sirius_physical_cte>(op.ctename,
                                                          op.table_index,
                                                          right->types,    // ← _types declared here
                                                          std::move(left),  // top/producer
                                                          std::move(right), // bottom/consumer
                                                          op.estimated_cardinality);
  ```
- **D-04:** `src/op/sirius_physical_cte.cpp:75-81` `execute()` is a passthrough:
  ```cpp
  return std::make_unique<pipelineable_operator_data>(
    dynamic_cast<const pipelineable_operator_data&>(input_data).get_read_only_batches(false));
  ```
- **D-05:** Mismatch: `_types` is set to consumer subplan's output types (e.g., 3 columns for the final Q11 result `(ps_partkey, value)`-like), but `execute()` forwards the producer's upstream batches (HASH_JOIN id=4 output, e.g., 5 columns).
- **D-06:** The validation function at `src/pipeline/gpu_pipeline_task.cpp:41-65` (`validate_operator_output_types`) detects the mismatch and logs a warning but does NOT throw. Downstream PROJECTION operators presumably select columns by index from the wrong-shaped batch, producing wrong/empty results.

### Likely fix shape (untested — verify before applying)

- **D-08:** Verify which child is producer in DuckDB's `LogicalMaterializedCTE` convention. Read DuckDB source (`duckdb/planner/operator/logical_materialized_cte.hpp`) or follow `op.children[0]->types` usage at `sirius_plan_cte.cpp:32` (which assigns to `working_table` types — that's the materialized output, so `children[0]` IS the producer). If true, the fix is `left->types` since `left = create_plan(*op.children[0])`.
- **D-09:** Cross-check: the recursive CTE planner (`src/planner/sirius_plan_recursive_cte.cpp`) — does it have the same mismatch shape? If yes, fix it too. If different shape, leave as-is.

## Existing Code Insights

### Reusable Assets
- **`sirius_physical_cte::cte_scans`** — vector of CTE_SCAN consumers; populated by the planner at line 56. Whatever shape these consumers expect should align with the CTE's `_types`.
- **`get_read_only_batches(false)`** — the passthrough mechanism in `execute()`; preserves batch shape (column count + types).
- **`validate_operator_output_types`** — the canary that fired the warning; reuseable as a self-check post-fix (warning count should drop to 0).
- **`mgpu_test_utils`** — Phase 22 added a comprehensive multi-GPU test infrastructure including `mgpu_env_params`, `scoped_mgpu_env`, `generate_parquet_surface`. Reuseable for the new SF10 Q11 test gate.
- **`RUN_TPCH_MGPU` macro** in `test/cpp/integration/test_gpu_execution_tpch.cpp` — current TPC-H test parameterization shape; new SF10 Q11 test should follow this pattern.

### Established Patterns
- **Operator types declaration** — `sirius_physical_operator(SiriusPhysicalOperatorType, types, estimated_cardinality)` constructor takes types via std::move; the operator base stores them and exposes via `get_types()`. Other operators (HASH_JOIN, PROJECTION, AGGREGATE) declare their own output types matching what `execute()` produces. CTE is the anomaly because it's a passthrough.
- **CTE meta-pipeline construction** — `sirius_physical_cte::build_pipelines` at `src/op/sirius_physical_cte.cpp:50-67` creates a child meta_pipeline for the materialization (children[0]) and continues current pipeline with consumer (children[1]). Producer and consumer have different downstream paths.
- **Validate-before-throw pattern** — `gpu_pipeline_task.cpp:41` validates output types but only logs warnings. This was likely added during early development as a defensive check; its presence-but-no-throw means a bug like K.7 ships silently.

<specifics>
## Specific Ideas

- **Direct one-line fix candidate (untested):** `cte = duckdb::make_uniq<sirius::op::sirius_physical_cte>(op.ctename, op.table_index, op.children[0]->types, ...)` — using the LogicalMaterializedCTE's children[0] types directly (the producer side). This bypasses the dependency on `left` already being moved by argument-evaluation-order.

- **Why `right->types` was likely chosen** (educated guess): the planner author may have intended the CTE to declare its OUTPUT types as what the consumer ultimately produces. But `execute()` is a passthrough — it forwards intermediate (producer-side) batches, not transformed (consumer-side) batches. The intended-vs-actual semantics diverged.

- **The 5-column batch coming into CTE id=17** at Q11 SF10/SF100: probably `(ps_partkey, ps_supplycost, ps_availqty, s_suppkey, n_nationkey)` or similar after the JOIN. Inspecting the actual column types via instrumentation (add `SIRIUS_LOG_INFO` printing actual types vs expected types) would confirm, but the column count alone is enough signal for the fix shape.

- **Test gate selection:** SF10 is sufficient to exercise `pipeline_task` (28 dispatches at SF10 vs 51 at SF100). SF10 dataset already on disk at `/home/felipe/sirius/test_datasets/tpch_parquet_sf10/`. Test runtime should be sub-minute even with full TPC-H Q11 logic, well under the existing `[TPC-H][parquet]` budget.

- **Argument evaluation order in C++:** the existing planner code does `make_uniq<sirius_physical_cte>(..., right->types, std::move(left), std::move(right), ...)`. This is technically UB pre-C++20 because argument evaluation order is unspecified. C++17/20 sequencing guarantees only intra-argument operations. The expression `right->types` may be evaluated AFTER `std::move(right)` depending on compiler. This is unrelated to K.7's primary cause but worth noting — the fix should also stabilize this by reading `op.children[1]->types` (or `op.children[0]->types` per the new fix) instead of `right->types`.

</specifics>

## Deferred Ideas

- **Other queries with similar CTE planner bugs.** This phase fixes the planner globally; if a TPC-H query other than Q11 uses materialized CTE with producer/consumer type mismatch, it will also be fixed by D-07. But scoping a Q11-specific gate covers the canary; broader test coverage (all 22 TPC-H queries at SF10) is a separate test-quality improvement phase.
- **Strengthening `validate_operator_output_types` to throw instead of warn.** The validator's silent-warning-then-return behavior is what allowed K.7 to ship silently. Changing it to throw would make column-count mismatches a hard error during CI. But changing this may surface other latent bugs (the comment about `delim_join` warnings being expected suggests at least one operator legitimately violates the contract). Out of scope for 22.3.
- **Recursive CTE.** If `sirius_plan_recursive_cte.cpp` doesn't have the same shape, no fix needed. If it does, addressed in 22.3 per D-09. If it has a *different* shape that's also broken, surface as 22.4.
- **DuckDB CPU baseline comparison.** Q11 SF10 should match DuckDB's standalone `read_parquet`-based execution. Adding that comparison as a property test is a v1.6+ test-quality improvement.
