## Executive summary

Phase 22.3 was scaffolded to close K.7 — the residual carry-forward from Phase 22.2 that "Q11 returns 0 rows at any scale ≥ SF10 regardless of num_gpus." During execution, the architectural hypothesis (D-03..D-08 in `22.3-CONTEXT.md`) was empirically tested and found to be wrong: the column-count validator warning was a symptom of a misdeclared operator schema, not a cause of empty results.

Deeper investigation against a DuckDB CPU baseline established that **K.7 is not a Sirius bug**. The reproduction SQL fixture used a constant `0.0001` HAVING fraction instead of the spec-compliant `0.0001/SF` scaling. At SF10, `sum * 0.0001 ≈ 81M`, which exceeds `max(per-partkey value) ≈ 20M` — so the correct answer for that exact SQL is 0 rows. DuckDB CPU returns 0 rows for the same query. Sirius matches. With the spec-compliant fraction (`0.00001` at SF10), Sirius returns 8,685 rows, identical to DuckDB CPU.

The phase was re-scoped from "fix K.7 (data-flow bug)" to "cleanup CTE operator types declaration" — the validator-warning fix is a real correctness improvement (the CTE op was lying about its output schema even though no downstream consumer actually misbehaved because of it), and a new SF10 Q11 regression test gates against future genuine breakage of the CTE materialization path at non-trivial scale.

## What shipped

### Code change

**`src/planner/sirius_plan_cte.cpp:43-58`** — Changed CTE operator's `_types` from `right->types` (consumer subplan output) to a captured copy of `left->types` (producer/materialization schema). `left = create_plan(*op.children[0])` is the materialization side per DuckDB's `LogicalMaterializedCTE` convention, and `sirius_physical_cte::execute()` is a passthrough that forwards the producer's batches. Capturing `left->types` into a local `producer_types` before the constructor call also stabilizes argument evaluation order (the previous expression read through `right` while `right` was being moved in the same call).

Net change: +6 lines added, +2 lines comment, −1 line removed (8-line diff).

## Investigation summary (where the original hypothesis went wrong)

### What CONTEXT.md predicted (D-03..D-08)
The CTE op declared `_types = right->types` (consumer 2-col shape) but `execute()` forwarded producer 5-col batches. The validator at `gpu_pipeline_task.cpp:41` detected the mismatch and warned. CONTEXT hypothesized that downstream PROJECTIONs were "presumably select[ing] columns by index from the wrong-shaped batch, producing wrong/empty results."

### What empirical investigation found
- **The fix eliminates the validator warning** — confirmed at SF10 (was 1 warning, now 0) and SF100 (was 4 warnings, now 0).
- **The fix does NOT change the row count** — Q11 still returned 0 rows at SF10 post-fix. The validator's warning was purely cosmetic; downstream operators were correctly using their own `_types` declarations (set by their own planners), not the CTE op's misdeclared output schema. The 5-col batch flowed correctly into the consumer pipelines (Pipeline #13 PROJECTION id=6 and Pipeline #16 PROJECTION id=9, both verified to receive 323,920 rows × 5 cols at SF10).
- **The runtime data flow was correct end-to-end** — pipeline trace logs at trace level showed every operator processed the expected row counts: HASH_JOIN(323,920) → CTE passthrough → PROJECTION(323,920) → HASH_GROUP_BY(304,774); subquery branch UNGROUPED_AGGREGATE(1 row threshold). NESTED_LOOP_JOIN id=16 received `[304774, 1]` row inputs and produced 0 — but **this is correct** given the SQL fixture's 0.0001 constant: the threshold value (81,029,137.65) exceeds max single-partkey value (~20M) at SF10, so all rows correctly fail the HAVING comparison.
- **DuckDB CPU baseline confirmed the 0-row result is correct** for the broken SQL fixture and 8,685 rows for the spec-compliant fixture. Sirius matches DuckDB exactly in both cases.

### Root cause of the misdiagnosis
The CONTEXT.md scaffolding was based on Phase 22.2's "K.6 closure exposed K.7" framing, but the K.7 reproduction (`/tmp/claude/p22_2_sf10_q11.sql`) was never validated against DuckDB CPU baseline. The 0-row result was assumed to be a Sirius bug because SF1 returned 51 rows. In reality, SF1 happens to return 51 rows because at SF1 the threshold (8,103) is BELOW the max single-partkey value (~17M). At SF10+, the threshold scales linearly with sum but max single-partkey value scales ~linearly with rows — eventually the constant `0.0001` makes the threshold exceed max value. This is intrinsic to the broken SQL fixture, not Sirius.

The lesson is captured in the phase-22.3 work: **always validate reproductions against DuckDB CPU baseline before scaffolding a fix phase**.
