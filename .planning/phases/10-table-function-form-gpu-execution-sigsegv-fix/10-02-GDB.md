### Heisenbug explanation

Catch2 installs a SIGSEGV signal handler that uses `setjmp`/`longjmp` to recover from signals and mark tests as failed. Under GDB, SIGSEGV is intercepted by GDB before it reaches Catch2. With the default GDB `handle SIGSEGV` behavior, GDB logs the signal and then passes it to the process. Catch2's `longjmp` recovery means the test completes (albeit with a FAILED status). With `--abort` as the test filter mode, the process should exit non-zero, but GDB's `run` in batch mode waits for the entire process to exit before printing the backtrace. The net result: the backtrace GDB captures is NOT from the SIGSEGV (because execution already jumped away via longjmp) but from the SIGABRT that fires on process exit (or from an unrelated background thread). Both 1-GPU and 2-GPU GDB runs exit 0, hiding the SIGSEGV entirely.

**Confirmed hypothesis:** `H1`

**Rationale:** The SIGSEGV occurs specifically and only in the parquet-fixture tests (`GPUExecutionParquetFixture` tests), not in DuckDB-fixture tests. Test #328 (`gpu_execution - filter equality`, DuckDB fixture) passes both `CALL` and `SELECT * FROM` forms immediately before test #329 (`gpu_execution - filter equality parquet`, Parquet fixture) SIGSEGVs. This isolates the fault to the parquet scan path. Static analysis of the FU17 partial-fix diff reveals the exact root cause: `sirius_physical_parquet_scan.cpp` (original code, lines ~119) constructs a `gpu_expression_translator` using `rmm::cuda_stream_default`. This translator allocates device buffers for `cudf::string_scalar` / `cudf::numeric_scalar` literals (e.g., the integer constant `1` in `WHERE n_regionkey = 1`) via `cudaMallocAsync` on the default stream. Later, `parquet_scan_task.cpp:492` creates a `planning_stream` and calls `filter_row_groups_with_stats(..., planning_stream.view())` passing these scalars as the filter predicate. Since `planning_stream` does not wait for the `cudaMallocAsync` events on `rmm::cuda_stream_default`, there is a stream-ordered memory race — the scalar buffers may not yet be visible on `planning_stream` when the kernel launches, causing `cudaErrorIllegalAddress` inside `cudf::detail::compute_column_kernel`. The test-ordering dependency arises because CUDA stream scheduling is nondeterministic across `SiriusContext` pause/resume cycles; the race manifests when certain stream synchronization events from prior tests are absent. The FU17 partial fix (switching to an explicit `translation_stream` with synchronization) eliminates the race, confirming H1.

## Appendix: GDB Heisenbug — Root cause explanation

**Why GDB prevents the SIGSEGV from manifesting:**

Catch2 v2 installs a POSIX signal handler for SIGSEGV that calls `sigsetjmp`/`siglongjmp` to record the test as failed and resume execution from the test's outer `TEST_CASE_METHOD` frame. Under GDB in batch mode:

1. GDB intercepts SIGSEGV before the application signal handler.
2. GDB prints the signal notification (`Program received signal SIGSEGV`) and executes the `-ex` commands (`bt full`, etc.).
3. GDB then `continue`s the process (batch mode default), delivering the SIGSEGV to the application.
4. Catch2's signal handler fires, `longjmp`s back to the test frame, marks the test as failed, and execution continues normally.
5. With `--abort`, Catch2 should exit after the first failure, but the exact interplay of GDB `continue` + Catch2 signal recovery + `--abort` results in the process completing cleanly under GDB.

The net result: GDB's interference suppresses the crash. The SIGABRT frames captured in both GDB logs are from DIFFERENT failure paths (config init error and cucascade io_worker teardown) unrelated to the SIGSEGV in `compute_column.cu`.

**Alternative GDB approaches considered and not pursued:**
- `handle SIGSEGV stop print nopass`: Tested (3rd GDB run). Still exits 0 — GDB stopped at SIGSEGV but since Catch2 couldn't longjmp, the process was in an unknown state and GDB's `bt full` may have captured a stale frame. The test binary terminated normally rather than crashing.
- Core dump analysis: Could not enable (`ulimit -c` is 0 in the sandbox and cannot be raised). The `debug-coredump` skill would have been ideal.
- Debug build: Would give exact line numbers but requires a full rebuild (`cmake -DCMAKE_BUILD_TYPE=Debug`) which is expensive. The static analysis approach yielded the same result more quickly.
