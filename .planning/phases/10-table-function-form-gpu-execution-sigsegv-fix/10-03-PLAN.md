    Fix shape (driven by 10-02-GDB.md fault_frame and the diff between PROCEDURE-form (works) and TABLE_FUNCTION-form (crashes)):

    The 09-04-VALIDATION.md Open Issue notes that `CALL gpu_execution(...)` (PROCEDURE form) returns Sirius result directly — pre-crash log shows `Execute query time: 6.46 ms` on the first invocation. The second call uses `SELECT * FROM gpu_execution(...)` (TABLE_FUNCTION form), which wraps the result through DuckDB's table-function binding. The likely divergence:

    Candidate root causes (apply whichever the gdb backtrace fingerprints):

    a. **GPUResult lifetime cut short:** `SiriusTableFunctionData` doesn't keep the GPUResult / underlying GPU columns alive across the materialization scan. Fix: store the GPUResult (or its column-view tree) as a member of `SiriusTableFunctionData` and release only on bind-data destruction.

    b. **Bind-data move-vs-copy bug:** `SiriusTableFunctionBind` uses `make_uniq<SiriusTableFunctionData>()` and returns it; `SiriusTableFunctionFunc` casts via `(SiriusTableFunctionData&)*data_p.bind_data`. If a member is moved/swapped/reset between bind and func calls, the func call sees a zombie state. Fix: audit all moves of SiriusTableFunctionData; ensure the GPU pointers/columns are stably-addressed.

    c. **Multi-chunk emission not implemented:** the TABLE_FUNCTION's `SiriusTableFunctionFunc` may be called repeatedly to emit chunks until exhausted. If state-tracking (offset, row index, done-flag) is missing, the second call into the func re-runs the whole query against an already-consumed result.

    d. **Stream/device binding leak:** the bind-time function captures a CUDA context/stream that's torn down by the time the func runs. Fix: re-acquire device context inside SiriusTableFunctionFunc via cuda_set_device_raii.

    Concrete steps:

    4. Hygiene: no `rmm::cuda_stream_default` introductions; if you add a stream acquire, use the existing topology stream pool (`SiriusContext::get_topology()->get_stream_for_device(...)`)
