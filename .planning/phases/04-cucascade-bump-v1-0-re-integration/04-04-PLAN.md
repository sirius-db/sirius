### YAML config reader on dev

`src/sirius_config.cpp` / `src/include/config.hpp` — per CLAUDE.md "Architecture" section:
  - Runtime configuration loader
  - Reads YAML (via yaml-cpp) at startup from `$SIRIUS_CONFIG` or a default path
  - Exposes `get_hw_topology()` (system_topology_info — GPU count, NUMA domains, GPU↔NUMA mapping)
  - Exposes per-GPU `gpu_memory_space_config` (includes `numa_id` field per research OQ-2)
  - NO libconfig++ dependency anywhere (verified by research: grep 'libconfig' src/ returned 0 hits on dev)

### libconfig → YAML translation map (from src/sirius_config.cpp:34-65)

If Task 1 Step 1 finds any libconfig symbol reintroduced by Plans 02-03, consult this map (derived from dev's PR #565 YAML keys in `src/sirius_config.cpp` lines 34-65 and the per-GPU config parser at lines 267-284):

| Likely libconfig symbol | YAML equivalent in dev |
|------------------------|------------------------|
| `libconfig::Config cfg; cfg.readFile(path);` | `sirius::config::load_from_yaml(path)` → returns `sirius_config` |
| `cfg.lookup("gpu_count")` / `cfg.lookup("num_gpus")` | derived from `config_.get_hw_topology().gpus.size()` — topology discovery, no YAML key |
| `cfg.lookup("gpu_numa_node")` | `config_.get_hw_topology().gpus[i].numa_node` (derived) OR `gpu_memory_space_config.numa_id` (YAML key `numa_id` per section 267-284) |
| `cfg.lookup("gpu_memory_budget")` / `gpu_mem_bytes` | `gpu_memory_space_config.total_bytes` (YAML key `total_bytes`) |
| `cfg.lookup("host_memory_budget")` | `host_memory_space_config.total_bytes` |
| `#include <libconfig.h++>` | `#include "sirius_config.hpp"` + `yaml-cpp/yaml.h` if direct YAML access needed |
| `libconfig::Setting& root = cfg.getRoot();` | No equivalent needed — `sirius_config` exposes typed getters |

Any libconfig symbol NOT in this table lacks an obvious YAML equivalent and requires user judgment.

### v1.0's multi-GPU configuration consumers

v1.0 does NOT load libconfig. Per research section 2 and OQ-2, v1.0 consumes:
  - `config_.get_hw_topology().gpus[i].numa_node` — already YAML on dev
  - `reservation_manager_configurator::build()` — takes YAML-loaded memory_space_configs
  - `memory_manager_->get_memory_spaces_for_tier(Tier::GPU)` — downstream of YAML config
  - `preferred_numa_node` (new in Plan 03) — populated from hw_topology at context init, NOT read from YAML directly

Conclusion: PORT-03 is a no-op from a code-change perspective unless a specific config field is missing on dev. The plan is primarily VERIFICATION; Task 1.5 is a conditional remediation that runs only if the grep gate finds a libconfig reintroduction.
