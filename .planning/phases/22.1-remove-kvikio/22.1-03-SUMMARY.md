## Confirmation: scan_data.gpu_memory_space is non-null at read_table_from_metadata entry

The plan's Task 2 design assumption was that `scan_data.gpu_memory_space` is non-null at the time `read_table_from_metadata` is invoked. Verification:

- `parquet_scan_data::prepare_for_processing(requested_memory_space, stream)` (src/include/op/scan/parquet_scan_operator_data.hpp:147-151) writes the requested memory space pointer into `gpu_memory_space` BEFORE the operator's `execute()` calls `read_table_from_metadata`. The cucascade pipeline executor populates this hook for every source task — see PIN-MGPU-01 / Phase 22 22-01 PLAN.
- The pre-existing operator code at `sirius_gpu_parquet_scan_operator.cpp:154` (now line ~190 after my edits) already constructs `rmm::device_async_resource_ref mr_ref(scan_data.gpu_memory_space->get_default_allocator())` from the same field. If that field were null, the pre-22.1 code would have segfaulted; since it didn't, the field is reliably non-null here.
- Belt-and-suspenders: my migration adds an explicit `if (scan_data.gpu_memory_space == nullptr) throw runtime_error(...)` guard so any future regression that would null this field surfaces as a clear Phase 22.1 D-04 throw instead of a segfault.

The migration is therefore safe — single-GPU-per-scan_data, with the per-GPU ioctx selected once per call from the populated `gpu_memory_space` field.
