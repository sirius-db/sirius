### Race interpretation

- **Writer (cudaMallocAsync side):** `sirius::op::sirius_physical_grouped_aggregate::execute` produces a cudf::table on stream A via `gpu_aggregate_impl::local_grouped_aggregate` → `cudf::table::table(copy ctor)` → `cudf::column::column(copy ctor)` → `rmm::device_buffer::allocate_async` → `cucascade::memory::detail::reservation_aware_resource_adaptor_impl::allocate` → `rmm::mr::cuda_async_view_memory_resource::do_allocate` → `cudaMallocFromPoolAsync` on writer stream.
- **Reader (cudaMemcpy side):** `sirius::pipeline::lock_or_prepare_batch` → `cucascade::data_batch::convert_to<gpu_table_representation>` → `cucascade::convert_gpu_to_gpu` (representation_converter.cpp:801) → `reconstruct_column_p2p` (line 656) → `alloc_and_peer_copy_async` (line 590) → `cudaMemcpyAsync` on a different (target) stream.
- **The race:** `cucascade::convert_gpu_to_gpu` syncs ONLY (a) the caller's stream `stream.synchronize()` at representation_converter.cpp:809 and (b) the source-device-wide `cudaDeviceSynchronize()` at line 827. Neither of these establishes ordering with the original WRITER stream's allocation event, because the source memory was allocated from a `cudaMallocAsync` pool with stream-ordered semantics that only become visible on streams that explicitly observe the allocation event via `cudaStreamWaitEvent`. Source-device-wide `cudaDeviceSynchronize` is documented as insufficient for stream-ordered allocations issued on a different mempool context (per project_phase08_fu17.md: "cudaDeviceSynchronize() does not implicitly establish event ordering for cudaMallocAsync allocations that were issued on a completely different context"). The sanitizer confirms this empirically: even with the source-device sync in place, every GPU→GPU conversion's first peer-copy reads memory that the sanitizer cannot prove has been allocated on the reader's stream timeline.

## Recommended Fix Shape

cucascade-side gpu_table_representation extension with set_writer_event/get_writer_event accessor; submodule bump required

Concrete: extend `cucascade::gpu_table_representation` (cucascade/include/cucascade/data/gpu_data_representation.hpp) with a `cudaEvent_t _writer_event` member and `set_writer_event(cudaEvent_t) / get_writer_event() const` accessors. At every Sirius write-site that produces a `gpu_table_representation` (notably `gpu_aggregate_impl::local_grouped_aggregate` and any other operator's cudf::table copy ctor / move ctor), record an event on the writer stream and call `set_writer_event` immediately after the cudf::table is wrapped. In `cucascade::convert_gpu_to_gpu` at representation_converter.cpp:801-854, call `cudaStreamWaitEvent(target_stream, gpu_source.get_writer_event(), 0)` BEFORE the `for (cudf::size_type i = 0; i < src_view.num_columns(); ++i)` loop that issues `reconstruct_column_p2p` (line 842). This replaces the brute-force `cudaDeviceSynchronize` at line 827 with precise event-ordered synchronization that does establish cross-mempool visibility. The existing `stream.synchronize()` at line 809 can stay (it covers the caller-side stream) and the source `cudaDeviceSynchronize` at line 827 can stay (defense-in-depth) or be replaced. The minimum viable patch is just the `cudaStreamWaitEvent` plus the writer-event hookup at the producer site.

## Notes for Wave 4 (13-04 fix plan)

1. **Submodule bump is unavoidable** — the fix lands in `cucascade/src/data/representation_converter.cpp` and `cucascade/include/cucascade/data/gpu_data_representation.hpp`. After landing the cucascade change on a feature branch and bumping the submodule pin in Sirius, the sanitizer must be re-run to confirm the FIRST error has either disappeared (race closed) or moved to a NEW site (next race in queue). Per 13-RESEARCH.md Pitfall 1, the FIRST-error-fingerprint protocol applies again post-fix.
2. **Sirius producer-side hookup** — every operator that constructs a `gpu_table_representation` from a writer stream MUST call `set_writer_event` immediately after the table is wrapped. Audit candidates (the writer side of the race): `gpu_aggregate_impl::local_grouped_aggregate` (confirmed in this trace), but also any operator that returns a fresh `cudf::table` produced on a non-default stream. A repository-wide grep for `std::make_unique<cucascade::gpu_table_representation>` and `std::make_unique<gpu_table_representation>` is the right starting point.
3. **Q11-specific shape** — the bug is NOT Q11-specific. The race fires on every GPU→GPU representation conversion across all 22 TPC-H queries when SCHED-RR is enabled. Q11 is just the FIRST query whose plan shape (DELIM_JOIN over 3-table join in batch mode after Q1-Q10 have warmed up cross-test state) makes the cumulative race pile up enough to corrupt the GPU context and produce the user-visible 1800s SIGTERM timeout. Fixing the race closes the entire `[TPC-H][parquet]` filter under SCHED-RR, not just Q11.
4. **HYG preserved** — the fix must NOT introduce `rmm::cuda_stream_default` outside `src/legacy/`. Use explicit `rmm::cuda_stream` per device, threaded through the `gpu_table_representation` constructor.
