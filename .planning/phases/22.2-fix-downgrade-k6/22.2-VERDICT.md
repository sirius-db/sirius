## A — Root cause

`src/downgrade/downgrade_executor.cpp:62-89` (pre-fix shape):

```cpp
void downgrade_executor::start() {
  // ...
  {
    auto device_id = _memory_space ? _memory_space->get_device_id() : 0;
    _stream_pool   = std::make_unique<cucascade::memory::exclusive_stream_pool>(
      rmm::cuda_device_id{device_id}, _config.thread_pool.num_threads);   // ← crashes for HOST-tier
  }
  absl::AnyInvocable<void() noexcept> per_thread_init = nullptr;
  if (_memory_space) {                                                     // ← only checks non-null
    auto device_id  = _memory_space->get_device_id();                     // ← returns -1 for HOST
    per_thread_init = [device_id]() noexcept {
      cudaError_t err = cudaSetDevice(device_id);                          // ← cudaSetDevice(-1) fails
      // ...
    };
  }
}
```

`SiriusContext::initialize` creates `downgrade_executors_` for **both** `Tier::GPU` and `Tier::HOST` via `create_executors_for_tier(...)`. HOST-tier memory_spaces have `get_device_id() == -1` (sentinel for "no GPU device"). The `start()` method unconditionally:
1. Constructs `exclusive_stream_pool` keyed to `rmm::cuda_device_id{-1}`
2. Wires per-thread init that calls `cudaSetDevice(-1)`

Both fail at runtime. Symptoms:
- At SF1: silent — HOST-tier executor rarely services downgrade requests when host pressure is low.
- At SF100: host pressure routes work to the dead worker; the executor errors out; `task_scheduler.cpp:205` catches and drains. Query returns empty result.

---

## B — Fix

`src/downgrade/downgrade_executor.cpp:62-92` (post-fix):

Gate both the stream pool's device_id selection and the per-thread CUDA-binding lambda on `_space_id.tier == cucascade::memory::Tier::GPU`. For non-GPU tiers, default the stream pool to GPU 0 (the stream is async-ordering metadata; host→disk migration work is CPU-side) and skip the per-thread init entirely.

Diff is +13 / -3 LOC + 13 lines of explanatory comment block (28 LOC total change). One file, no signature changes, no caller updates needed.

### K.7 isolation evidence (CTE column count mismatch)

```
[2026-05-08 09:50:28.882] [warning] [gpu_pipeline_task.cpp:56]
  gpu_pipeline_task: operator 'CTE' (id=17) output batch 0 column count mismatch:
  got 5, expected 3
```

Fires 4× during SF100 Q11 num_gpus=2; absent at SF1 (Q11 SF1 num_gpus=2 returns correct rows). Operator id=17 is the CTE that materializes the HAVING-clause subquery (the `sum(ps_supplycost * ps_availqty) * 0.0001` threshold). The CTE produces 5 columns where downstream expects 3 — likely a partition-merge / GPU-aggregation shape mismatch specific to scale-factor and num_gpus combinations.

K.7 is a separate phase candidate. Out of scope for Phase 22.2.
